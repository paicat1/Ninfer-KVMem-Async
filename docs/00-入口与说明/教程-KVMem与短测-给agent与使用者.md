### 0.2 测速：**数数字语料，1000 token 进 / 1000 token 出**（照下面做，**不随包发脚本**）

> **本包故意不带测速脚本。** 脚本本身会出问题（PowerShell 版本、执行策略、环境变量、引号转义都会让它挂），
> 而对方看到"工具报错"会误判成"部署失败"。所以这里只给**指令**：用你手上任何 OpenAI 兼容客户端发**一条**请求即可。

**发什么**（题面就是"顺序数字 + 接着数"，逐字照抄）：

```
1 2 3 4 5 ... 一直到 300        （就是这一串数字本身，用空格隔开）

Continue the same number sequence from the next number. Output numbers only,
in the same space-separated format, and keep going until the length limit.
```

**怎么设**：
- 地址 `http://127.0.0.1:<端口>/v1/chat/completions`（PTQ1 档 8095 · PQ2-mtponly 档 8091 · PQ2-dflash 档 8094）；
- `model` 填启动器里的 `--model-id`（默认 `qwen3.8-27b`）；
- **`max_tokens = 1000`**；`temperature = 0`；
- 思考已由启动器关掉（`--default-reasoning-effort none`），**不要再打开**；
- 只要**一条**请求。`finish_reason = length` 是正常的（它就该写满 1000 token）。

**回答长什么样**：继续数下去（`301 302 303 …`）。若它答成别的样子，说明请求写错了，不是引擎的问题。

**回报这三个数** —— 去**引擎自己的控制台**抄那一行（这是权威读数，别自己算）：

```
req#1 done | openai-chat | output limit | prompt <N> | output 1,000 | cache 0 (0.0%) |
   TTFT <N> ms | total <N>s | queue <N> ms | prefill <N> tok/s | decode <N> tok/s | mtp accepted <a>/<b>
```

**期望量级**（构建机实测，RTX 4080 SUPER / sm_89 / 16 GB 级卡、池 17920、数数字语料 1000 出）：

| 档位 | 题面 | TTFT | 预填 | 解码 | 1000 token 总耗时 |
|---|---|---|---|---|---|
| **PTQ1_0**（`--spec mtp`） | 1,133 token | 578 ms | **1.97k tok/s** | **194.6 tok/s**（mtp 接受 88.1%） | **5.7 s** |
| **PQ2 全量**（`--spec dflash2`） | 2,533 token | 754 ms | **3.52k tok/s** | **278.0 tok/s**（dflash2 接受 100%） | **4.4 s** |

- 卡型/档位不同，**2 倍以内**都算正常；**差 3 倍以上**再按 §6 第 3 类上报（附证据）。
- **语料不能换**：同一台机上换成散文，解码会掉一半（278 → 160 tok/s）。用数数字才能横向比。

**★ 用 dflash 版本模型时，必须把 dflash 窗口数设成 12**（不是 4）：

- 也就是启动器里的 **`--draft-tokens 12`**（`start-pq2-dflash.bat`；**本包已默认改成 12**，你只需确认没被改回 4）。
- **为什么**：dflash2 草稿头在"数数字"这种可预测输出上几乎全中，窗口越深收益越大 —— 构建机实测同一台机、同一题面：
  **窗口 4 ⇒ 解码 278 tok/s（1000 token 4.4 秒）**；**窗口 12 ⇒ 解码 600 tok/s（1000 token 2.4 秒）**，约 **2.2 倍**。
- **代价（写清楚，别只讲好处）**：输出**不可预测**时（随机数、开放问答）窗口 12 反而更慢（实测同机随机四位数：
  184 vs 265 tok/s），因为多出来的草稿要逐条验证。**换档位/换任务时可回头用 4 对比一次**。
- 只对 **dflash2 档**下这条指令；`--spec mtp` 的档位（PTQ1 / PQ2-mtponly）另有 `--adaptive-mtp` 这条路（**未测**，要试先问 UP主）。

## §1 给使用者：KVMem 是什么（一句话 + 一个类比）

**一句话**：KVMem 让"**显存里只放一小块 KV 缓存**"变成合法配置 —— 长上下文不再要求显存装得下，
装不下的部分留在**内存（主机侧）**，每次需要时按"**跟当前问题最相关**"的原则搬回来一小批。

**类比**：显存是你的**书桌**，内存是**书架**，KVMem 是那个**帮你按问题去书架取书**的助手。
没有它，书桌放不下的内容等于不存在（模型会说"文里没有这句话"）；有它，助手每轮按你的问题取回最相关的几本。

**它解决的具体病**（这个项目上实测过的）：题面比显存池大 ⇒ 中段内容"消失"，
**没有报错、HTTP 200、答案看上去很合理但是错的**（静默答错）。KVMem 就是治这个的。

## §2 你的显存账怎么算（三个数，一次算清）

| 旋钮 | 含义 | 举例 |
|---|---|---|
| `--kv-capacity` | **设备池**：显存里放多少 token 的 KV（64 token = 1 页） | `4000` ⇒ 63 页 ⇒ 运行时约 1.4 GiB |
| `--max-context` | **逻辑上下文**：一次请求最多能有多长 | `262144` |
| `--host-kv-mib` | **主机池**：内存里留给"搬出来"的 KV | `16384`（16 GiB） |

**容量规则（引擎启动期就会检查，不满足直接拒绝并报数字）**：
`主机池页数 + 设备池页数 ≥ 逻辑上下文页数`。
换算（本模型 k8v4）：**每 1 token 的逻辑上下文 ≈ 25 KiB 主机池** ⇒ 256K≈6.6 GiB · 512K≈13.2 GiB · 1M≈26 GiB。

**实测（这就是"能用"的样子）**

| 形状 | 设备池 | 结果 |
|---|---|---|
| 题面 42k token | **4,032 token（63 页）** | 两轮提问都答对（6/6 + 6/6），引擎侧 `SELECT` 252 行 |
| 题面 94.7k token（超池 **23.5×**） | 4,032 token（63 页） | 两轮都答对（3/3 + 3/3），零静默错 |

⇒ **小卡（≤10 GB）用 PQ2-mtponly 档 + 小设备池 + 大主机池，长题面是可以用的。**

| 档位 | 启动器 | 适用 | 端口 |
|---|---|---|---|
| PTQ1_0 | `start-ptq1-mtp.bat` | RTX 30/40/50 系，5.96 GiB 模型 | 8095 |

**三件已经自动、你不必设的事**（2026-10-02 引擎换代后）：
1. **内容打分默认开**：只要启动器设了 `NINFER_KV_WINDOW`，检索就按"与问题相关"排序 ——
   **不需要**再设 `NINFER_TERNARY_KVMEM*` 任何变量；
2. **检索窗口 = 你的问题**（64 行）—— 这是让"小池也不答错"的关键那一刀，已内置；
3. **PTQ1 快路默认开**（`NINFER_TERNARY_PTQ1_FAST`，启动器显式写着）。

**怎么确认它在工作（两条日志行，缺一不可）**
```
[ring] content scoring ON by default (the ring is configured): ...      <- 启动期
kvmem_score: SELECT label=text_prefill_chunk n_blocks=... query_tokens=64 ...   <- 发过请求后
```
**第二条行数 = 0 ⇒ 打分没跑、退回词法排序 ⇒ 小池下会静默答错。** 这一条是本教程最该记住的判据。

## §4 KVMem 的缺点与边界（诚实清单，照抄请一起抄走）

1. **设备池不是"越小越好"**：已测下限是 **4,032 token（63 页）**；
   再小会让"每轮可搬回的页数"（设备池 × 50%）变得很薄，**未测**，别拿它去压极限。
2. **主机池是真的内存，而且是钉住的**：`--host-kv-mib 16384` = 16 GiB 常驻内存。
   机器内存不够就别硬上大上下文（启动期会拒绝，不会静默降级）。
3. **跨页缝截断**：针/关键串正好跨在两页交界处时，若只搬回一侧，答案可能被截半（如 `ARCH-4201` → `ARCH-420`）。
   这是**已知未修**的固有性质，表现为"答案看起来像被砍了尾巴"。
4. **dtype 覆盖不均**：小池下的验收只在 `--kv-dtype k8v4`（交付档）上做过；
   其它精度"掩码接线"验过、**小池验收没做**。
5. **2 分钟以上的冷预填仍可能在连接层被掐**（客户端报"连接被关闭"）：
   根因**未定位**；已做缓解（Windows 补 TCP keep-alive、服务端 keep-alive 窗口 5s→120s、读写超时 300s）。
   **缓解 ≠ 已修**；遇到就按 §6 上报。
6. **推测解码（MTP/dflash2）的收益取决于任务**：可预测输出（数数字、模板化文本）解码可快 2 倍以上
   （实测 1000 token：278 → 600 tok/s，draft 4 → 12），随机/开放文本反而更慢。**别拿一个任务的数当通用值。**
7. **它不是"无限上下文"**：逻辑上下文仍有上限（`--max-context`），超了请求会被拒（这是对的，不是 bug）。

**判活必须真发一条请求**（§0.2 那一条数数字请求就够）。

**三条最常见的误判**（都是踩过的）：
1. **把"截断"当"丢上下文"**：`max_tokens` 太小、或思考没关，正文被砍 ⇒ 看着像 KV 丢内容。
   **先确认 `finish_reason != length` 且答案非空**，否则这条读数直接作废。
2. **把"思考绕圈"当引擎 bug**：那是**模型侧**行为，处方在 `docs\04-思维循环的防治.md`（三层）。
3. **把"长测试没跑完"当部署失败**：§0.1 的 15 分钟清单才是验收口径。

## §6 遇到这三种情况，**直接找 UP主**（不要自己硬调）

> UP主 这边对这三类都有**成套解决方案**（含参数预设、平台层护栏、以及按卡差异的处方）。

| # | 情况 | 你要带上的证据 |
|---|---|---|
| 1 | **思考循环**（反复绕圈 / 空交付 / 固定点 / 半截） | 卡与档位 · 逐字 argv · 一轮完整原文（含 `finish_reason`）· 是否已按 `docs\04-思维循环的防治.md` 上过 L1/L3 |
