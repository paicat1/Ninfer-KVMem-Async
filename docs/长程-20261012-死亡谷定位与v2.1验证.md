## 0. 背景与目标

- 现状：本仓自持树全量干净构建（版本 G，`G_clean_93285948`）在**多轮深堆积下几分钟内跌入死亡谷**

## 2. 已定案（2026-10-12 08:1x）

### 2.1 挂账45 假设**证伪**（原"中文 /showIncludes 前缀 → 记不到头依赖"不成立）

- 证据：`ninja -t deps src/models/.../materialization.cpp.obj` → `#deps 115, deps mtime ... (VALID)`，
  依赖清单**明确含** `program_impl.h`（以及 `context.h`/`kv_store.h`/`host_kv_store.h`/`draft_context.h`/`disk_kv_store.h`）。
- 结论：**头依赖被完整记录** ⇒ "改头必须全量重编"的纪律可解除，增量编译可信（迭代从 ~1.5h → 分钟级）。
- 遗留：10-11"三次二分全崩"的真因待另证；**新纪律**：任何把源码"拷进树"的操作必须确认 mtime 已更新
  （拷贝保留旧 mtime 会让 ninja 认为未变 —— 这是最可能的真凶）。
- 佐证：VSLANG=1033 实测未改变 cl 输出语言（本段日志 29,857 行中文 / 0 行英文），本条与依赖追踪无关。

### 2.2 v2.1 的深度机制（读 `patches/ledger46_v2.1_multibatch.patch`）

- `PendingDemote` 单槽 → `PendingDemoteRing`（N 槽环形队列）；`retire_pending_demote(...,bool wait)`；
  depth≥2 时 retire 走**非阻塞**（`context_completion_.ready()`，依赖同流 FIFO）；depth=1 = v2 语义逐字保留。
- 深度由 `NINFER_ASYNC_DEMOTE_DEPTH` 决定 ⇒ **A/B 无需重编**。

## 3. 现场事实（2026-10-12 08:1x，G/depth=2 首轮实测）

- **测试负载形态**：确定性填充 220 KB ⇒ `span_abs=[3,54796)` = **prompt 54,796 token**（远大于 ring 窗口 16K、小于池 65,536）。
- **depth=2 表现**：prefill 在 76.9-307.6 tok/s 区间、稳定段 **153 tok/s**；`host 29-60%` 持续；
  日志刷 `[ring] budgets ... (pool 1024)` 与 `[ninfer] ring retrieve: preferred=128 restored=128` 每 chunk 一次。
  ⇒ **"序列一大就发作"的 demote/retrieve 风暴在 prefill 阶段即出现**（生产上同机 prefill 曾达 1.2-2.15k tok/s，
  那是在 ~10K 小序列下）。
- **一次静默死亡（待受控复现）**：08:13:52 最后一行后进程消失，**无任何错误行、无 WER 转储**；
  时间点紧随"杀掉测试客户端（socket 中途断开）"数秒 ⇒ 疑点：**客户端中途断开导致引擎静默退出**。
  若成立，则用户"跑几轮以后崩溃"可能有一条与 67K 超池无关的独立通道。
  → 受控复现计划：E1 完成后，故意在生成中途杀客户端，观察引擎是否消失（做两次取一致）。

## 3.1 测试台自身的三个坑（已修，记以防再犯）

1. **进程名跟随 exe 文件名** ✗：把版本 exe 直接以 `G_clean_93285948.exe` 之名运行 ⇒ 进程名变成 `G_clean_93285948`，
   而 `Get-Process ninfer-serve` 看不见它 ⇒ "实例像死了"（实际活着、占着 15.7 GB 显存、还在 8094 上听），
   `stop` 只杀掉了 tee ⇒ 引擎日志在 tee 死后冻结 ⇒ 被误读成"静默死亡"。
   → **修正**：控制台把版本 exe 复制到 `engine\test-run\ninfer-serve.exe` 再运行（进程名恒为 `infer-serve`）。
2. **端口 LISTEN 不等于实例就绪** ✗：旧实例的 socket 会让"监听=1"成立 ⇒ 误判新实例已起。
   → **修正**：就绪判据 = 读日志出现 `listening on http`（失败则 `FATAL`/`serve_tee end`）。
3. **日志被 tee 独占** ✗：直接读必抛"文件被占用"。
   → **修正**：一律先 `Copy-Item` 快照再读（控制台、测试台、人工排查都照此）。

另加一道 **显存闸门**：启动前查 `nvidia-smi`，used > ~2.5 GB 即拒绝启动（旧实例未释放会导致
`FATAL requested Engine runtime reservation requires ... 0 bytes available`）。
