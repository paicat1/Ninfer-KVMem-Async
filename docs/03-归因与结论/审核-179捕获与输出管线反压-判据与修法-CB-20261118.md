## 〇、摘要（四句）

1. **§240 的「179 捕获」有一个能同时解释三条观测的候选**：引擎被自己的日志写路径反压卡住——`host 0.0%` 纯阻塞、`179 = 1/5.59 ms` 定量吻合、态依赖（日志文件随实例累积变慢）。
2. **定量链条**：`serve_tee.py` L116 每 128 行 gzip 关/开 + L273 明文 `buffering=0` 逐行 syscall + L300-306 控制台逐行 flush；叠加引擎**按步刷屏**（`[ninfer] ensure profile` 18,112 行 + `[ring] budgets` 9,056 行，占 28,049 行的 **96.9%**，注释自写 98.6% 待对齐）⇒ 每行写路径 1→5-6 ms。
3. **判决未闭合**：定量吻合是强相容证据，不是直接证明。**两个零成本前置**（`.gz` 行率反推、QuickEdit 排除）→ 再上 **T3**（3 分钟）。
4. **修复分两档**：A 档（有界队列 + 丢显示，零 trade-off，可定稿）→ B 档（批量 deflate，**仅在 T6 确认 gzip 是主因后**启用，丢失上限不变）。

## 一、机制：反压链的四个环节

| # | 环节 | 位置 | 事实 |
|---|---|---|---|
| ① | 引擎按步同步写 stderr | `context.cpp` L2731-2737（`ensure_profile_emit`，每次 `ensure_ring_room` 一行）；`[ring] budgets`（:2481）**每次映射一行**、`mask hidden`（:2136）常态每步一行、`demote-other short`（:1925）常态每轮一行 | 三类**均无开关**（`serve_tee.py` L87-94 注释 2026-10-10 取证自证） |
| ② | 管道零缓冲 | `serve_tee.py` L294 `Popen(..., bufsize=0)` | 反压**零延迟**传导到引擎 `write(2)` |
| ③ | tee 单线程三步同步 | `serve_tee.py` L319-341：`readline()` → `emit()`（控制台写 + flush）→ `log.write()`（明文无缓冲）/ `sampler.feed()`（gzip） | 无队列、无独立写线程 |
| ④ | gzip 每 128 行轮转 | `serve_tee.py` L116 `GZ_ROTATE_EVERY = 128`；L273 `open(logfile, "ab", buffering=0)` | 每次 = deflate 收尾 + close + reopen + NTFS 元数据（+ 杀软扫描） |

**定量检验**：

```
1 / 179 tok/s = 5.59 ms / token
若每 decode step 触发一行日志，而每行写路径成本 ≈ 5.6 ms ⇒ 恰好 179 tok/s
```

**这不是「节流率」，是「每 token 一行日志 × 每行 5.6 ms」的倒数。** 空转窗 `host 0.0% (0 us)` = 引擎阻塞在 `write(2)`，tee 正在做 console/gzip 的活——两侧都不在算。

**态依赖的具体机制**：日志文件随实例累积（A4 接在 A3 之后）⇒ 每次 reopen/元数据/杀软扫描更慢 ⇒ 每行成本从 ~1 ms 漂到 5–6 ms。**「首个实例快」不是巧合，是文件还小。**

## 二、必须先做的两个零成本前置（都在 T3 之前）

### 2.1 `.gz` 行率反推（比 T3 更硬，且不需要新实验）

```
取捕获窗内的 .gz → 窗内行数 ÷ 窗时长 = tee 实际行率
```

| 结果 | 判定 |
|---|---|
| ≈ 179 行/秒（与 tok/s 同量级） | **tee 吞吐封顶直接实锤**，H1 成立 |
| 远高于 179 行/秒 | **H1 降级**——tee 不是瓶颈，转 H2/H3 |

**为什么它比 T3 硬**：单变量、零改动、用的是已经存在的证据；T3 反而混了三个变量（见 3.1）。

### 2.2 QuickEdit 选区排除（T1 基线的有效性保证）

Windows 控制台一旦进入**选区/暂停**模式，所有写入阻塞，直到选区取消——**与「0% CPU + 整窗空转」完全同形**。

**⇒ 跑矩阵前必须**：关闭 QuickEdit + 确认窗口未处于选区、未点选。否则 T1 的「慢」可能一半来自这里，整晚白跑。

## 三、判决矩阵（每格 3 分钟冷填充）

| 格 | 变量 | 做法 | 判据 |
|---|---|---|---|
| **T3** | tee 全链 | 引擎直连：`... > logs\t3.log 2>&1`（不经 tee） | **快 ≥3× 且 179 消失 ⇒ H1 实锤** |
| **T4** | 控制台 flush | tee 正常，`1>NUL` | 快 ⇒ **控制台渲染管线是主因** |
| **T6** | gzip 轮转 | `set SERVE_TEE_LOG_MODE=full` | **单向判据**：快 ⇒ 轮转是主犯；**慢 ⇒ 不能排除**（见 3.1） |
| **T5** | 插桩量 | `set NINFER_DEMOTE_PROFILE=0`（其余同 T1） | 快 ⇒ 插桩为主；**注意 `[ring] budgets` 9,056 行不受该开关控制**，必有残量 |
| **T7** | 双静音（条件触发） | NUL + `LOG_MODE=full` | 仅当 T4/T6「都改善但不彻底」时跑；T7 仍慢 ⇒ 存在第三因子 |

### 3.1 两处必须标注的变量混淆

1. **T6 不是单变量格**：`LOG_MODE=full` 同时令 `gz=None`（轮转消失）**且**明文从「关键行 0.5%」变「全量 100%」（`buffering=0` ⇒ 逐行 syscall，行数约 ×200）。**判据只能单向使用**，否则「T6 慢」会被误读成「轮转无嫌疑」。
2. **T3 亦非单变量**：直连同时去掉「tee 进程」「控制台」「gzip」三者。**它只回答「管线是否有罪」，不负责归因**——归因靠 T4/T6。

## 四、修法：两档（A 可定稿，B 待 T6）

### A 档（必做，零 trade-off）

```
tee 改：读线程只做 readline → 入有界队列（满则丢「窗口显示」，绝不丢 .gz）
        独立写线程：消费队列 → 控制台（可丢）→ 明文/gzip（不可丢）
效果：引擎永不因日志阻塞（把「阻塞」变「积压」）
```

### B 档（条件触发：T6 证明 gzip 是主因）

```
写线程内攒 128 行 → 一次 deflate + 一次 write → 仍每 128 行一个 gzip 成员
效果：丢失上限维持 128 行不变，同时消掉逐行小写开销
```

**为什么需要 B**：**队列只解耦，不提速**。写侧吞吐不变时，队列只涨不消 ⇒ 要么内存涨，要么被迫丢 `.gz`（违反「全量不丢」）。所以：

| T6 结果 | 修法 |
|---|---|
| T6 快（gzip 主因） | A + B |
| T6 慢、T4 快（控制台主因） | **A 足够** |
| T4/T6 都只部分改善 | A + B，并核查第三因子 |

### 明确不做（避免用 trade-off 换吞吐）

- ❌ `GZ_ROTATE_EVERY` 128 → 4096：128 是**丢失上限控制**（L116 注释自证「强杀最多丢 N 行」，属 §220 的 EOFError 修复），放大 32 倍是 trade-off 不是收益
- ❌ `buffering=0` → 大缓冲：同理（保证关键行不丢）
- ⚠ 仅当 A 方案被否决时才考虑上面两条，并显式接受丢失上限放大

### 附带项（需重编，视效果决定）

`context.cpp` L2731-2737 `ensure_profile_emit` 改为**窗口聚合**（照抄旁边 `ring_profile_window_end` 的「256 次一行」写法）；`[ring] budgets` 行需一并处理（它不受 `DEMOTE_PROFILE` 门控）。
