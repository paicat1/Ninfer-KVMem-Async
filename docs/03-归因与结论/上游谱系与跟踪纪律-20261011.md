## 四、跟踪方式

1. **每次大问题排查前**：先 `git fetch` Bonsai 线 + 翻 `docs/06-Bug手册.md` 新条目——**先看上游有没有解法，再闷头自己撞墙**；
2. **定期（每周）**：`HEAD..origin/main` 计数 + Bug 手册 diff 摘要；
3. **指代纪律**：禁用"官方"统称；说"Bonsai 线"、"兄弟件 RC2"、"NInfer 原始仓"、"tancau 环线"、"qw3 策略层"；
4. **上游解法入库路径**：Bonsai 线分析 → **与前作 P 系列对照去重合并**（同一修法两条线的各自落地）→ 对照本线实测 → 评估移植（env 级 > patch 级 > merge 级，按风险递增）→ 实测验证 → 构建史记档；
5. **本档维护**：谱系变化（新仓/新分支/新下游）时更新本文件 + 修订记录。
6. **上游跟进后必跑逐字门（2026-10-20 审核 M2）**：每次 cherry-pick / rebase / 跟进上游后，跑一次 `python scripts/verbatim_gate.py`（逐字一致门，8 提示），通过再合入——上游与本地 19 补丁同文件区变更时，这是唯一能兜住"静默语义漂移"的机器门。

### 6.4 关键 issue 动态与精读结论

**#101 · prefix reuse collapse（open；已精读全文+评论）**——
- **问题**：agent harness 每轮重写尾部消息（如 `Tool-call turn N of 100.`）→ role 翻转 → 最长公共前缀边界移动 → 最近 checkpoint 在边界**后一行**（off-by-one）→ selector 全清 → **每轮全量重算且自我锁定**；
- **实证**（同版本 A/B，`5d1ac0a` 编译两次）：105 尾改轮 prefill **1,349.4s → 139.8s（−89.6%）**、new rows 1,134,982 → 47,828、TTFT p50 13,156 → 1,347 ms；追加型轮零变化（对照）；反转顺序复现；代价 = 额外 checkpoint host 状态（peak 628→785 MB）；
- **修法**：`run_prefill_multimodal()` 单段 decode 拆两段，在已知相等边界留 checkpoint（数行 patch）；
- **对本线**：**代码修法不适用**（llama.cpp backend 血统，机制不同）；**可借鉴的是方法论**——①"每轮尾改 nudge"是**跨 harness 普遍模式**（作者称多个独立 harness 复现）；②回归测试设计（trace 判据：`no_recurrent_checkpoint` / `oldest_checkpoint − lcp = +1` / `prefix_hit_rows`）可仿制；③**家庭自查项**：本线 DSH 会话 cache% 是否出现"特定轮型骤降"（本线实测命中 97-100%，预计正常——以日志验证为准）；
- **精读附注**：其"同版本编译两次 A/B + 反转顺序"的科学方法与本线证据文化同构，可作探针设计范例。

**#113 · 工具调用偶尔失败（open，4 评论）**——
- 社区报告（10-08）：DSH 会话工具调用出错导致中断（畸形 `<tool_call>`）；workbuddy、pi 框架（0.18RC1）同现；**低占用时（20%+）即偶发**；
- 社区猜测："**kv 缓存中断丢失（里面有工具调用的定义）**"；
- **维护者 wangleye 回复（10-09）**："会把上游的一些工具修复的补丁在下一个版本加入"→ **RC3 工具调用约束即兑现**；

### 6.5 本线独有成果核查（"上游有没有想到异步页流水"）

**结论：在已审阅的全部上游材料范围内（Bonsai 线 23 提交 + docs/13/14 + tancau 全仓 + RC2/RC3 说明 + 主要 issues + 始祖/兄弟线近期提交），未发现"异步页流水"（页搬运与 decode 解耦流水）的同款实现。**

- Bonsai 线：B34 页漂移立案 + D-01 sink 缓解 + P-01..P-08 修法清单——**无搬运时序层改动**；
- tancau：最近的思想邻居 = **Phase 3（worker 隔离/分层 restore）——park 未实现**；其已完成的自噬修复（跳过 mid-ensure restore）是"减少无效页操作"（治 churn），非"搬运-解码并行"；其收官判定恰为 **"decode at wall"**（接受解码侧的物理墙）；
- kvmem-llama.cpp：RC3 分层（RAM/SSD = 存储**空间**维度）+ LRFU（淘汰策略）+ 明确声明"本次没有加入 decode 期间的持续 attention score 累积"——**无解耦流水机制**；
- iamwavecut / Neroued：structured-output / 约束解码 / 内核性能——非 KV 搬运域。

**诚实边界**：机制思想（异步 I/O / 流水线 / 脏页后台回写）在 OS 领域不新；本线贡献 = **在 NInfer/KVMem 引擎内的具体落地（PendingDemote + transfer stream + 次步收割 + 正确性契约）+ 全量实测（20-40 倍、E4 验证）**——就本生态而言，目前是**唯一实现 + 唯一实测数据**（回馈资本）。

#### 6.7.1 净增量：论文**正文机制细节**（10-15 调研只有"论文存在+作者+双后端"，无正文）

| 机制 | 内容 | 对本线 |
|---|---|---|
| **Raw K + re-RoPE** | GPU 外保留**去 RoPE 的 raw K**；入块在新位置**重新施加 RoPE**；常驻块用 **bounded delta re-RoPE**（累计达阈值从 raw K 重建） | **`#53` 的物理解释候选**：页位置变 → RoPE 帧不匹配 → **K 值本身变** → 输出必分叉（比"求和序"更直接） |

| **Step-level 调度** | KL：同步内 **0.070 bit** vs 跨 step **2.59 bit（37.3×）**；每 step 更新工作集，decode 期固定 | **v1 PageHeat 衰减应按 step 边界重置**，而非固定步数 |

#### 6.7.7 研判与参考意见（CB 判断，供用户裁决）

**① 定位判断：分层表述（既不自吹，也不全盘否定）**

**三层事实（项目既有口径，README L7/L121 + 构建史 §165 第 6 条）**：

| 层 | 事实 | 出处 |
|---|---|---|
| **通用技术层** | 异步 I/O、脏页后台回写、预读——OS 领域数十年的通用技术，**不是本线发明** | README L121 明确自比"异步 I/O" |
| **KVMem 生态层** | KVMem 环的搬运层原本**同步**（demote 阻塞 decode）；**本线在其上引入异步页流水（v2 搬运层）——"在 KVMem 基础上向前发展"** | README L7"本仓的核心增量是异步页流水"；挂账 42 全链（取消检查点前移 → 批量 demote → 异步 demote） |
| **本线贡献层** | ①具体落地（`PendingDemoteRing` + transfer stream + 次步收割 + 正确性契约）②剂量学实测（深载 r=0.80、最深段 ≈2×、跨平台 +32.4%、depth 1–4 曲线） | §167 / §176 / §178 |

**与论文的关系：同族思想、不同形态、独立收敛**——

| 论文 | 本线 | 关系 |
|---|---|---|
| Proactive stage-out（**prefill chunk 级**，1 批在飞） | 异步 demote ring（**decode 期多批**，depth 1–4） | 同族，形态不同（负载形态逼出来的） |
| Retrieval-aware hierarchical reuse（已实现） | 估计器（设计阶段） | **论文先行**，本线可借设计不借代码 |
| Packed & pipelined rematerialization（三阶段） | batch publish（patch 23） | 论文更完整（含 gather/散射） |

**正确表述（两层都要说）**：

- ✅ **"异步页流水是本线对 KVMem 同步搬运层的增量改造，并给出全量 A/B 实测"**——这是本仓的核心增量（README 口径）
- ✅ "论文的 proactive stage-out 与本线是同期独立收敛的同族解，形态不同（他们 prefill 级单批，我们 decode 级多批）"
- ❌ "异步技术是本线发明的"——通用技术，OS 领域几十年
- ❌ "本线没有原创"——落地实现 + 剂量学 + decode 级多批 ring 是实打实的

**② 我们真正还独有的是三条（且都不是算法原创）**

| 独有 | 性质 | 能否守住 |
|---|---|---|
| **decode 期多批 in-flight ring**（depth 1–4） | 负载形态逼出来的（单请求长 decode） | 论文明确 decode 期零搬运 ⇒ 他们不会做 |
| **MTP 草稿头 + 自转量化** | 工程优化（IQ4NL 省 212 MB、接受率 93%） | 论文用 NVFP4-MTP，未做草稿头精度优化 |
| **16 GB 桌面 + 中文 agent 产品形态** | 场景/工程 | 论文是 24 GB 笔记本 + 96 GB 服务器 |

**③ 最该吸收的三条（按优先级）**

| 优先级 | 项 | 理由 | 成本 |
|---|---|---|---|
| **P0** | **Raw K + re-RoPE** | 若我们 restore 是"原字节搬回"，页位置变化时 **K 的 RoPE 帧可能已失配** ⇒ 不仅解释 `#53`，还可能解释**超池召回后质量下降** | 读码（0）→ 若缺则**引擎改动**（大） |
| **P1** | **step-level 衰减** | v1 `PageHeat` 的衰减窗口按 step 边界重置（KL 37.3× 实测依据），零成本校准 | 设计修正（0） |
| **P2** | **频率感知淘汰的实现细节** | 我们的 v1/v2 还在设计，论文已实现 ⇒ **直接读他们的算法，不要重新发明** | 读码（0） |

**④ 不建议跟的三条（场景不匹配）**

| 不跟 | 理由 |
|---|---|
| **NVMe 三层** | 我们的工作区 229K，host 环 16 GiB 已够；加 NVMe = I/O 复杂度 + 慢态风险 |
| **Mean-K 32-token 块索引** | 我们页级已够；改块粒度 = 改页管理决策 = **改输出 sha**（`#53` 类风险） |
| **10M 工作区** | 我们的负载（DSH 桌面 agent）无此需求；追规模会偏离 16 GB 桌面定位 |

**⑤ 发布口径（三条，按"分层"而非"禁令"）**

1. **别说**"比 KVMem 快 6 倍"（388 vs 50）——口径错配（理想值比生产值）
2. **说清分层**：异步 I/O 是通用技术 → 本线在 **KVMem 同步搬运层**上做**异步页流水改造**（这是增量，README 口径）→ 论文的 proactive stage-out 是同族不同形态（他们 prefill 级单批，我们 decode 级多批）
3. **可以说**："在 16 GB 桌面卡上，异步页流水 + MTP 的组合实测 X tok/s（超池 N×），并给出全量 A/B 与方法论"——这是我们真正有数据的地方

**⑥ 战略判断**

- **算法原创窗口已关闭**（论文已发表并开源）；
- **工程与场景窗口仍开**：16 GB 桌面、投机解码组合、中文 agent 产品化、以及"慢态/死亡谷"这类**别人没遇到的工程问题**；
- **回馈路径存在**：若 decode 级 ring 在多批 in-flight 上确有独有价值（depth 收益曲线），可作为 **PR/issue 反馈给 kvmem**——这比"对标"更有价值，也符合本项目"回馈上游"的既有姿态。
