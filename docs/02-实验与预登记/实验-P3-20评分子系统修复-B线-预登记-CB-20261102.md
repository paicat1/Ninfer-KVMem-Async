## 二 机制精化：词法失效的真面目是 `recall@budget` 被挤占

原表述"词法选高频项"不准确。实际机制（TELE 精化，构建史 L606 / L1916 旁证）：

```
kvmem_score: SELECT 的 budget_blocks = 512 / kept = 512 / skip ≈ 560  ← 硬顶
排名误差的表现不是"选错一个"，而是"答案页被挤出 512 预算"
filler-300 = 多个含 "300" 的 filler 块把含真答案的块挤出预算 ⇒ 静默错
```

⇒ **角色 A（检索正确性）的正确指标 = `recall@budget`**（答案承载页在预算内的召回率）。标准检索指标，可测、可设门槛。

**代码场景是 `recall@budget` 的地狱难度**：依赖闭包大而散（定义 / 签名 / 约束 / 调用点分布在几十页），且每轮都在扩大 ⇒ 512 预算被挤爆的概率最高。

## 三 三层拆分（职责单一化）

| 层 | 职责 | 现状 | 目标 |
|---|---|---|---|
| **信号层** | 提供"哪些页该选"的依据 | 内容评分（**精度耦合**：低精度 K 的均值打分失真） | ① bf16 激活算分表（prefill 时免费、精度免疫）② attention-heat 累计（P3-14 PageHeat，精度无关） |
| **政策层** | 决定"花多少预算选" | 默认深挖到底（last 2323/2365） | 深度预算 + 摊销（按 turn 而非每步）+ 迟滞防 thrashing |
| **守卫层** | 保证"答案依赖不被漏掉" | 无（靠深挖兜底） | **两阶段**：常驻廉价候选（词法 / heat / 近窗，硬预算）+ **事件触发的定向深检索** |

**关键判据点（读码第一问）**：`kvmem_score` 的分数表是**前量化**还是**后量化**计算？

- 若**后量化**（读 KV 页的量化值算）⇒ 精度耦合是结构性的，换 bf16 激活算表可解；
- 若**前量化**（prefill 时用激活算好存表）⇒ 精度耦合不在分数表，而在"读回/比较"环节，修复点不同。

（施工方案 L33 曾写"打分不读 KV 页内容：查 ops 预计算分数表" ⇒ 倾向后者，但需代码确认。）

## 四 档位 × 工作负载配对（回答"判死 vs 不判死"）

| 工作负载 | 档位 | 选择策略 | 理由 | **验证依赖** |
|---|---|---|---|---|
| **闲聊 / 摘要 / 长文生成** | **低精度（rk2v4-e8）** | 词法 + 深度预算 | 正确性需求低 ⇒ 池倍增收益全额兑现 | **行动 #1**（SCORE=0 必须先证不静默错） |
| **推理 / 长 thinking** | 中精度 | 事件触发深检索 | 早期约束必须召回，但不需要逐字 |
| **代码 / 工具调用** | **高精度（rk8v4+）** | 守卫常开 + 依赖闭包预取 | 标识符 / 签名 / 约束必须逐字；**高精度 KV 本身是选页信号的降噪器** | **行动 #2/#3**（若 rk8v4 也深挖 / 也失真 ⇒ **本行需重写**） |

⇒ **低精度档不是被判死，是被重新安置到 trade-off 有利的负载**。"档位 × 负载"配对，比"判死 / 不判死"高一个维度。

**代价（必须写明）**：代码任务用 rk8v4 ⇒ 池 **−11%（58,368 vs 65,536，暂定值——X21 池上限重扫后更新）** ⇒ 大代码库的上下文上限降低。这一条是真实 trade-off，不是免费。

## 五 三时间粒度配置架构（自动化 vs 手动）

| 配置项 | 引擎能自测？ | 正确形态 | 时间粒度 |
|---|---|---|---|
| **深度保险丝**（`preferred last` 超阈值 → 降深度预算 / 切词法） | **能**（`last` 在 profile 每步可见） | **全自动**，`env` 未显式表态时才生效（手动 override 优先） | **每步** |
| **任务类型先验**（代码 / 推理 / 闲聊） | **不能**（引擎只见 token 流，猜内容是脆弱设计） | **客户端声明**（serve API 可选字段 `correctness-first` / `efficiency-first`；启动器预设作缺省） | **每请求 / 每会话** |
| **档位（KvDtype）** | **不能**（改档 = 换容器 / 重启） | **启动时手动定**，按当天工作负载 | **每次启动** |
| **召回深度上限**（`preferred last` 的硬顶，**独立于评分预算**） | **能**（`last` 每步可见） | **全自动**：保险丝压它；**启动时可给初值**（按 §四 负载配对） | **每步（保险丝） / 每次启动（初值）** |

**优先级与默认值（原表缺这段，补齐）**：

| 层级 | 未设置时的默认 | 与上层冲突时 |
|---|---|---|
| `env` 显式值（`NINFER_TERNARY_KVMEM_SCORE` 等） | — | **最高**，覆盖一切（含保险丝） |
| 请求级声明（`correctness-first` / `efficiency-first`） | **efficiency-first**（保守：不默认深挖） | 高于档位默认，低于 `env` |
| 档位默认（按 §四 配对表） | 见 §四 | 最低 |

⇒ **`env` 是总闸**：显式 `SCORE=0` 就全局关，保险丝不得覆盖（否则手动 override 失效，违反本节设计原则）。

**设计原则**：**可观测的交给引擎自动（深度 / 命中率 / 预算占用），不可观测的交给客户端声明（任务性质 / 正确性要求）。**

**⚠ 深挖行为本身也在修复范围内（LUMMY 疑点 1，成立）**：§199⑥ 显示 SCORE=1 时 `preferred` 深达 2323、SCORE=0 词法仅 ≈1149——
**"深挖"不只是"评分开销"，它同时改变了页集合**（更多 host 页被拉进候选）。因此：

- 只调"评分的时间预算"（摊销 / 缓存）**不足以**消除伤害——深挖导致的页集合差异会原样保留；
- 必须同时可调**召回深度上限**（上表新增行）——它才是"页集合"的闸门；
- ⇒ 政策层的完整形态 = **深度预算 + 评分摊销 + 迟滞**（三者缺一不可，P3-14 原设计即如此）。

两个反模式：
- 让引擎猜任务类型 ⇒ 脆弱（内容分类误判会静默改变策略）；
- 让用户盯深度 ⇒ 人不可扩展（§一 五层失守的第五层）。

## 六 判据（两分支 + 质量门 + 成本上界）

### 6.1 主判据：两通道贡献拆分

```
甲通道（组成质量 → 接受率崩塌）：SCORE×OFF 已给一半答案
乙通道（forward 内 scoring 开销 / 读回等待 × async 竞争 → 每步延迟）

判据：两通道各自对 2.17× 的贡献占比
  甲 ≥ 60% ⇒ 优先修信号层（换 bf16 算表 / heat）
  乙 ≥ 60% ⇒ 优先修政策层（摊销 / 深度预算）
  各 40–60% ⇒ 两层并行，先做成本低的（政策层）
```

**一阶分解公式（TELE 补，先登记防事后发明）**

MTP 下 decode 速度 ∝ 接受率（一阶成立），故"接受率下降造成的那部分速度损失"= 甲通道：

```
甲占比 = ( OFF速度 − OFF速度 × ON接受率/OFF接受率 ) / ( OFF速度 − ON速度 )
乙占比 = 1 − 甲
```

**用 §198/§199 现有三格数据直接算（已验算）**：

| 格 | OFF 速度 / 接受率 | ON 速度 / 接受率 | **甲（组成质量）** | **乙（每步延迟）** |
|---|---|---|---|---|
| r1 · SCORE=1 | 313.6 / 91.3% | 144.4 / 72.3% | **38.6%** | **61.4%** |
| r2 · SCORE=1 | 312.5 / 97.5% | 273.0 / 94.1% | **27.6%** | **72.4%** |
| r1 · SCORE=0 | 339.3 / 93.5% | 296.9 / 89.2% | **36.8%** | **63.2%** |

⇒ **三格全部乙 ≥ 60%** ⇒ 按本节判据，**政策层优先（摊销 / 深度预算），保险丝（行动 #4）是第一块修复，不是临时措施**；信号层修复排第二。

**⚠ 边界**：线性模型是一阶近似；**权威测量以行动 #2/#3 的 scoring 段打点为准**。本表的作用是"免费预判 + 防事后发明公式"。

### 6.2 质量门：`recall@budget` 门槛

```
在"代码类探针"（含标识符 / 签名 / 约束引用）上：
  recall@budget(SCORE=1) vs recall@budget(词法)
  要求：SCORE=1 ≥ 词法 + 10pp，否则评分的正确性价值不成立
```

**绝对门（TELE 补，缺它则代码负载安全性无判据）**

```
代码类探针 recall@budget(SCORE=1) ≥ 95%（暂定）
未达 ⇒ 该负载在此系统上不安全，与"评分值不值"无关
```

**一石二鸟**：这条绝对门同时是 **§四 配对表第 3 行（代码 ⇒ 高精度）的实证实验**——该行目前是断言，不是证据。

**当前状态**：`recall@budget` **无度量**（判据缺口，行动 #3 先确认有无；无则补建）。

### 6.3 成本上界：深度预算

```
preferred last 深度 ≤ 1500（暂定：词法水平 ≈1150 + 30% 余量）
超限 ⇒ 触发保险丝（降深度预算），不直接切 SCORE=0（保正确性角色）
```

**⚠ 阈值必须等行动 #2 标定，不能直接上生产**：

| 若 rk8v4 的 `last` | 后果 |
|---|---|
| ≈1150（与词法同量级） | 1500 合理，无需调整 |
| **≈1800+（也深挖）** | **1500 会误触发健康档** ⇒ 阈值上调或改"相对阈值"（本档基线 ×1.3） |
| 无数据 | **不得上线**——拍脑袋阈值会把健康的 rk8v4 挡掉 |

⇒ 保险丝的**实现**可先做（#4），**阈值**必须等 #2 数据后填。

### 6.4 保险丝的两个动作必须分开（TELE）

| 动作 | 牺牲 | 何时用 |
|---|---|---|
| **切 SCORE=0** | 牺牲角色 A（正确性） | 仅在"效率优先"负载 + 正确性验证通过后 |
| **压深度预算** | 只牺牲成本，不牺牲召回上限 | **默认动作** |

### 6.5 总验收（修完什么算成功）

分项判据（6.1–6.4）都有，但缺"整体是否达标"的判据。三条同时满足才算闭环：

| # | 验收项 | 门槛 | 对应负载 |
|---|---|---|---|
| **V1** | 代码类探针 `recall@budget` | **≥ 95%**（SCORE=1） | 代码 / 工具调用 |
| **V2** | 闲聊/长文 decode（SCORE=0 vs 词法基线） | **≥ 332**（词法基线 339.3 的 98%） | 长文生成 |
| **V3** | 代码任务 decode（高精度 + 守卫） | **≥ 349**（rk8v4 基线 388 的 90%） | 代码 / 工具调用 |

**任一不达 ⇒ 该负载不上生产**（不是整体回滚，是**按负载分档放行**）。

## 八 边界与风险（四条，落盘前必须写明）
