# 方案：深池重载归因测试（预登记 · **判据先写死**）

- 立件：桌面版 CodeBuddy（CB）· 2026-10-17 11:2x · 用户令："继续抓紧深池机会做归因测试"
- 目标：判别 **H1（请求形态驱动）** vs **H2（机器态驱动）** —— 即"每 token 走 host 阻塞路径"到底由**请求的深超池形态**引起，还是由**机器贴边状态**引起。
- 来源：`docs\归因-29分钟持续谷与下一步预登记-CB-20261017.md` 的 **E-A**。

## 一、当前机会（实测）

| 项 | 值 |
|---|---|
| 池容量 | **65536**（`--kv-capacity`） |
| 逻辑上下文上限 | **262144**（`--max-context`）⇒ **4× 超池**可达 |
| 引擎连续运行 | **>14.6 h**（10-16 20:50 起服，未重启） |
| 当前空闲态 | GPU 1117 MHz / 3% / 29.63 W；**自由显存仅 338 MiB**（贴边） |

⇒ **"深池机会" = 4× 超池 + 贴边状态 + 长连续运行** 三者同时具备。

## 二、测试设计（单变量）

**一发重载请求**，复刻 29 分钟谷的形态：
- **长上下文**：逐步加深至**深超池**（>2× 池，即 >131k token 上下文）；
- **长输出**：`max_tokens ≥ 2000`（**不是**猎人的 200）；
- **不施加外部压力**（不动 memhold/vram_hold）⇒ 只测"请求形态"这一个变量。

## 三、预登记判据（**先写死，后观察**）

| 观测 | 判定 |
|---|---|
| **快**（decode ≥150 tok/s 且 `host` <40%） | ⇒ **证伪 H2** ⇒ 29 分钟谷属**请求形态（H1）** |
| **慢**（decode <30 tok/s 且 `host` ≈100%） | ⇒ **支持 H2** ⇒ **机器态仍在（即便空闲）** |
| 中间态（decode 30–150） | ⇒ 记录为"部分谷"，**不下结论**，等第二批 |

**同时记录**（每条都进台账）：`decode`（探针口径）· `host%` · `power` · `clk` · `util` · `ring retrieve` 行 · 自由显存 · 是否出现 `waiting ≥1`。
