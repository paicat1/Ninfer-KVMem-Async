## 三、P1 发现（必须修正后施工）

### P1-1 编译纪律与挂账 45 教训直接冲突

- 设计稿 §6.3：「编译：build-1208a **增量（只重编改动 TU）**」。
- 但本树已知缺陷（挂账 45，构建史 L1589）：中文 /showIncludes 未被 ninja 识别 → **改头文件后 header consumers 不重编** → 布局混编 → 构造期堆踩踏（0xC0000005/0xC0000374，三次二分全崩）。
- **v2.1 恰好要改头文件 `program_impl.h`（槽结构）**——按「增量只重编改动 TU」执行 = 高概率重现挂账 45 混编崩溃。
- 修复候选（VSLANG=1033）当前状态 = **「待下次增量编译验证」（未验证）**——不能作为施工依据。
- **修正要求**：§6.3 改为 **「全量重编（清 build-1208a 重建）」**（最稳，25-40 分钟可接受）；如坚持增量，必须先单独验证 VSLANG=1033 修复有效（观察 header consumers 确实重编）——**推荐直接全量**。
- **关联用户令**：「下次再动编译，一定要保持好现在的成果」——编译环节是最大风险点，本修正即该令的直接落实。

## 四、P2 发现（建议修正/补充）

### P2-2 「槽满背压」的收益边界（关注项）

- 死亡谷期每步 demote 需求暴增时：DEPTH=N 只把「每步异步批数」从 1 提到 N，**剩余批仍走同步路径（阻塞）**——收益上限取决于每步实际需求批数（req#61 解剖：谷内页操作 ~300ms/步量级）。
- 建议：P2 验证时**同时记录「同步路径占比/批数分布」**（profile 采样）——若同步占比仍高，下一迭代应转「早期页 pin」（根本解）而非继续加深槽。
- 本项不阻塞施工（P2 数据本就会揭示）。

## 五、P3 发现（表述精确性）

1. **「DEPTH=1 = v2 行为（无缝回退）」不精确**：v2.1 收割统一改为非阻塞 eventQuery——DEPTH=1 是「单槽 + 非阻塞查」（行为近似 v2，且对 decode 步更安全）；**逐位回退 = exe 备份 / `NINFER_ASYNC_DEMOTE=0`**。建议表述区分「安全档」与「逐位回退」。
2. **「transfer_streams」复数**：尾起连续收割（break on 未完成）依赖「批完成序 = 提交序」——同一 stream 内 CUDA 保证 FIFO 完成；若多 stream 则顺序不保证（仅延迟收割，无正确性影响）。建议注明「提交到同一 transfer stream」或说明乱序仅延迟收割。
3. **RAII 逆序析构论述**：真正保证 =「每槽独立同步其 transfer」（数组逆序是充分条件之一）；结论安全，无需改动（备注即可）。
