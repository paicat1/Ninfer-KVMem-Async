## 1. 原作者的工作与进展

### 1.1 核心洞察

大语言模型每生成一个 token，都要"回顾"之前全部 token 的中间状态（KV Cache）。Agent 场景（多轮工具调用、长文件阅读）把上下文推到几十万到上百万 token——按 FP16 计算，100 万 token 的 KV 约 **32 GiB**，而消费卡只有 16 GB 显存。

作者的关键观察：**模型生成每一步，真正"看见"的 KV 只是一小部分**——

```
完整 KV（存放在 Host RAM，可选下沉 SSD）
├── Sink（固定开头窗口，如 12K token）    ← 常驻 GPU
├── Recent（最近窗口，如 1K token）        ← 常驻 GPU
└── 其余部分                              ← 按"检索"命中才换入 GPU
```

### 1.2 开创性技术（原作者实现的首创或系统性实践）

| 技术 | 内容 |
|---|---|
| **KV 虚拟化** | 完整原生 KV（含量化附属数据、MTP KV）存放 Host RAM、可选下沉 SSD；GPU 只保留"当前用得着的" |
| **检索驱动的按需换入** | 不是"全量搬运"，而是按查询相关性挑选历史片段——大大降低搬运量 |
| **历史加权打分（LRFU）与 GQA max** | 用当前 query 的相关性更新历史分数（λ=0.5、top-frac=0.9）；同 KV head 组取最大相关性 |
| **所有权移动而非复制** | 历史在"活动↔闲置"之间**移动同一份记录**；恢复时只读实际选中的内容，不生成全量冷快照、不重新量化 |
| **配额与版本化发布** | Host/SSD 配额（H/D）；写入先取配额、完成后发布；读租约保护；排队取消可撤销 |
| **跨后端契约** | 同一套内存契约同时服务 llama.cpp 与 NInfer 两个引擎（含 166 文件级的 NInfer 深度集成） |
| **64-token 页粒度** | 检索统计块与原生物理页对齐，搬运/选择/统计按同一粒度实现 |

### 1.3 实践与进展（公开成果）

- **论文**：arXiv 2609.04852（KVMem: Virtualizing Million-Token Agent Workspaces on a Consumer GPU）。
- **双后端正式化**：0.18.0 版本同时提供 llama.cpp 与 NInfer 后端源码（NInfer 侧为正式运行包，llama.cpp 侧为 RC1）；Windows RTX 30/40/50（含 sm120a）正式运行包发布。
- **实测成绩（RC3，RTX 5060 Ti 16GB + Qwen3.8-27B GSQ-RCO IQ3_S 模型）**：
  - 日常文本生成 **50.08 tok/s**、代码生成 64.54 tok/s；
  - **长历史工具轮次 53.24 tok/s**（32 轮、输入 261,522 token 的一次完整长历史测试）；
  - 整卡显存峰值约 14.12 GiB。

## 2. 那道留下的墙：同步换页

在原作者实现中（以当时的形态为准），换页是**同步**的：需要搬运时，推理停下来等搬运完成。

```
同步模型：
[推理步]→[等搬运]→[推理步]→[等搬运]→ ……
```

由此形成一个"红线"式的工程约束：**GPU 预算必须覆盖当前需求**，否则每一步都吊在搬运上——所谓"池不要小于工作集"的建议，本质是在**回避换页**，而不是**驾驭换页**。

这是"装得下"与"跑得快"之间的第一道妥协。**我们的探索从这道墙开始。**

## 3. 我们在其基础上的探索与实践

### 3.1 核心改进：异步页流水（让搬运和计算同时发生）

**思想一句话：把"等搬运"变成"搬运与计算重叠"——上游提交搬运后立即返回，继续跑解码，下一步开始前页已就位。**

```
异步页流水：
[推理步]     [推理步]     [推理步]
    └──搬运──┘ └──搬运──┘ └──搬运──   ← 与下一解码步重叠
```

机制四件（以本引擎实现为准）：

| 机制 | 作用 |
|---|---|
| **页（64 token）+ 批（8 页/次）** | 搬运的最小单位与批量，控制单次占用规模 |
| **提交后立即返回** | 解码步不等待搬运完成——"异步"的本质 |
| **在飞页计数** | "已离开设备、尚未发布主机"的中间态页被如实记账——正确性关键 |
| **publish / drop 账本** | 搬完并通过校验才"发布"新副本；确定无用才"丢弃"——数据不丢失、不重复 |

**搬运是怎么被"藏"起来的（机制解剖）**：

| 角色 | 是谁 | 职责 |
|---|---|---|
| 主厨 | GPU **计算单元（SM）** | 跑解码的整张计算图——每个解码步约 **27-32 ms** |
| 专职跑腿 | GPU **拷贝引擎（DMA）** | 在显存 ↔ 内存之间搬页——每批 8 页约 **1-3 ms** |
| 经理 | Host 调度线程 | 决定"搬哪些页"（空闲裁决/水位）、提交搬运任务、记账——微秒级，**不亲手搬** |

- **藏在哪**：藏在**解码步的图执行时间之内**——当 GPU 在跑当前步那 27-32 ms 时，DMA 引擎同时把下一页（或上一批）搬完（1-3 ms）；
- **为什么藏得住**：① 计算与拷贝走**不同的硬件单元**（SM vs 拷贝引擎），天然并行；② 搬运量小（1-3 ms ≪ 27-32 ms）；
- **为什么安全**：正在被当前步使用的页**不搬**——"搬哪些页"由空闲裁决选出，在飞页计数 + publish/drop 账本保证"不丢失、不重复"。

一句话比喻：**不是让主厨停下活去仓库取菜，而是后厨一直开火、跑腿小哥专职在仓库和灶台之间跑**——两双不同的手，同时干活。

**经理怎么决定"搬哪些页"（三道过滤器）**：

| 过滤器 | 规则 | 性质 |
|---|---|---|
| ① 保护范围（硬规则） | sink（固定开头）+ recent 窗口 + 当前步正在使用的页——**永不搬** | 零误判区 |
| ② 水位触发（必要性） | 只在"空闲页 < 阈值"时才启动搬出——**不缺就不搬** | 宁缺勿搬 |
| ③ 相关性打分（选择谁） | 召回侧按当前 query 的相关性给历史打分，**得分高的优先装回**（历史以 32K 步长锚点组织） | 唯一的"预判"，失误来源 |

- **搬出去**（demote）= 被动决策：缺空间才发生，从"保护范围之外最冷的一端"选页；
- **搬回来**（restore）= 按需决策：sink + recent + 检索命中集的并集，多一个不搬。

**命中失误的双保险**（预判失误无法归零）：
1. **让决策更准**：保护范围把最易误判区排除出预判；相关性打分把最可能要用的排在前面；
2. **让失误更便宜**：误搬的代价 = 一次 1-3 ms 的后台搬运（被步窗吸收）+ 批量摊薄 + **A2 无损兜底**（最坏是"多搬两次"，永远不会"输出出错"）。

**实测效果**：
- 正常期单批搬运 **1-3 ms**，解码步窗 **27-32 ms** —— **搬运被完全隐藏在步窗内**；
- **74.4K token 深度超池（池约 65K）时，decode 仍达 114.4 tok/s**；
- **同日对照实验（2026-10-16，关闭异步（OFF）vs 保留异步（ON）的同条件对照）**：在深轮重载场景（多轮递进 + 部分缓存复用 + 长输出，2.3–3.5× 超池），同步臂比异步臂**慢约 20%**（中位 decode 188 vs 235 tok/s）；最深段（3.5× 超池）差距 **约 2 倍**（235.6 vs 119.4）；伴随一个数量级的停机（ring STALL 33 → 2 次）。而浅载/单发场景下两臂打平（r=1.13）——**含义：异步的价值随工作集深度上升而显现，它正是为深载场景设计的**（口径：n=3/臂、单机、健康期；异步前"多轮必死"的更强主张未复现——观测到的是"可用但慢"）。**另注**：本次对照中同步臂未现死亡谷——可能因前序多轮修复已碰巧缓解了该状态（未在对照中复现，留待后续验证）。**另注**：本次对照中同步臂未现死亡谷——可能因前序多轮修复已碰巧缓解了该状态（未在对照中复现，留待后续验证）。

#### 数学基础：异步页流水的收益是一条不等式（2026-10-19 定稿）

异步页流水的收益不是经验观察，而是一条由**守恒律**保证的不等式。推导四步：

**第一步：守恒律（搬运义务的来源与规模）。** 工作集 > 池容量时，每步解码新增的页无处安放 ⇒ 必须换出等量的页（新增 = 换出）。**搬运义务的总量由工作集/池比与序列增速决定，与开关无关**——关掉异步，义务不消失，只是换一个地方支付。

**第二步：支付位置不等式。** 同一笔义务，两种支付位置：

```
同步：T = T_compute + T_move      （义务 100% 落在关键路径上）
异步：T = max(T_compute, T_move)  （义务落入影子时间，解码只承担溢出部分）
⇒ T_async ≤ T_sync 恒成立（异步路径无强制同步点时）
   T_async < T_sync 当且仅当 0 < 被隐藏的义务 < 流水容量
```

同步方案里，搬运时间**必然**吞噬解码——它在关键路径上，无处可放；异步方案里，搬运时间**至多**吞噬解码——有余量即被吸收。两者相等的唯一情形：义务为零或全部溢出——这正是本技术的两个边界工况。

**第三步：收益幅度的三参数公式（参数全部实测）。**

```
收益% = 被隐藏的搬运时间 / 同步步窗 = （义务率 × 单位搬运成本）/ 步窗
```

| 参数 | 值 | 来源 |
|---|---|---|
| 步窗 | 27-32 ms | 实测（解码计算图执行） |
| 单位搬运成本 | 1-3 ms / 8 页批（13 MiB，≈10 GB/s） | 实测（DMA 实跑） |
| 搬运义务率 | 工作集/池比 × 序列增速 | 守恒律决定 |

**第四步：义务的两种形态（决定收益出现在哪——这是关键一层）。**

| 形态 | 规模 | 占步窗 | 异步收益 |
|---|---|---|---|
| **稳态换页**（每步新增 ≈0.09 页 ≈ 0.15 MiB；全秒 ≈10 MiB/s，占 DMA 吞吐 0.1%） | 小 | **≈0.05%** | ≈0——藏不藏无所谓 |
| **召回爆发**（轮首 turn closure，集中召回数十页 = 数十 MiB） | 集中在轮首数步 | 可达数%-数十% | **收益主体**：爆发被完整隐藏 |

⇒ **收益的精确工况画像**：稳态换页义务对 10 GB/s 的 DMA 微不足道（约 0.05% 步窗）——**异步收益的主要来源不是"稳态换页"，而是"轮首召回爆发"**：工作集越超池、轮次越长，轮首爆发越大，异步收益越大。这一层解释了全部实测：浅载/单发（义务小）r≈1.02-1.13（等价）；深轮多轮（轮首爆发）r=0.80。

**第五步：流水深度（DEPTH）的理论上限——"最多几批同时在飞"**：

- **需求侧**：稳态义务率 ≈0.09 页/步 ⇒ 1 批（8 页）已可覆盖约 11 步的义务；**深度需求的真正来源是召回爆发**——爆发深度（页）÷ 8 = 有意义的批数；
- **供给侧硬上限**：设备 free 槽（≤1,024）· Host 配额（数千页）· 双份缓冲（每批 ≈26 MiB）——理论上几十批可行；
- **理论甜蜜点：2-4 批**（尚未实测——浅载仅测过 D2 一档，深载分档待测）——超过峰值义务深度的档位是闲置（排队批次不会让 DMA 更快，只是把同一笔义务摊得更平）；
- **DEPTH=1 是最差配置**（2026-10-19 三档实测：D1 182.6 < D0 183.6）：既支付半流水的管理/收割开销，又无摊薄收益——**要么 0（纯同步），要么 ≥2**。

**实测对照（2026-10-19 三档，浅载零外压，各 12 拍）**：DEPTH=2 avg 187.1 > DEPTH=0 avg 183.6 > DEPTH=1 avg 182.6——方向与不等式一致（异步 ≥ 同步），幅度与浅载义务预测一致（+1.9%，样本量未钉显著；D1 反常 = 半流水开销，已立挂账复查）。**深载（长程多轮、深超池堆积、轮首爆发密集）的 ON/OFF 对照是关键测量——理论预测收益落在"轮首爆发规模 / 步窗"区间，待实机长跑测得。**


**第六步：三层分工（本技术在加速栈中的位置）。** 单次解码的时间构成 = 权重计算 + KV 读 + KV 写 + 调度——本技术对四项均不做贡献：**单步速度的天花板由硬件效能决定（L1：带宽/算力）**，单步的乘法加速器是投机解码（**L2：MTP 接受率**）。本技术属于 **L3 系统层**：不加速单步，而是保证长程持续性——工作集超池时把换页义务移出关键路径，使 L1×L2 的速度在第一百轮对话里仍然成立（保全系数 ≈1.0；无 L3 的历史极端案例被换页侵蚀至 5.6 tok/s）。三层近似乘法关系：**长程有效速度 ≈ L1 × L2 × L3 保全系数**。且存在耦合：L2 越快 → 页产生率越高 → 深超池下对 L3 的需求越大——三者是同一流水线的上下游，不是竞争关系。

### 3.2 目标函数修正：池从"容量门槛"变成"搬运频率旋钮"

异步之后，"池越大越好"的直觉失效——换页不再是灾难，容量就变成了**调节搬运节奏的旋钮**：

```
池 < 工作集（~42K）   ：每步都在搬运——最差区
工作集 ≤ 池 < 请求线   ：常规轮次零搬运——甜点区（本机请求线实测：中位 ~56K / 最大 ~96K）
池 ≥ 请求线           ：边际收益骤降（实测：64K vs 51K 仅多撑约 8 轮会话）
```

**结论：16GB 显存是零和的——每 1 GiB 给池，就少 1 GiB 给 KV 精度（影响每一轮输出质量）或权重档位。理想形态是：浅池（够工作集）+ 深流水（搬运全隐藏）+ 高 KV 精度。**

### 3.3 正确性工程：异步的代价要自己扛住

**说人话版**：异步 = 请了"跑腿小哥"（见 §3.1 解剖）。规矩立不好会丢件、会搬错——所以我们给他立三条规矩，外加一张"考卷"。

1. **捕获期/运行期分离**：部分属性在"捕获"阶段固化，切换通过重启完成——操作边界明确；
2. **publish 前不可丢弃**：任何"唯一有效副本"在发布新副本前不得释放；
3. **取消可回滚**：取消是可撤销的排队事件；已开始的 I/O 排空后才回收配额。

**无损门验证**：同一 prompt 在"池内"与"首次超池"两条路径下——**输出逐字完全相同**。异步不改变模型输出，只改变搬运发生的时机。

## 5. 存在的问题与仍在攻关的课题

### 5.1 一个攻关中的问题：时段性慢态（我们内部叫"死亡谷"）

这是本线最"硬"的攻关课题——如实写出来（含最新进展）：

**现象与指纹**：
- 长时间负载下偶发的延迟尖峰：同一个解码步的耗时可从正常的 30 ms 级涨到数百毫秒级（深端可达秒级）；
- **指纹**：GPU 占用率满、频率满，但**功耗极低、显存几乎不动**；
- **性质**：分钟级自愈；**输出不受影响**（池内 vs 谷中的输出逐字相同）。

**攻关进展（五步，全部有实测支撑）**：

1. **仪表化**：把解码步拆成四个时间区段 + 设备侧段内打点——让"时间花在哪"可视化；
2. **按需复现（里程碑）**：从外部进程施加显存压力（占用约 1.2 GiB）即可**稳定造出该状态**——施加即入谷（探针速度降至健康的 1/25，即"谷档"）、释放即恢复、两轮可重复 ⇒ 不再依赖"等它自己出现"；**更深的档位（深档，decode ≈1.6 = 健康的 ~1/100）也可复现，但受"机器态时窗"支配**（2026-10-16 深档搜索实验，全晚 12 发长持）：**时窗内 4/4 命中**（两簇窗口：17:32-17:44、19:23-19:35；含长跑引擎的首持/第 2 持与重启后首持，形态高度一致 [~1.6, ~1.6, ~9]，探针被拖至约 100 s/发；**样本量限定：重启后首持 2/2、长跑首持 2/2，而"第 2 持"为 n=1 单次观测**，不单独作结论）；**时窗外 8/8 皆为谷档**（含全新实例的重启首持与紧接第 2 持——"重启即复现"的配方被证伪）；剂量（1.2/2.4/3.6 GiB）、时长（600 s）、脉冲串、静置（8.5 min）均非决定变量 ⇒ **当前最佳解释 = 机器态时窗**（开合条件未知；1.5h 尺度上不是简单"休息-恢复"）；深档条件解析中，**不外推为"随时可造"**；
3. **机制定位**：该状态下**整轮时间全部花在 host 侧的提交调用里**（`submit ≈ wall`、`wait = sync ≈ 0`；自然样本 3286 条 + 人造样本 6 条）——不是设备等待、不是内核执行、不是内存拷贝；且外部进程的算力 / 拷贝 / 驱动节流全部正常 ⇒ **卡点在引擎进程自身的提交路径（驱动内部阻塞）**；
4. **候选排除**：PDL 重叠等待（原最大嫌疑）❌ 出局（ON/OFF 回切反例）；页中转路径 ❌；宿主↔设备路径降速 ❌；host 页档位策略 ❌；池大小 ❌；驱动节流 ❌——逐项实测排除；
5. **缓解已确认一条**：**避免与引擎争抢显存**（本轮唯一确证有效的缓解手段）。

**当前状态**：机制已从"自旋猜测"收敛到"提交阻塞"，并备好 **3 步、约 2 分钟的最小复现协议**（可供上游 / 驱动侧研判）；全时段监控与自愈机制在岗。**仍待解**：自然状态下该慢态的触发源（外部显存压力只解释了"人工通道"）——以长跑守望 + 案例驱动的现场捕获持续取证。

**追捕状态的一个侧面**（2026-10-16）：这段攻关已连续 **120 小时（5 昼夜）不间断**（10-11 → 10-16，全程工程化受控压测 + 现场取证），中途顺手修复和改进了大量问题（仪表缺陷、回归、自伤 bug 等）；今天（10-16）再次进行异步页流水极深池 AB 测试（结果见 §3.1）。真凶尚未抓获，但有两条可以明说的进展——① **嫌疑范围在系统性收紧**：PDL（本曾的第一嫌疑）、页中转路径、宿主↔设备降速、host 页档位策略、池大小、驱动节流均已逐项实测出局（其中 PDL 为开关回切反例所否证）；② **猎捕方式已升级**：该状态可以按需制造（外部显存压力协议，施加即入谷、释放即恢复；**深档受"机器态时窗"支配——窗内 4/4、窗外 8/8，开合条件解析中**），不必再"等窗口"。剩下的是把提交路径上的具体阻塞点钉到行号级。

> **想自己复现？** 见 [**≈2 分钟最小复现协议**](研判-驱动提交阻塞-最小复现与可行动项-20261016.md)（[English](Minimal-Reproduction-Valley-On-Demand-20261016.md)；一条命令 `scripts\valley_minrepro.ps1`）与 [**谷 FAQ**](FAQ-死亡谷-20261016.md)。

### 5.2 其余问题清单

1. **流水击穿边界**：慢峰时单批搬运 11.5-33.7 ms 会接近甚至超过解码步窗（27-32 ms）——异步方案固有的"暴露窗口"；
2. **深流水尚未转正**：多批搬运同时在飞（加深流水深度）是摊薄击穿的正确方向，当前仍在验证；
3. **SSD 层的取舍（有意为之，非跟随项）**：原作者的分层含 SSD 下沉层；对我们的目标场景（**稠密模型、单路长上下文**），全部 KV 都能常驻 Host RAM（最坏 262K × 33 KiB ≈ **8.6 GB**，本机 RAM 128 GB）——**SSD 没有容量上的必要性**，而其热路径成本（同源实测 +11%）与工程复杂度是实打实的。我们的优先级：把 **RAM↔显存这一层的搬运做成流水线（深流水）**；SSD 留待"跨重启持久化 / 海量闲置会话"型需求出现时再评估；
4. **拷贝式搬运**：我们的 demote/restore 仍是拷贝语义；**原作者已实现"所有权移动"**——正在追赶。**附判据（待排）**：它对"时段性慢态"（§5.1）的作用是**间接的、概率性的**——谷的链在"提交→驱动阻塞"（搬运量已被实测排除），但所有权移动能减少**页管理事件数**（更少的拷贝提交与分配/释放动作），可能缩小暴露面；若"叠加态假说"的触发条件涉及引擎自身活动，则可能顺带减触发。**判别实验**：所有权移动落地后，用现成的**按需复现协议**做"拷贝版 vs 移动版"的**入谷率 / 谷深配对对照**（n 次），同时把"**页管理活动密度**"列入自诱导审计的时间线；
5. **覆盖差异**：我们深耕"单路长上下文"；原作者的"多路并发"场景我们覆盖不足。

## 6. 未来的方向

1. **深流水**：多批在飞，把击穿余量拿回来——"浅池 + 深流水 + 高精度"形态的最后一环；
2. **所有权移动**：向原作者的语义看齐（搬运不复制、恢复生成零快照），降低搬运的字节成本；
3. **Host 层深化（而非 SSD 跟随）**：扩大 Host 配额（RAM 充足，比 SSD 快三个数量级）、优化 RAM↔显存搬运；SSD 留待特定需求（跨重启持久化 / 海量闲置会话）出现时按需评估——**容量分层对"装不下"是解药，对"走得慢"不是**；
4. **精度×容量联合优化**：把"省下池预算换 KV 质量"做成自动策略（本机已有完整的精度-容量精算表）；
5. **向上游回馈**：把我们验证过的修复与实测数据贡献回社区（本引擎与 llama.cpp/NInfer 生态），并对齐双后端契约；
6. **决策质量观测（误搬率）**：统计"搬出的页在 N 步内又被搬回"的比率——让"打分阈值 / 保护范围该不该调"**从猜变成量**（纯观测，不改引擎）。

## 8. 总结（三句话）

1. **原作者把"装不下"变成"装得下"**——KV 虚拟化让 16GB 消费卡承载百万 token 工作区；
2. **我们在其基础上把"换页"从同步等待变成异步页流水**——搬运与计算重叠，超池不等于减速；
3. **目前：第一阶段已交付，第二阶段（深流水/所有权移动/SSD 层）在途**——目标：让消费级显卡上的长程 Agent 会话，从"持续装得下"到"持续跑得快"。
