# 设计稿：挂账 42 第三步 v2 —— 跨 decode 步 pending 流水化（异步 demote）

> 2026-10-11 · CodeBuddy 起草，待 TELE 复核后施工。
> 前置：挂账 44 profile 定案（patch `ledger44_demote_profile`）——瓶颈 = demote 拷贝在
> compute stream 同步等待（慢峰 3.4-7.8ms/批，27:17 双峰分布，快慢 10-20 倍），账本全部无罪。

## 1. 目标

demote 的 D2H 拷贝与 decode kernel **并行**：拷贝提交后 demote 函数立即返回（decode 步继续），
拷贝在 transfer stream 上飞行，下一步的 demote 调用收割上一批（等待已被上一步 kernel 时间覆盖）。
预期：decode 期页满停顿从"每批 3.4-7.8ms 串行"→ 接近零。

## 2. 机制

### 2.1 状态（ProgramImpl 新成员）

```cpp
struct PendingDemote {
    std::optional<HostKVExtentReservation> reservation;  // extent pin（RAII）
    std::vector<LogicalKVPageHandle> handles;            // 已 prepare 的页
    LogicalKVPageStore* store = nullptr;                 // 来源 store（text/backend 校验）
    bool submitted = false;                              // copy 已提交 transfer_streams
};
std::optional<PendingDemote> pending_demote_text_;
std::optional<PendingDemote> pending_demote_backend_;
```

- 一次只挂一批（每 store 一槽）——arena extent 的连续分配约束决定；
- event 复用现成机制：`context_completion_.record(transfer_streams)`（materialization 先例）
  ——收割判定用 `context_completion_` 的完成查询（与事务的 `transfer_submitted` 消费同款）。

### 2.2 时序

```
decode 步 N:
  ensure_sequence_kv_mapped → ensure_ring_room:
    ① 收割 pending（若挂）: wait copy event（≈0ms——上一步 kernel 期间拷贝已飞完）
                            → publish（extent 账本）→ 逐页 release + drop → 清槽
    ② early-verdict（现有 free_final < need throw）——此时 free 已含收割页 ✓
    ③ 需要释放: 攒批（K=8，语义不变）→ copy_to_host(..., transfer_streams) 异步提交
                            → transfer record event → **函数返回，pending 挂起**
  decode kernel N+1 跑（与 D2H 并行 ✓）
decode 步 N+1: 回到 ①
```

### 2.3 正确性锚点（逐条）

| # | 风险 | 防线 |
|---|---|---|
| a | copy 读到页的"未来写入" | 提交点前的 compute 工作必须完成：copy 提交前 compute record event → transfer wait event。提交点处 compute 队列为空（demote 在步首、kernel 未发）→ 等待瞬时零开销 |
| b | drop 丢数据（拷贝未完成） | 收割序 = wait copy event → publish → release → drop。drop 只发生在事件完成后 |
| c | pending 页被重复 demote | prepare 的 source pin（source_pins > 0）→ 候选扫描 L1975 跳过 ✓（天然去重） |
| d | early-verdict 误判（free 少算了 pending 批） | 收割（①）在 early-verdict（②）之前 |
| e | 异常/取消时 pending 悬空 | PendingDemote 析构兜底 `synchronize_transfer_streams()` + reservation RAII 释 pin；ensure_ring_room 的 throw 路径与 decode_cancelled break 路径都先收割再走 |
| f | 引擎关停 | ProgramImpl 析构先 `synchronize_transfer_streams()`（commit.cpp L914 先例） |
| g | text/backend 两套 store | pending 按 store 分槽；flush/收割按来源 store 校验 |

### 2.4 回退开关

`NINFER_ASYNC_DEMOTE`（默认 1=异步；0=退回同步批量）——运行时读一次，风险兜底与 A/B 对照两用。

## 3. 不变式（与批量版一致）

- 页生命周期谓词不变（committed full / device_resident / source_pins / can_pin_source）；
- publish 拒绝 → 整批保留 device replica（2026-10-02 契约）；
- drop 失败不计数；
- 取消检查点保留（挂账 42 第一步），收割不受取消影响（数据安全优先）。

## 4. 验证计划

1. 编译（j6 独立窗口）→ EXITCODE=0；
2. 部署（重启现役 @8094，用户已默许短暂中断）；
3. A 臂探针无回归（decode ≈100，TTFT 正常）；
4. multiturn 超池探针（demote 批次的 profile 行：**copy 段应全变快峰**（launch 即返），
   `since` 段不变，收割等待不可见（被 kernel 覆盖））；
5. 实机长会话（用户 DSH）——decode 波形从"平稳 4-6"→ 预期回 100+；
   profile 的 `tail` 段（收割的 publish/drop）若升高即为流水化代价可见化。

## 5. 明确不做（范围外）

- restore 侧异步化（H2D 本来 stream 排队、非卡点）；
- 多批 in-flight（一次一批够——批 4ms × 每步一批，流水窗口已足）；
- demote_other_addresses_to_host 的批量化（多 address 冷页路径，单序列场景低频）。

## 6. TELE 复核三缺口答复（2026-10-11 17:50 增补，施工依据）

### 6.1 缺口 A：正常请求终止时 pending 收尾

**策略 = 每次 ensure_ring_room 调用首无条件收割**（施工简化，2026-10-11 18:2x 修订——**比原 age 上限方案更强**）：
- 收割点是 `ensure_ring_room` 开头（任何新请求必经；decode 每步、prefill 每 chunk 都过这里）；
- **原"age 上限 32"方案被弃用**：由于收割就在每次调用开头，"挂着跨多次调用"的窗口天然不存在
  （挂起窗口 = 两次相邻调用之间 = 一步 decode / 一个 prefill chunk——**4ms 拷贝完全被覆盖**）；
  引擎 idle（无调用）期间 pending 挂着 = 池暂少 8 页 + 8 页暂不可检索——idle 无请求，无影响；
- **行为差异明写**：pending 期间（≤一步）该 8 页 `host_resident=false` 未 publish → 检索 mask
  看不到它们（"silently unreadable"契约的临时子集）——窗口 8 页/上千页且仅一步，可接受；
- TELE 复核（18:2x）指出"age 上限未在代码实现"——**属施工期有意简化**（更强方案），本注记为准。

### 6.2 缺口 B：序列/上下文释放与 pending 交互

**防线 = prepare 的 source pin（已验证：host_kv_store.h:134 `pages.pin_source(page)`）**：
- 序列驱逐/rewind 的页回收路径必须检查 `source_pins != 0` 并跳过（pin 的设计语义）；
- **施工时验证**：grep 序列释放路径（release/evict/rewind）对 source_pins 的检查点——
  若某路径缺检查，在该路径前插入"强制收割 pending"（施工任务清单化）；
- 兜底：即使序列释放后页被回收，pending 的收割也只在"页仍 valid 且 device_resident"时
  drop（施工时收割循环加 valid 检查——`pages.valid(logical) && pages.device_resident(logical)`
  才 drop，否则仅 release pin）。

### 6.3 缺口 C：异常路径完整语义（放弃批 = 可重试状态）

**放弃语义（与原版 prepare/publish 失败路径逐条同构）**：
1. `synchronize_transfer_streams()`（保证在飞的 D2H 完成——无悬空写）；
2. 释放 reservation（extent 归还 arena——**host 副本丢弃**）；
3. 页状态：`set_writer(false)` 已做（攒批前）、`release_active_reference` **不还**（与原版
   失败路径同构——writer 清但 reference 保留）、device replica **不 drop**（数据完整）；
4. 结果 = "这批 demote 没发生"——下次扫描可重新选中（可重试）✓；
5. `PendingDemote` 析构函数 = 上述 1-3 的 RAII 兜底（覆盖 throw/取消/关停三路）。

### 6.4 锚点 a 口径修正（采纳 TELE）

"等待瞬时零开销" → **"预期 ≈0、以 profile 验证"**（提交点在步首、kernel 未入队——但
prefill 路径的 ensure_ring_room 在 prefill kernel 入队后调用，event 等待 = 等已入队 kernel
完成——**正确性必需**（页写入可能来自 prefill kernel），**性能影响限于 prefill 期**
（本来不敏感），施工时在两路径分别记录 profile）。

### 6.5 施工任务清单（含上述验证项）

1. PendingDemote 结构 + 两槽 + 析构兜底（6.3 语义）；
2. `ensure_ring_room` 开头收割（**每次调用首无条件收割**，见 6.1 修订；原 age 上限方案弃用）+ early-verdict 在收割后；
3. demote 攒批路径改"提交 + 挂起"（copy → transfer_streams + compute→transfer event 顺序 + record）；
4. 收割循环加 `valid && device_resident` 检查（6.2 兜底）；
5. **施工时验证项**：grep 序列释放路径的 source_pins 检查（6.2）；prefill 路径 profile 记录（6.4）；
6. `NINFER_ASYNC_DEMOTE=0` 回退开关；
7. 编译 → 部署（重启现役）→ A 臂探针 → multiturn profile 行（copy 全快峰）→ 实机波形。
