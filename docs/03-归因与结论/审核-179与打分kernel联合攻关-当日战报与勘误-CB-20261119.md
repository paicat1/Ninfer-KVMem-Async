## 〇、当日净结论（五条）

1. **179 捕获已定量归因（§242）**：`kvmem_retrieve_scores_kernel` 占 GPU 忙碌 **86.5%**，2,432 次 × 187–191 ms；memcpy 仅 **0.27%**；注入开销 +1.3% ⇒ **日志反压（H1）死**。
2. **`group = 6` 已钉死**：现役 ARMED 行 `heads=24 kv_heads=4 head_dim=256`（构建史 :297 / `docs/_research/...部署适配.md` L297 双处可查）⇒ GQA 每组 6 个 q-head 共享一行 K。
3. **1b（per-head 一趟化）是唯一干净的「减半」方案**：单 block 覆盖全部 4096 候选 ⇒ **softmax 在 block 内闭合，零跨 block 同步**，16 KB shared 装得下，且同时砍掉「一遍 dot」与「一遍 K 读」。
4. **1e（全局 scratch）作废**：logits 全量 = 896 token × 24 head × 4096 块 × 4B ≈ **336 MiB/launch**，比它想省的 201 MiB K 读**还大 1.7 倍**。
5. **真正未解的问题**：算力 0.3%、带宽 0.1%（见 §3 勘误），两者都远未饱和 ⇒ 瓶颈在**延迟链 / 指令构成 / launch 粒度**，不在流量。下一步该量的是 profiler 利用率，不是再算一遍账。

## 三、四处勘误（含办公室自己的三处，逐条留档）

### 3.1 H1（日志反压）——证伪，办公室提出的假设

- 误读 `host 0.0%` 为「CPU 空闲、阻塞在 syscall」，实为「**host 侧搬运量为 0**」；
- `1/5.59 ms = 178.9` 与 `896 ÷ 5.04 s = 178.1` 是**数值巧合**；
- 直接否证：注入开销 +1.3%（520.9 → 531.0 s）。

### 3.2 「traffic-bound 实锤」——单位错误，差 1000 倍（办公室）

```
192 MiB ÷ 187 ms = 201.3 MB ÷ 0.187 s ≈ 1.08 GB/s
```

**不是 1.03 TB/s。** 且 RTX 5080 是 **GDDR7（~960 GB/s）**，无 HBM。1.08 GB/s 占带宽 **0.11%** ⇒ 「数据在搬」不成立。

### 3.3 1e（全局 scratch）——量级算错 896 倍（办公室）

我按「单 token」算了 384 KiB，实际一次 launch 覆盖 896 个 token：

```
logits = 896 × 24 × 4096 × 4B ≈ 352 MB ≈ 336 MiB / launch
```

**比它想省的 201 MiB K 读还大 1.7 倍** ⇒ **1e 作废**（不是「需要跨 block 同步」这么简单，是根本不该存在）。

### 3.4 「b 分割可零跨 block 同步」——不成立（TELE 提出，办公室补正）

softmax 的 `(max, sum)` 是**全候选集上的归约**；把 4096 个候选切给 16 个 block 后，必须再做一次跨 block 合并 ⇒ 仍需第二个 kernel 或 cooperative launch。且 shared 里的 logits **跨 kernel 不存活**，phase 2 要么重算、要么落全局（又回到 3.3 的 336 MiB）。

**⇒ 只有「单 block 覆盖全部候选」的结构能在 block 内闭合 softmax。这正是 1b 干净的根因，也是为什么 b 分割救不了它。**

> **备注（TELE 提出，挂起可重评）**：若 M0 判出「流量主导」，b 分割的**理论下限**（只读 K 32 MiB + 局部统计）低于 1b 的 96 MiB——但需额外 kernel 与 logits 落盘（336 MiB）或重算。**⇒ 暂按否决挂起；流量主导时重评。**
>
> **另需澄清**：1b **不**改变 launch 结构。「合并 per-layer launch」是刀 2（`grid = layers × tokens` 的合并），§242 已因「GPU 无空闲段 + 需缓存 16 层 q ≈176 MB」撤销——两者不能混算收益。

## 四、仍未解的核心问题

```
每 launch：~45 GFLOP 于 187 ms ⇒ 0.24 TFLOPS（峰值 0.3%）
           201 MB   于 187 ms ⇒ 1.08 GB/s（带宽 0.11%）
```

两把尺子都远未饱和，那么 187 ms 花在哪？候选按可检验性排序：

| # | 候选 | 判别手段（nsys metrics） | 若成立的对策 |
|---|---|---|---|
| A | **依赖链延迟**：每 dot 单累加器、256 次串行 FMA（1a 已加 4 累加器，仅 -8.3% ⇒ 部分成立） | `smsp__average_warp_latency`、`stall_long_scoreboard`、`stall_wait` | 提高 ILP（更多独立累加器/更宽向量），或 1b 减半 |
| B | **expf / SFU 占比**（每 (b,head) 两次 `expf`，共 196K/launch） | `smsp__inst_executed_pipe_xu`、`sfu_cycles_active` | 用 `__expf` / 查表近似（注意精度，M2 1e-5） |
| C | **launch 粒度**：每层一次 launch，每次仅 896 block | `launch__grid_size`、`sm__ctas_active` | 合并层维（但 §242 已判刀 2 无收益，需复核） |
| D | **未合并访存 / 缓存命中差**（`kbar` 行 1 KB，stride 访问） | `l1tex__t_sector_hit_rate`、`lts__t_sector_hit_rate` | 行对齐 / `__ldg` / 共享预取 |
| E | **block 内 256 线程处理 4096 块 = 每线程 16 次串行** | 实测 `sm__warps_active` 与理论对照 | 增线程或增 block（拆分 head 维） |

**⇒ 下一步不是再算流量账，而是拿 nsys 的「stall reason + 利用率」两页数据。**

## 六、方法论纪律（当日最贵的三条，双方各领）

1. **任何定量断言必须二次验算，且写全量纲**——当日三处错误（`host 0.0%` 语义、TB/s 单位、1e 的 896 倍）全部只需一次量纲检查即可发现。
2. **「利用率」只能来自 profiler，不能来自手算**——0.3% 与 0.11% 都是手算结果，它们自相矛盾（两个都远未饱和却跑满 187 ms），这本身就是「手算不够用」的信号。
3. **三方一致 ≠ 成立，收敛的是推理链不是事实**（LUMMY 已把这条写进角色定义）——H1 是典型案例：办公室提出、TELE 核机制、LUMMY 补前置，三方都说「收敛」，实机 nsys 一次就推翻。
