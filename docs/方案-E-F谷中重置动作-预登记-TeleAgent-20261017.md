## 一、理论与实践支持（结合 130h 数据）

**支持（5 条）**：
1. **【最强】请求结束 → 状态立即消失（437 实证）**：29 分钟自然持续谷，10:00 请求一结束，host 从 ~100% 掉到 25–36%、util 7%、功耗 30W——**"结束请求"是已验证的有效重置动作**；
2. **状态可逆（浅谷）**：外部压力释放 → 立即恢复（93× / 18× / 14× 反转；第四轮 / E-C / E-D）——**"状态"可被改变**；
3. **深谷粘性（新数据）**：shot 5–8 释放后残留 0.19 / 1.1 / 0.82 / 0.44 s（递减）；完全恢复 ~2–3 分钟或请求结束——**释放不足以清深谷** ⇒ **需要更强的动作**（本方案的直接动机）；
4. **重启先例**：E-C / E-D 重启后恢复健康（但不免疫）——**"重置类动作"在进程级有效过**；
5. **机制线索**：病灶 = host 侧提交链（每轮 `program_submit` 26 ms → 0.3–2.5 s）；**"结束请求"断开了提交链**，新请求 = 新提交序列（**可能走干净路径**）⇒ "取消 + 续写"理论上等效于"**人为提前触发'请求结束'**"。

**风险 / 反方（3 条，诚实列）**：
1. **重置 ≠ 免疫**：重启后仍可能谷（E-E 重启后 40 分钟又谷）；shot 5 谷后 shot 6–8 连续谷（但均为 400 档，暂不能区分"谷后效应" vs "400 效应"）；
2. **粘性机理未知**：若"粘性"位于"引擎不可及层"（驱动内部），引擎侧重置可能无效——**需实验检验**；
3. **外压仍在时重置可能无效**（取消 + 续写后立即再谷）——对照实验设计见 §四。

## 一.5 机理假说 H5（用户 · 时序链）与数据对照（2026-10-17 22:0x）

**H5（用户提出）**：谷 = 异步流水**时序不对齐**（接不上 → 停滞）；**粘性 = 未完成的时序任务必须按规程走完**，走完才有机会重新异步流水；"搬运藏在解码背后"（延迟隐藏）在资源紧张时可能**堆积**；重置 = 让时序**归位**。约束：**损失只允许时间维度，不允许解码正确性 / 信息完整性损失**。

**与数据对照——支持（4）**：
1. **等待发生在"提交侧"**：`program_submit` 26 ms → 0.3–2.5 s（93×），而 `device_wait` 不变（350–540 µs）⇒ "在等什么"已定位在 **host 提交路径**（符合"接不上"）；
2. **粘性像"残留消化"**：残留链 189 → 1104 → 815 → 437 ms（递减）；完全恢复 ~2–3 分钟或"请求结束"——符合"走完才归位"；
3. **"请求结束"= 归位的已验证实例**：437 实证（29 分钟谷，完成瞬间 host 100%→25%、util 7%、30 W）；
4. **延迟隐藏退化方向合理**：异步 overlap 在资源紧张时退化（排队/串行化）是常见模式；**且引擎自身搬页计数 = 0**（d2h/h2d/spill/evict 全 0）⇒ 若"堆积"存在，**在引擎不可见层（驱动/OS）**——与"粘性驻留引擎不可自清层"判读一致。

**需要按数据修正（2）**：
1. "GPU 不运算" → 实测 **util 仍 100%、功耗腰斩**（70–86 W vs 250–290 W）——是"**低效活动/忙等**"而非"停摆"；
2. "时序错位"是**概率事件**（150 MiB≈20%、400 MiB=100%）——错位条件含未刻画的时变变量；设计上重置需容忍"误触发"（代价=时间）。

**待验证（ETW 目标）**：等待对象的具体形态——队列满 / 驱动内部锁 / 内存管理慢路径 / WDDM 迁移与同步事件——**H5 把 ETW 的观察目标从"泛泛的驱动活动"收窄到"等待链 / 同步事件"**。

## 二、重置动作光谱（全部 vs 针对性）

| 级 | 动作 | 重置对象 | 原理 | 开发量 | 代价 |
|---|---|---|---|---|---|
| **R1** | **取消 + 续写** | **当前请求的提交链** | 人为触发"请求结束 → 状态消失"；续写 = 同前缀重发 | **零**（客户端即可） | 中断感知；续写开销；丢 ≤1 轮 |
| **R5** | **引导完成 + 续写** | **当前请求的"完成"清理路径** | 模拟 437 的"**请求完成**"复位语义（区别于取消/断开——结束路径可能不同）；让请求到达完成点 | 小–中（接口待 CB 确认） | 同 R1 级（丢进行中尾部 + 续写开销） |
| R2 | **内存池 trim** | 分配器"空闲块持有" | 主动归还空闲显存 | 小（引擎侧，若无现成接口） | ≈零 |
| R3 | **清 KV 池** | 池"贴边 / 碎片状态" | 重建池分配 | 中 | 丢缓存（重算前缀） |
| R4 | **重建 CUDA 上下文** | 整个 CUDA 状态 | 重做初始化 | 大 | ≈部分重启 |
| R0 | （参照）**重启引擎** | 进程 | 全重置 | 零（已有） | 服务中断；已证有效但不免疫 |

**设计原则**：从**最针对性、最低代价**开始（R1 → R5）——无效再升级（R2 → R3 → R4）；**每级独立判据**；**总约束（用户）：只损失时间，不损失解码正确性 / 信息完整性**——据此 R3（清池）/ R4 标注为"信息 / 缓存重建代价"，仅在前级无效且用户认可时启用。

## 三、代价分析（逐项）

**上下文**：
- R1：**已生成内容保留**（作为新请求上下文重发）——"输出连续性"可保（除取消瞬间 ≤1 轮）；
- R1 的 **KV 缓存行为待观察**：重发 = 新 turn（同前缀）——**预期 cache 命中**（历史 turn closure 99.9%）——观察项：**续写 TTFT**（若命中应低）；
- R3 / R4：缓存 / 上下文丢失（重算 / 重载）。

**解码**：
- R1：取消丢"进行中的一轮"（≤1 轮 token）；**续写从已生成末尾继续**；
- 判据加"**续写连续性**"：续写首段内容与原轨迹一致（人工抽检样本）。

**其他**：R0 中断服务；R2 无感。

## 四、实验设计（E-F）

**造谷**：`vram_hold 400 MiB`（复现率轮终版 **3/3**——稳定可靠）。

**单拍序列**：
1. 自然基线确认（host/round <100 ms）；
2. 施加 400 MiB；
3. 发 437 形态请求；
4. **等谷确认**：host/round >300 ms 持续 ≥30 s；
5. **执行 R1**（取消 + 以已生成内容续写）；**R1 无效时按判读矩阵先试 R5**（引导完成 + 续写——区分结束语义）；
6. 观察 60 s：host/round、功耗、产出；
7. **条件 A（有压）**：保持压力，观察 120 s——测"重置有效性 + 是否再谷"；
8. **条件 B（撤压）**：撤压后观察——与"纯撤压"（历史数据）对照恢复速度；
9. 恢复确认 → 下一拍。

**预登记判据**：
- **R1 有效**：重置后 60 s 内 host/round 回 <100 ms **且**功耗回 250 W+ **且**续写正常产出；
- **R1 部分**：60 s 内 <300 ms 但未回 <100 ms；
- **R1 无效**：仍 >300 ms；
- **代价记录**：取消丢 token 数；续写 TTFT；cache 命中（日志）；
- **正确性验证（用户约束落地）**：续写首段与原轨迹一致（人工抽检）· 续写后 KV 行为正常（cache 命中 / turn closure）· **全程零信息损坏**（丢失仅限"结束瞬间 ≤1 轮"）。

**样本**：条件 A ×2、条件 B ×2（n≥2）；每拍 ~6 分钟；总 ~25–30 分钟。

**工具 / 前提**：
- 全程走规范入口（spawn_visible）+ 可见窗口；台账 + reqlog + 引擎日志 + compute-apps；
- **前提：用户批准 + 先明确解锁**（当前锁 `release_by=user only`——上次教训：须先问）；
- 实现细节（断连 vs 引擎接口取消；续写拼装）**待 CB 确认**。

## 五、判读矩阵

| 结果 | 结论 | 后续 |
|---|---|---|
| **R1 有效 + 有压也恢复** | **强机制**：重置可打破粘性 | 工程化"自愈循环"（检测 → R1 → 验证） |
| R1 有效 + 仅撤压后恢复 | 与"释放"同级（重置无独立价值） | 转 R2 / R3 评估 |
| R1 无效 | **先试 R5**（区分"取消语义不触发复位" vs "重置本身无效"） | R5 有效 ⇒ **结束语义敏感**（H5 细化）；R5 也无效 ⇒ 粘性在"引擎不可及层" → 升级 R2 / R3；R0 兜底 |

## 六、风险与回退

- 低风险：不重启、不改配置、不动引擎参数；
- 回退：任一步异常 → 撤压 → 引擎健康确认；
- 全程可见窗口 + 用户可随时中止。

## 七、交互形态设想（用户提出 · 记录备用 · 产品化后置）

- **面板预设阈值**：在 serve 启动器面板上设置"重置触发阈值"（如 host/round 或功耗指纹），谷中自动执行；
- **手动按键干涉**：面板上加"重置"按键，用户即时触发；
- **TELE 注**：①先"手动最小版"验证有效性，自动化阈值（误触发风险）与面板（产品化）后置——**新功能双门**（方案0 + 一次性判定）届时再走；②自动化形态需先解决"误触发无害性"证明（重置代价 = 时间；未谷时触发无收益但有代价）。
