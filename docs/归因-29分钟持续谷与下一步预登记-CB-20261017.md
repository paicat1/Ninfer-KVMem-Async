## 一、归因结论（逐变量差分：谷期 vs 谷后）

| 变量 | 谷期 09:31–10:00 | 谷后 10:00–10:20 | 分得开？ |
|---|---|---|---|
| **host%（引擎自报）** | **99.6%**（24.5–169） | 70.2%（22–108） | ✅ |
| **GPU 功耗** | **78.3 W** | **30.4 W** | ✅ |
| **SM 时钟** | **2910 MHz** | 1605 MHz | ✅ |
| **GPU util** | **100%** | **7%** | ✅ |
| **显存占用** | 15,749 MiB | **15,785 MiB** | ❌ **几乎没变** |
| 主机空闲 | 89,048 MiB | 89,328 MiB | ❌ 没变 |

**逐分钟（决定性）**：
- 09:38–10:00：**每分钟 12 条 throughput 行、`running` 恒 1、`host` 恒 99–100%**（12 条/分 = 每 5 s 一条，全程在飞）；
- **10:00 请求结束 → `running`=0 → host 掉到 25–36% → util 7% → 功耗 30 W**。

### 结论

1. **【确立】那 29 分钟 = 一个长请求在飞**，它的**每个 token 都走 host 阻塞路径**（host≈100%）；
   **请求一结束，状态立刻消失** ⇒ 不是"独立于请求的机器状态"。
2. **【确立】状态的结束与显存无关**：谷期与谷后**显存占用几乎相同**（15,749 vs 15,785 MiB）、主机空闲相同 ⇒ **显存不是"退出条件"**。
3. **【未定·本轮核心问题】为什么那 29 分钟里每个 token 都被 host 拖住**——两个候选：
   - **H1 请求形态驱动**：该请求**深超池 + 长输出**（thinking 16000 + 输出上限 32768，实测 13 tok/s × 22 min ≈ 17k token）⇒ 每 token 需 host 往返；
   - **H2 机器态驱动**：引擎显存贴边（自由 **343 MiB**）+ 外部占用 **642 MB**（>400 MB 确证阈值）⇒ 页流水拿不到空间 ⇒ 每次提交被拖住。
   ⇒ **两者可由 E-A 判别（下节）**，这是当前最便宜、信息量最大的一步。

## 二、E-A：重载探针（**需用户批准** · 二级"预授权微取证"）

- **现状**：引擎空闲健康（10:11 探针 `decode 172.9 / 241 W / util 99%`）。
- **做法**：发**一发重载请求**，复刻谷期形态：**深超池长上下文 + 长输出 >=2000 token**（同"深轮重载"协议）。
- **预登记判据**：
  - **快**（>=150 tok/s 且 host <40%）⇒ **证伪 H2** ⇒ 那 29 分钟是**请求形态（H1）**；解法＝避免单请求过深/过长，或增大池/降上下文；
  - **慢**（<30 tok/s 且 host ~100%）⇒ **支持 H2** ⇒ **机器态仍在（即便空闲）** ⇒ 解法＝换池给余量（E-C）。
- **成本/风险**：数分钟 · 只加一发请求 · 零风险。

## 三、E-C：换池对照（**需用户批准重启**）
