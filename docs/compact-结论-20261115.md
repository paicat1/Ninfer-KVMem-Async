# DSH 压缩配置排查结论（2026-11-15）

> 供构建史落账。所有结论标注证据来源；未证实的部分单独列出，不混入结论。
> 调查范围：DSH 0.2.2-rc.3（asar 包）/ profile `core-020` / 本地引擎 ninfer-kvmem 8094。

---

## 一、已证实的机制

### 1. patch 覆盖规则（`cordis.patch.yml`）

| patch 形态 | 对 base 条目**有** config 块 | 对 base 条目**无** config 块 |
|---|---|---|
| `- id: X` + `config: {...}` | ✅ 生效 | ❌ **静默无效** |
| `- id: X` + `disabled: true` | ✅ 生效 | ✅ 生效 |
| `- insert: [{id, name, config}]` | ✅ 生效 | ✅ 生效 |

证据链：

- `agent-default-model`（base L90 自带 `config:`）→ profile 的 `config:` 覆盖成功，模型默认值真的变成 ninfer
- `compaction-basic` / `command-compact` / `token-meter`（base 无 `config:`）→ 加 `config:` 后**四个探针全部无效**
- `pwsh-sandbox`（无 config）→ `disabled: true` 生效
- `insert` 新条目 → `retainRatio: 0.99` 探针让插件加载失败，证明 config 传进去了

**结论**：patch 的 `config:` 只能"改"已存在的 config，不能"创建"。行级字段（`disabled` / `enabled`）不受此限。要带 config 必须 `insert` 新条目。

**正确写法**（本机已验证）：

```yaml
- id: compaction-basic
  disabled: true

- insert:
    - id: compaction-tuned
      name: '@deepseek-ai/dsh-compaction-basic'
      config:
        auto: true
        headroomTokens: 8192
        maxTokens: 32768
```

### 2. 插件失败有**两套**机制，日志只覆盖前者

| 类型 | 表现 | 观测位置 |
|---|---|---|
| 启动期激活失败 | `dsh: warning: N entry did not activate` + 堆栈 | `logs\core-020\dsh-web.log`（每次启动截断重写） |
| 激活后自检失败 | `fiberPhase: failed` + `diagnostic` 原文 | **只有** `plugin_manager` / Web UI「内置插件」页 |

反例：`retainRatio: 0.99` 让 `compaction-tuned` 自检失败，`dsh-web.log` 里**一个字都没有**，只显示 `1 entry did not activate`（那是 permission-presets）。

### 3. `enabled: false` 不可信

`plugin_manager` 里：

- `command-compact` = `enabled:false` → 但 `/compact` 命令**能正常使用**
- `tool-pwsh` / `tool-fs` = `enabled:false` → 但 pwsh、读写工具**都能用**

**结论**：`enabled` 只表示"没在管理界面手动启用"，不代表未加载。判断插件是否真的在跑，看 `fiberPhase`（`active` / `failed` / `null`）。

### 4. `resolveConfig` 是**构造期立即执行**，不是惰性

```js
// dsh-compaction-basic/lib/index.js
L824  constructor(ctx, config = {}) {
L826      this.config = resolveConfig(config);      // ← 立即执行
L827      if (this.config.auto) this._registerAutomaticCompaction();
```

所以配置非法会在**启动/激活时**就失败，不会等到第一次压缩。

### 5. `auto` 的默认值是 `true`

```js
L85   auto: config.auto ?? true
```

含义：任何**没配 auto 的** compaction 实例都会注册 pre-step 自动压缩监听器。

### 6. 引擎 reqlog 是区分 O 来源的唯一手段

`serve/request_log.cpp`：

```cpp
L240-242  {"requested_output_tokens_source",
           context.requested_output_tokens_client_set ? "client" : "server_default"}
L532-533  << " max_tokens=" << context.requested_output_tokens << ' '
          << (context.requested_output_tokens_client_set ? "(client)" : "(server default)")
```

即 `work\data\reqlog_serve_8094.jsonl` 里的 `request.requested_output_tokens_source` 字段，能**一刀切开**"客户端显式发的" vs "引擎默认填的"。引擎 INFO 日志的 `max output` 做不到这一点。

### 7. 三处 token 口径对照

| 来源 | 字段 | 实测关系 |
|---|---|---|
| 引擎 INFO 日志 | `prompt=` | 与 DSH 的 `pressureTokens` **完全相等**（47,619 = 47,619） |
| DSH 会话投影 | `surfaceTokens` | = `messageTokens + systemTokens`（25,715 = 23,281 + 2,434） |
| DSH 会话投影 | `pressureTokens` | = 引擎 `prompt`，**已含**系统与工具 |

推论：判断压缩时机时，可直接拿引擎日志的 `prompt=` 当压力值，不必换算。

### 8. `/v1/models` 的 `context_window` 是假值

引擎 `/v1/models` 报 `context_window: 262144`（= `--max-context`），而真实 KV 池是 `--kv-capacity` 指定的 122,880。

可信源只有两处：

- 起服日志：`capacity | KV 122,880 tokens, ... explicit`
- `/stats`：`capacity.kv_capacity_tokens`

### 9. 同一 model-id 可对应多个池，DSH 无法区分

`model_ids.json` 里 `swift` / `gsq` / `q2lynn` 三个 id 各自存在 80k 与 120k 两档池，**对外 id 完全一样**（日志里带 `+dflash2q4km` 后缀只是 spec 头信息）。

解法：拆成多个 provider（`ninfer` / `ninfer-80k` / `ninfer-40k`），用 `contextWindow` 区分池档。已验证引擎 `openai_chat_request.cpp:1034-1038` 只校验 model 是非空字符串，不比对已加载模型，所以同 id 挂多个 provider 是安全的。

## 四、待验证（下次长会话留意）

`headroomTokens: 8192` 是否真的生效——决定压缩阈值是 81,920 还是 24,576。

判据（无需额外工具，看界面上下文百分比即可）：

| 自动压缩首次触发的位置 | 结论 |
|---|---|
| ~25K（约 19%） | `headroomTokens` 未生效，阈值仍是 24,576，老病根没治 |
| ~80K（约 66%） | 生效，阈值 81,920 |

**注意**：不能用"某个压力值没触发压缩"来反推阈值——`compactPressure` 在阈值达标后若 `selectCompactableRange` 返回空范围，会静默返回（L970 `if (result === null && !requireBelowThreshold) return null`）。这个坑本轮踩过两次。
