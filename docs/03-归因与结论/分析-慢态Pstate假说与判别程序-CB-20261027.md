## 一、既有实测：慢态是"满频自旋"，不是降频

**原文（L2460）**：

> 慢轮 1 Hz 采样 = **SM 100% / 满频 2902 MHz / 功耗仅 63–98 W / 显存活动 4–19%**；对照快轮 = 129–217 W / 显存 64%（5080 TGP≈360 W）。⇒ 慢态 = **SM 烧时间不烧功率、不碰显存的忙等/自旋**；**排除降频（满频）**、排除带宽（mem 低）、排除重算（功耗低）。这也解释"util 100% 却慢"与"谷与负载无关"。

**两条独立证据**（L2460 + 定案补充）：

1. 08:08 采样：满频 100% / 63–98 W / 显存 4–19%；
2. 慢态引擎**饿死并行核 8×**（周期数恒定 ~1.06 M、墙钟 8×）⇒ 是**真实指令占用（自旋/长占用）**，不是空闲等待。

**排除清单**（原文）：降频 ✗（满频 2902）、带宽 ✗（显存 4–19%）、重算 ✗（功耗低）、机器/驱动 ✗（满速无节流）⇒ **退化是引擎图内行为**。

⇒ **#58 的假说必须换成"自旋"（spin-wait），P-state 彻底出局。**

---

## 二、正确假说：kernel 内自旋等 host，host 侧变慢 ⇒ 自旋时间被放大

```
GPU 侧：kernel 内 spin-wait 轮询某个 host 写入的标志（页就绪 / 提交完成）
host 侧：提交路径变慢（驱动内部阻塞 —— 谷期实测 submit≈wall、wait=sync≈0）
   ⇒ GPU 满频空转烧 SM 周期、不读显存、不吃功率
   ⇒ 墙钟 6–7× 放大，输出 sha 不变（计算本身没错，只是等）
```

三条特征与实测全对：满频（2902）✓、低功耗（63–98 W）✓、显存低活动（4–19%）✓、sha 不变 ✓。

**与死亡谷同源**：谷期实测"`submit ≈ wall`、`wait = sync ≈ 0`"——即 host 提交调用本身阻塞，GPU 在自旋等它。#58 的"两晚 6–7×、与负载无关"很可能**不是新现象，而是死亡谷的"机器态时窗"形态**（构建史已记"深档受机器态时窗支配"）。**#58 与 #13（谷）应合并立案**，而不是并列两个谜。

## 三、判别程序（v2，替换 v1 的锁频实验）

**v1 的 `-lgc` 锁频实验作废**——慢态本来就在满频 2902，锁频没有可锁的空间。

**正确判别（跑中采样，不是跑前）**：

```powershell
# 慢态发作时，在跑的过程中采一次（不是跑前）
nvidia-smi --query-gpu=clocks.sm,power.draw,utilization.gpu,utilization.memory,temperature.gpu \
           --format=csv,noheader
```

| 采样结果 | 判定 |
|---|---|
| clocks.sm ≈ 2902 **且** power < 110 W **且** mem-util < 25% | **自旋指纹成立**（与 L2460 一致）→ 转 §四 攻关 |
| clocks.sm < 2000 | 才是 P-state 问题（v1 假说复活）——但目前无此类证据 |
| power > 200 W 且 mem-util 高 | 不是自旋，转查带宽/重算 |

**辅助判据**：`NINFER_SPIN_STAMP_VERBOSE=1` + `NINFER_STEP_PROFILE=1`（I3b s6/s7 已有 spin-stamp 打点，case_20261017_223315 用过），直接看 spin 段耗时。

## 四、攻关方向（v2）

1. **定位 spin 循环点**：I3b s6/s7 的 spin-stamp 打点已能拆出"哪段在自旋"；先确认是 demote 的 retire 等待、还是 restore 的页就绪等待（**restore 侧 18.7× demote，嫌疑最大**）。
2. **查 host 提交路径**（#44）：谷期已见 `engine_commit_output` 爆炸（zxz v33 对照 1.5 ms→1004 ms/窗）；同一仪器搬到 #58 时窗，看是否同款。
3. **机器态时窗的记录**：慢态"时有时无"⇒ 需要连续采样（1 Hz）建立"机器态时间序列"，而不是跑前跑后各一次。
4. **不要做的事**：锁频（无效）、降池（§174 已排除）、换 exe（§174 已排除）。
