# 设计稿：挂账 46 v2.1 —— 多批 in-flight（削死亡谷）

> 2026-10-11 · CodeBuddy 起草，待 TELE 复核后施工。
> 前置：v2 异步 demote 已验证（`4c4dcfa` 检查点，exe sha256 `8FCA91461E299073`，
> 实机 333 tok/s 峰值 + 多轮可用 + 死亡谷自愈）。
> 目标：消除死亡谷——req#61 解剖（§三·十九 §3.1）：demote copy 慢（avg 11.5 / max 33.68 ms）
> + 多轮需求暴增 → 页操作超窗口（host 峰值 318.5%）→ decode 1-6 tok/s。

## 1. 目标

**把 demote 的 PCIe 流水填满**：v2 一次只挂一批（8 页）在飞——copy 墙钟时间（avg 11.5ms）
在死亡谷期成为串行瓶颈。v2.1 = **每 store 多槽 in-flight**（N 批同时飞），
预期：copy 吞吐从"批串行"→"流水并行"，**谷内 decode 从 1-6 提到 20+，谷时长缩短**。

## 2. 机制

### 2.1 现状（v2，检查点 4c4dcfa）

```cpp
// program_impl.h
std::optional<PendingDemote> pending_demote_text_;     // 每 store 一槽
std::optional<PendingDemote> pending_demote_backend_;
// 时序：首批满批(8页) copy 提交 transfer_streams → 立即返回
//       下一步 ensure_ring_room 先 retire（wait copy → publish → release+drop）
```

### 2.2 v2.1 改动（单槽 → N 槽环形队列）

```cpp
// program_impl.h
static constexpr std::uint32_t kPendingDemoteDepth = 4;   // 档位见 §4
struct PendingDemoteRing {
    std::array<std::optional<PendingDemote>, kPendingDemoteDepth> slots;
    std::uint32_t head = 0;   // 下一个提交位
    std::uint32_t tail = 0;   // 下一个收割位
    std::uint32_t live = 0;   // 在飞批数
};
PendingDemoteRing pending_demote_text_;
PendingDemoteRing pending_demote_backend_;
```

**提交侧**（`demote_kv_pages_to_host` 的 flush_batch submit 路径）：
- 攒批 + 提交循环**直到槽满**（`live < depth`）——一次调用可挂 N 批（N×8 页在飞）；
- 槽满时**回退同步路径**（原有 flush_batch submit=false 逻辑——正确性不变）。

**收割侧**（`retire_pending_demote`）：
- **v2 的阻塞 wait → v2.1 的 `cudaEventQuery` 非阻塞查**：完成的批立即 publish+drop；
  未完成的批**留在槽里**（下一步再查）——**这是"流水"的关键**（不阻塞 decode 步）；
- 收割循环扫**所有槽**（从 tail 起，完成的连续批全收）。

**容量约束**：
- extent pin：N 批 × extent（host arena 余量——单批 8 页 ≈ 16MB 级，N=4 ≈ 64MB ≪ host-kv-mib 16384——安全）；
- 页 release 延迟：in-flight 批的页仍占 device replica（**drop 在 publish 后——正确性契约不变**）；
  free 计算自然正确（drop 后才计 free——现有逻辑）；
- **RAII 析构**：槽数组**逆序析构**（v2 注释契约：pending batches synchronize while fences still live）——
  N 槽保持同款顺序（数组逆序天然满足）。

## 3. 时序（v2.1）

```
decode 步 N:
  ensure_ring_room:
    ① 收割循环: for slot from tail: if eventQuery(ready) { publish+drop; live-- } else break
       （v2 是 wait——v2.1 只收已完成的，未完成留槽）
    ② early-verdict（free 已含①收回的页）
    ③ 需要释放: 攒批(K=8) → while (live < depth) submit async batch → 立即返回
       槽满 → 剩余批走同步路径（正确性兜底）
```

## 4. 开关与档位

| 开关 | 值 | 行为 |
|---|---|---|
| `NINFER_ASYNC_DEMOTE` | 1（默认） | v2.1 异步（槽深见下） |
| | 0 | 同步批量回退（A/B 对照臂） |
| `NINFER_ASYNC_DEMOTE_DEPTH` | **1** | **= v2 行为（无缝回退）** |
| | **2（推荐起步）** | 2 批在飞（16 页）——先验证 |
| | 4 / 8 | 深流水（验证 2 后再调） |

**保守起步理由**：extent pin 数量增加 → arena 碎片风险；先 N=2 实测（探针 + 6 轮死亡谷复现），
数据好再升 4/8。

## 5. 风险与回退

| 风险 | 缓解 |
|---|---|
| arena 碎片（多 extent 同时 pin） | N 小步起步（2）；碎片降级逻辑已有（逐页回退） |
| 槽满时同步路径比例升高 | 监控 profile（sync fallback 计数） |
| 正确性（publish/drop 顺序） | 契约不变（drop 只在 publish 后）；RAII 逆序析构保持 |
| 最坏回退 | `DEPTH=1` = v2 行为；exe 回滚锚 `bak_v2_async_VERIFIED_20261011`（sha256 8FCA91461E299073） |
