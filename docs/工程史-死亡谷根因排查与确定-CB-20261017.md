## 0. 一句话结论

> **死亡谷的触发条件是「外部显存压力 ≥400 MiB + 引擎池贴边（自由显存 <400 MB）」；
> 机制定位为「host 侧 `program_submit` 每 round 慢 93×」（设备不忙、引擎自身零搬页）；
> 且已双向闭环：加压即塌、释放即复。**

## 3. 机制定位（reqlog 原件，字段级）

**每 round 的主机时间全部落在 `host_work.elapsed_seconds.program_submit`**：

```json
"decode_host_microseconds_per_round": 2463765,      ← 2.46 秒/round（健康 26,000）
"decode_device_wait_microseconds_per_round": 614.5,  ← 设备等待仅 0.6 ms
"elapsed_seconds": {
    "program_submit": 4.9266046,      ← 窗口内 4.93 秒全在这里
    "engine_boundary": 0.0000042, "engine_commit_output": 0.00055,
    "engine_maintenance": 0.0000266, "program_post": 0.00035, "total": 4.9275303
},
"work_class_seconds": { "decode_host": 4.9275303, "decode_device_wait": 0.001229 }
```

**排除表（全部实测）**：

| 候选 | 实测 | 判定 |
|---|---|---|
| 设备侧等待 | `device_wait` **0.35–0.6 ms，谷期与健康期相同** | ❌ 排除 |
| **引擎自身的搬页/驱逐** | **`d2h`=0 页 · `h2d`=0 页 · `actual_transfer_seconds`=0.0 · `spill_pages`=0 · `*_owners_evicted`=0** | ❌ **排除** |
| 准入策略 / 上下文推进 / 统计发布 | `detail_invocations` 全 0 · `detail_subset_seconds` ≈ 2.5e-05 s | ❌ 排除 |
| 主机内存/换页 | 主机空闲 88–89 GB · pagefile 用量极小 | ❌ 排除 |

**⇒ 修正后的机制表述**：
> **在外部显存压力下，引擎 host 侧的「程序提交」（`program_submit`）每 round 慢 93×；
> 设备不忙、引擎自身没有任何搬页 —— 瓶颈落在 host 提交路径里、且发生在引擎自身计数器看不见的位置（指向驱动层内存操作）。**

| 假说 | 何时提出 | 被什么推翻 |

## 6. 未闭合项（诚实标注，不得当结论）

1. **为什么 `program_submit` 会慢 93×** —— 候选：**驱动层分配/压缩竞争**（引擎计数器看不见）。
   要钉死需引擎内部计时（`NINFER_SPIN_STAMP_VERBOSE=1`）或 profiling ⇒ **需重启引擎**（119 h 栖息地会清零）。
2. **自然谷是"爬升"（92→472 ms，20 分钟）而实验是"阶跃"（27 ms → 2.4 s，一加压即到）** —— 差别未解释（可能是外压渐增 vs 突变，或存在第二因素）。

## 7. 解法与验证计划（**待用户批准**）

| 方案 | 做法 | 预期 | 验证 |
|---|---|---|---|
| **① 根治（推荐）** | **池 65536 → 51200** | 自由显存 **248 MB → ≈780 MB** ⇒ 离开贴边 | **E-C**：换池后跑**同一**重载请求，host/round 应保持 ~27 ms |
| ② 即时 | 关闭占显存程序 | ❌ **实测无效**：地板 ≈640 MB（dwm 173 + CodeBuddy 185 + msedgewebview2 98 + Overlay 77 + 系统）> 阈值 400 MB | 已实测（关 Edge/QQ/豆包均无效） |
| ③ 更保险 | 池再降 49152 | 留 ≥1 GB 余量 | 同 E-C |

**注意**：① 与"减少搬页"无关（**谷期零搬页**）—— 本质是**给驱动留出显存余量**。
