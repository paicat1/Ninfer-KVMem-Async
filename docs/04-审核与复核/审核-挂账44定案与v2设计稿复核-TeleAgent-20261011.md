### 2.2 ⚠️ 三个缺口（施工前需明确）

**缺口 A：请求正常终止时的 pending 收尾**
- 设计稿时序（2.2）只覆盖 decode 步循环（"下一步 ensure_ring_room 收割"）。
- 若请求正常结束（stop/output limit）后**无后续 decode 步**，pending 批挂着（extent pin 8 页 ≈ 20MB）直到下一请求。
- 需明确：收尾路径（建议请求收尾/事务结束处显式收割）或"留待下次"的语义 + 资源影响声明。

**缺口 B：序列/上下文释放（eviction）与 pending 的交互**
- pending 挂起期间若序列被释放/上下文被驱逐，pending 持有的页 handle 是否悬空？
- 需明确防线：释放路径先收割（或 synchronize），或论证 pin 保护充分（页被 pin 时不会被回收）。

**缺口 C：异常路径的完整语义**
- 设计稿 (e) 只写"析构兜底 synchronize + RAII 释 pin"。
- 但页的 `release_active_reference` 与 `drop_device_replica` 在异常路径的处置未写——是"完整收割"还是"保持可重试状态"？引用计数去向需明确。

### 2.3 表述修正建议
- 锚点 a："提交点处 compute 队列为空（demote 在步首）→ 等待瞬时零开销"——"等待瞬时"是**预期**而非必然；且 **prefill 路径**（prefill.cpp:690/1156/1246/1349 也调 ensure_ring_room）的队列状态需单独验证。建议改为"预期 ≈0，由 profile 验证；prefill/decode 两路径分别确认"。

### 2.4 验证计划补充建议
- 增加"收割等待时长"计时（验证"被 kernel 覆盖"假设）。
- 增加空转场景观测（请求结束后 pending 挂着时的行为）。
