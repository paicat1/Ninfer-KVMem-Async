## 四、跟踪方式

1. **每次大问题排查前**：先 `git fetch` Bonsai 线 + 翻 `docs/06-Bug手册.md` 新条目——**先看上游有没有解法，再闷头自己撞墙**；
2. **定期（每周）**：`HEAD..origin/main` 计数 + Bug 手册 diff 摘要；
3. **指代纪律**：禁用"官方"统称；说"Bonsai 线"、"兄弟件 RC2"、"NInfer 原始仓"、"tancau 环线"、"qw3 策略层"；
4. **上游解法入库路径**：Bonsai 线分析 → **与前作 P 系列对照去重合并**（同一修法两条线的各自落地）→ 对照本线实测 → 评估移植（env 级 > patch 级 > merge 级，按风险递增）→ 实测验证 → 构建史记档；
5. **本档维护**：谱系变化（新仓/新分支/新下游）时更新本文件 + 修订记录。
6. **上游跟进后必跑逐字门（2026-10-20 审核 M2）**：每次 cherry-pick / rebase / 跟进上游后，跑一次 `python scripts/verbatim_gate.py`（逐字一致门，8 提示），通过再合入——上游与本地 19 补丁同文件区变更时，这是唯一能兜住"静默语义漂移"的机器门。

### 6.4 关键 issue 动态与精读结论

**#101 · prefix reuse collapse（open；已精读全文+评论）**——
- **问题**：agent harness 每轮重写尾部消息（如 `Tool-call turn N of 100.`）→ role 翻转 → 最长公共前缀边界移动 → 最近 checkpoint 在边界**后一行**（off-by-one）→ selector 全清 → **每轮全量重算且自我锁定**；
- **实证**（同版本 A/B，`5d1ac0a` 编译两次）：105 尾改轮 prefill **1,349.4s → 139.8s（−89.6%）**、new rows 1,134,982 → 47,828、TTFT p50 13,156 → 1,347 ms；追加型轮零变化（对照）；反转顺序复现；代价 = 额外 checkpoint host 状态（peak 628→785 MB）；
- **修法**：`run_prefill_multimodal()` 单段 decode 拆两段，在已知相等边界留 checkpoint（数行 patch）；
- **对本线**：**代码修法不适用**（llama.cpp backend 血统，机制不同）；**可借鉴的是方法论**——①"每轮尾改 nudge"是**跨 harness 普遍模式**（作者称多个独立 harness 复现）；②回归测试设计（trace 判据：`no_recurrent_checkpoint` / `oldest_checkpoint − lcp = +1` / `prefix_hit_rows`）可仿制；③**家庭自查项**：本线 DSH 会话 cache% 是否出现"特定轮型骤降"（本线实测命中 97-100%，预计正常——以日志验证为准）；
- **精读附注**：其"同版本编译两次 A/B + 反转顺序"的科学方法与本线证据文化同构，可作探针设计范例。

**#113 · 工具调用偶尔失败（open，4 评论）**——
- 社区报告（10-08）：DSH 会话工具调用出错导致中断（畸形 `<tool_call>`）；workbuddy、pi 框架（0.18RC1）同现；**低占用时（20%+）即偶发**；

### 6.5 本线独有成果核查（"上游有没有想到异步页流水"）

**结论：在已审阅的全部上游材料范围内（Bonsai 线 23 提交 + docs/13/14 + tancau 全仓 + RC2/RC3 说明 + 主要 issues + 始祖/兄弟线近期提交），未发现"异步页流水"（页搬运与 decode 解耦流水）的同款实现。**

- Bonsai 线：B34 页漂移立案 + D-01 sink 缓解 + P-01..P-08 修法清单——**无搬运时序层改动**；
- tancau：最近的思想邻居 = **Phase 3（worker 隔离/分层 restore）——park 未实现**；其已完成的自噬修复（跳过 mid-ensure restore）是"减少无效页操作"（治 churn），非"搬运-解码并行"；其收官判定恰为 **"decode at wall"**（接受解码侧的物理墙）；
- kvmem-llama.cpp：RC3 分层（RAM/SSD = 存储**空间**维度）+ LRFU（淘汰策略）+ 明确声明"本次没有加入 decode 期间的持续 attention score 累积"——**无解耦流水机制**；
- iamwavecut / Neroued：structured-output / 约束解码 / 内核性能——非 KV 搬运域。

**诚实边界**：机制思想（异步 I/O / 流水线 / 脏页后台回写）在 OS 领域不新；本线贡献 = **在 NInfer/KVMem 引擎内的具体落地（PendingDemote + transfer stream + 次步收割 + 正确性契约）+ 全量实测（20-40 倍、E4 验证）**——就本生态而言，目前是**唯一实现 + 唯一实测数据**（回馈资本）。

**论文声称 vs 开源实现：三处重大分歧（代码级核对结果）**

| 机制 | 论文（QW3，私有，不可验证） | 开源 `kvmem/kvmem`（代码实锤） | 分歧 |
|---|---|---|---|
| **Raw K + re-RoPE** | 核心机制：去 RoPE raw K + 新位置重编码 + bounded delta | **`kvmem_store.hpp:10-11`：`Current native-payload execution keeps original RoPE positions; compact addresses do not rewrite K`**；`rope.hpp` 存在但 `:15-17` 注明 **“legacy set_selection 的 re-RoPE bookkeeping，不是 native transfer 契约”** | **论文做 re-RoPE，开源明确不做** |
| **Mean-K 检索** | 32-token 块、global softmax、索引驻 host | **`mean_key_retrieval.hpp`** 完整实现（Mean/Max 聚合、FP32 cosine、1e-6 epsilon）；但 **`raw_kv_store.hpp:33` 的 `block_tokens` 默认 128**，不是 32 | 实现有，**块粒度不同**（128 vs 32） |
| **频率感知淘汰** | Retrieval-aware（近期召回 + 累计频率，"优于纯 LRU"） | **`lrfu.hpp`**：LRFU 状态（scores / round / committed）+ `set_retrieval_scores`（`kvmem_store.cpp:243-249`） | **一致**（开源有 LRFU） |

**关键推论（修正 §8.3 的 P0）**：

- 论文的 re-RoPE 是**"紧凑重排执行视图"的代价**（位置变了必须重编码 K，论文自己承认"非数学等价"）；
- **开源实现选择了不重排**（保持原 RoPE 位置，`compact addresses do not rewrite K`）⇒ **不需要 re-RoPE，也没有重建误差**；
- **本线 restore 若为原字节搬回，与开源选择一致，是更保守正确的做法** ⇒ `#53` 分叉**不是 RoPE 问题**（除非本线确实做了重排，需读码确认）。

**发布口径**：

- ✅ "异步页流水是本线对 KVMem 同步搬运层的增量改造 + 全量 A/B 实测"
