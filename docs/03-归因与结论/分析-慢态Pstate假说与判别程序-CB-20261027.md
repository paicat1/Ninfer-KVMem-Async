## 一、既有实测锚点（构建史 L2460，2026-10-20 用户批"公断"）

> 慢轮 1 Hz 采样 = **SM 100% / 满频 2902 MHz / 功耗仅 63–98 W / 显存活动 4–19%**；快轮 = 129–217 W / 显存 64%。
> ⇒ 慢态 = **SM 烧时间不烧功率、不碰显存的忙等/自旋**；**排除降频（满频）、排除带宽（mem 低）、排除重算（功耗低）**。
> **机器/驱动层不是病灶（满速、无节流、纯核满性能）⇒ 退化是引擎图内行为**。

第二条独立证据（同节）：慢态引擎**饿死并行核 8×**（周期数恒定 ~1.06 M、墙钟 8×）⇒ 真实指令占用（自旋/长占用），非空闲等待。

**注意区分**：不是"显卡干等"（那会是 SM 空闲、util 低），而是 **GPU 满频执行自旋指令**。

## 二、现象分类：全域四带（**仅分析层标签**，判定优先级从上到下）

> **采样层 / 分析层分离**：采样层永远记**连续原始值**（clocks/power/mem 全量 CSV，无信息损失）；四带**只是事后分析的报告标签**，不是采样判据。慢态幅度是连续谱（123.8 / 27.4 / 1/25），离散化必然有边界样本——但原始值都在，边界样本永远可回溯、可重标。立案/触发一律用**相对降速**（连续量的函数），不用绝对带。

| 带 | 判据 | 含义 | 备注 |
|---|---|---|---|
| **F3 未升频** | `clocks.sm < 2000` | 时钟没升（v1 假说复活条件） | 目前**无证据**；要 1 Hz 采样才能排除 |
| **F4 带宽/重算** | `mem-util > 50%` **或** `power > 200 W` | 在跑真活（带宽或计算受限） | 双条件任一；与慢态无关（这是"健康的忙"） |
| **F1 自旋** | `clocks.sm ≥ 2600` **且** `power < 110 W` **且** `mem-util < 25%` | L2460 指纹：满频空转 | 深慢态（6–7×）的标准形态 |
| **F2 中带** | 其余（2000–2600 MHz / 110–200 W / 25–50% mem 的任意组合） | **部分自旋或轻度降速** | §174 的 **123.8（1.35×）疑似落此**，需实测归类 |

**全域性检查**：任意三相采样必落入且仅落入一带（F3→F4→F1→F2 顺序判定，先命中先归类）。
**阈值说明**：`clocks.sm ≥ 2600` 取"接近满频"而非固定 2902（boost 随温度负载浮动）；F4 的 `>50% mem` 与 `>200 W` 为**待标定初值**，首次发作后按实测调整。

## 五、捕捉方案（**仪器先于发作**）

### 5.1 机器态采样器（新增 `scripts/machine_state_sampler.ps1`）

- 1 Hz `nvidia-smi --query-gpu=timestamp,clocks.sm,clocks.mem,power.draw,utilization.gpu,utilization.memory,temperature.gpu,pcie.link.gen.current,pcie.link.width.current` → CSV
- **`clocks.mem` 是关键新增字段**：L2460 的"排除带宽"只看了 `utilization.memory`（请求量），**没看显存时钟**。若慢态时 `clocks.mem` 停在 810 MHz（P8）而非 ~15000 MHz（P0），则"显存活动 4–19%"不是"不读"，而是"读得极慢"——**这是一个完整的新解释，见 §5.5**
- **零 GPU 占用**，7×24 跑，可与 Y1'' 等任何实验并行
- **纯记录，无实时联动**：慢态发作瞬间不丢数据；是否启动守望者发探针，事后决定
- 文件命名：`.temp\machine_state_<yyyymmdd>.csv`

**自加密（1 Hz → 5 Hz × 30 s）双触发**：

1. **引擎侧通知（主）**：引擎实时知道自己掉速（`timings.predicted_per_second` 连续 N 步 > 基线 × 1.2 ⇒ 写 `.temp\slowdown.flag`）⇒ 采样器检测到 flag 即加密。**覆盖全谱（F1 与 F2 都能触发）、零误判**，采样器保持被动。
2. **采样器自查（兜底）**：`clocks.sm ≥ 2600 且 power < 110 W` ⇒ 加密（只覆盖 F1，作为引擎通知失效时的兜底）。

### 5.2 事后 join（不搞实时联动）

- 采样器 CSV（1 Hz）+ 引擎日志（`StepProfile=1` / `SPIN_STAMP_VERBOSE=1` / `demote profile step=`）按**时间戳** join
- §169 已确认：`step=` 落地后 logstat 可按 round 分段 ⇒ join 粒度到批
- **Y1'' 期间不挂守望者**：实验本身就是探针，机器态由采样器记录

### 5.3 慢态判据改良（双保险，替换 `decode < 60`）

| 条件 | 原判据 | 新判据 |
|---|---|---|
| 相对降速 | 无 | **> 20%**（对照"**当日 healthy 窗**"，不是当晚基线） |
| 绝对下限 | `decode < 60` | `decode < 90`（防中等降速漏检） |
| 组合 | —— | **相对降速 > 20% 且 decode < 90** 才立案 |

**基线双保险的原因**：慢态晚的"同配置基线"本身就是慢的（123.8 在慢态晚可能算"正常"）⇒ 必须用**当日最早的健康窗**或历史 P0 基线，否则相对降速被慢态基线稀释（§164 冷暖填互换教训的变体）。

### 5.4 发作时三张快照（跑中，不是跑前）

```powershell
# ① 形态
nvidia-smi --query-gpu=timestamp,clocks.sm,power.draw,utilization.gpu,utilization.memory,temperature.gpu --format=csv,noheader
# ② 链路（唯一未查的硬件层项）
nvidia-smi -q -d PCIE | Select-String 'Link Width|Link Speed'
# ③ 自旋定位（引擎侧）
#    NINFER_SPIN_STAMP_VERBOSE=1 + NINFER_STEP_PROFILE=1 已在起服 env
```

- ② 的意义：若链路从 `x16 Gen4` 掉到 `x8/Gen1`，host 提交会变慢 ⇒ 自旋时间放大，**根因在链路**（这是唯一可能归到"显卡层面"的项）
- ③ 的意义：定位自旋在"等 host 写入的标志"还是"等内部锁"——前者 → C1/C2，后者 → C3

### 5.5 "凉而慢"的解释空白与 `clocks.mem` 假说（v1 撤回后遗留）

P-state 撤回后，"凉而慢"（35–37℃ 反而慢、60℃ 反而快）**目前无任何解释**——uptime 已反向排除。剩余候选按"先能排除的"排序：

| # | 候选 | 判别 | 状态 |
|---|---|---|---|
| **M1** | **显存/PCIe 时钟未升**（`clocks.mem` 停在 P8 810 MHz） | 采样器 `clocks.mem` 字段（§5.1 已加） | **最可能**——冷态时显存时钟需暖机才升，SM 满频不代表 mem 满频；显存活动 4–19% 就可能是"读得极慢"而非"不读" |
| M2 | 冷态 PCIe 链路重训（Link Width/Speed 掉档） | `nvidia-smi -q -d PCIE` | 待测（§5.4 ②） |
| M3 | Windows 快速启动/休眠恢复后的驱动状态 | 驱动事件日志 + 对比"完整重启 vs 快速启动" | 待测 |
| M4 | 硬件接触类（凉缩接触不良） | 前三条排除后再议 | 最后 |

**若 M1 成立**，"凉而慢"有完整解释：冷态 ⇒ 显存时钟未升 ⇒ DMA/页搬运极慢 ⇒ kernel 自旋等数据 ⇒ SM 满频烧周期（63–98 W）、显存请求量低（4–19%）、墙钟放大 6–7×、输出 sha 不变。**与 L2460 全部观测相容，且不需要"引擎 bug"这个假设**。

## 六、#56 升级：restore 侧是主战场（不是"2.49% 不值得装"）

§174 N2 原文：`restore dev` 740 事件 / 总 10,227 ms / 均值 13.82 ms / **单次最大 64.01 ms**；`demote copy` 266 事件 / 547.6 ms / 均值 2.06 ms / 最大 7.52 ms。

- **单事件峰值 64 ms ≈ decode 步窗（27–32 ms）的 2 倍** ⇒ **一次 restore 爆发可独占两个 decode 步**
- 这是**尖峰问题**，不是稳态问题（均值 13.82 ms）
- #56 原结论"不装节奏器（2.49%<5%）"只算 demote 侧（3.4–7.8 ms/批）
- **升级后口径**：restore 侧存在**步窗 2 倍的单事件暴露**，结论反转预期显著 ⇒ 预取/节奏器在 restore 侧是**主战场**
- **尖峰对预取更敏感**：预取（提前搬、避开关键路径）优于节奏器（平滑）；内容打分器（`score`）已有，可直接给预取供"搬什么"

**路线图权重**（替换 §8.3）：restore 预取/节奏器 > demote 优化 > depth 调参。

**预取的三条设计边界**（否则会自我拆台）：

1. **池预算约束**：预取 = 把"将来要用的页"提前搬回 device，**占的是池空间**。超池场景池本就紧张 ⇒ 预取挤掉别的页 ⇒ 触发额外 demote。**预取窗口必须与池余量联动**（预取 N 页 ≤ 池余量 × 系数），且必须走 `ensure_ring_room` 同一裁决，不能绕过。
2. **净收益判定式**：`净收益 = 避免的步窗暴露 − 新增 demote 成本`。若预取导致 demote 点火数上升超过阈值，净收益可能为负——**预取不是免费的搬运前移，是"用池空间换时间"的交易**。
3. **预取优先级**：按内容打分（`score`）从高到低，只预取**命中概率最高**的 N 页；低分页不预取（避免无效占池）。

**⚠ 权重 ≠ 执行顺序**：上表是**价值排序**，不是实机夜的执行顺序。预取依赖"页需求估计器"（供"搬什么"），估计器还没建；实际执行顺序仍是：**深载分档最小版 → profile 双侧归因 → #33 → 估计器 → 预取**。

## 6b、捕捉三级递进与止损条款

慢态触发条件未知（时窗支配、凉慢热快反直觉）⇒ 不能一上来就"主动复现"，按三级递进：

**① 短期（零机时，现在就能做）：两晚差异清单**

§167 两晚的**全部环境差异**枚举——uptime（已反向排除）、当日 GPU 累计负载、驱动事件日志（含 TDR/重置）、后台进程集、Windows 更新/扫描任务、"凉"的可操作定义（停机时长？环境温度？风扇曲线？）。两晚对照只有一对，但**差异项枚举是零成本的**，可能直接浮出候选变量。

**② 中期（半主动复现）：预冷实验**

若"凉"浮出为候选 ⇒ 人为制造：GPU 预冷到环境温度后**立即**跑同负载，一次实验即可验证"凉 ⇒ 慢"是相关还是因果。这是最接近"主动复现"的低成本路径。**前提**：`clocks.mem` 字段已上线（§5.1），否则分不清"凉"影响的是 SM 还是 mem 时钟。

**③ 长期（采样器复利）：前兆模式**

采样器 7×24 跑起来后，每次发作都留下**发作前 N 分钟的连续环境曲线**——发作 3–5 次后，前兆模式（若有）会从数据里浮出来。"等发作"升级为"预测发作"。

**止损条款（防无限吞机时）**：3–5 次发作后仍无前兆模式、人工触发（预冷/外压/贴边）也失败 ⇒ **接受"等发作"为唯一路径**，慢态研究降为**采样器旁路的长尾任务**——不阻塞 Y1''/Y2（它们在健康窗跑，慢态数据旁路收集）。
