> 参与方：家里实机 / TELE 云端 / TELE 台式机 / LUMMY / 办公室

## 〇、摘要（五句）

1. **§238 把嫌疑收敛到引擎内部**：受控 A/B 下 OS 未逐出（pagefile 712 MB 不动、引擎页零写出），真实会话 265–472 token 小追加仍复现 **TTFT 17.5–24.2 s / silent 2–3**。
2. **`SCORE_BUDGET` 是「窗口覆盖」，不是「扫描量」也不是「搬页量」**：它决定 kept 候选集，**再被 ring 的 restore 预算二次截断**（`context.cpp` L1754-1755「The ring's restore budget is smaller than the selector's own budget, so the kept set is ranked again here and cut to `budget`」、L1779 `if (ranked.size() > budget) ranked.resize(budget)`）。
3. **⇒ 每轮真正搬的页数由 `NINFER_KV_RETRIEVE` 封顶（现役 512 页），与 `SCORE_BUDGET` 无关** —— 所以 A1/A2 都不可能改变静默段，**参数层无解**。
4. **量级对得上「逐页拷贝」而不是带宽**：512 页 × 20–30 ms ≈ 10–15 s；而 512 页 ≈ 800 MB，走 PCIe 只要几十毫秒。**⇒ 每页一次 ms 级开销**，且 `pageable` 内存的 `cudaMemcpyAsync` 会被驱动**逐笔 staging 串行化**（`arena.cu` L629-633 注释：pageable 走 bounce buffer，不能真正异步）。
5. **唯一判别实验 A3**：`NINFER_KV_RETRIEVE` 32768 → 16384（512 → 256 页），预期静默段**近似减半**（10–15 s → 5–8 s）。线性成立 ⇒ 每页固定开销实锤，修法=**按 extent 合并拷贝**；不线性 ⇒ 转 ①（chunk 尾 sync）/ mask O(n)。

## 一、三层成本分类

| 层 | 成本 | 是否可消除 | 证据 |
|---|---|---|---|
| **① chunk 尾同步** | 每 prefill chunk 一次 `cudaStreamSynchronize` | 可（异步化 / 延迟一轮） | `kvmem_score.h` L493；`text.cpp` L1877-1878 |
| **② 每页固定开销** | restore 512 页，每页一次提交/staging | **可**（extent 合并 / pinned staging） | `context.cpp` L1628-1635（已在 transfer stream 上批量提交）＋`arena.cu` L629-633（pageable 走 bounce buffer） |
| **③ 物理必需** | 本步要算的页必须在设备上 | 不可 | `context.cpp` L3058「The mask IS the resident set」 |

**⇒ 10–15 s 落在 ②**，量级来自「页数 × 每页开销」，不是带宽，也不是评分路径（D2H ≤16 KB）。

## 二、参数层的三个死结（都实测过，别再试）

### 2.1 `SCORE_BUDGET` 不能回退

`evidence/repro/kv_window_matrix_28k_80k.md` L31-37：

> 默认 32768 → `budget_blocks=512` → 42,276 prompt 下 **149 个块（9,536 token）被丢弃**；65536 → skip 归零；131072 → 2,048 块，80,385 仍 skip=0。跨 28K–80K 共 6 次运行 skip 恒 0。

`ninfer_launcher.py` L400-403 同结论。**回退 = 重演 11-14 已修的丢块缺陷。**

### 2.2 上调 `SCORE_BUDGET` 也无效（台式机 catch，成立但理由要换）

- 台式机说「kept 上限 = min(budget, 池页数)」，**代码里没有这个 min**：`kvmem_select_blocks` 只吃 `total_blocks/budget/sink/recent`，不认识池。
- 但**结论仍然成立**，真正的原因是**二次截断**：`context.cpp` L1774-1779 把 kept 按分数重排后 `resize(budget)`，而这里的 `budget` 是 **ring 的 restore 预算**（`NINFER_KV_RETRIEVE`，现役 512 页），**与 `SCORE_BUDGET` 无关**。
- **⇒ budget 2,048 → 4,096 不改变 restore 页数**：`preferred` 依旧是 ≤512。A1 是无效实验，且**不会 FATAL**（v4 写的「池装不下会 FATAL」不对，窗口被截断而非报错）。

### 2.3 下调 `SCORE_BUDGET` 同样无效

kept 变小不会让 restore 小于 512 页——restore 预算本来就只有 512；只是把**可选内容**变窄（丢块风险）。**⇒ A1/A2 双向死。**

### 2.4 三层参数各归各位（收敛表）

| 参数 | 控制什么 | 现役值 | 能否改静默段 |
|---|---|---|---|
| `SCORE_BUDGET` | kept **候选集**（覆盖 / 召回质量） | 2,048 块 | ❌（被二次截断） |
| `NINFER_KV_RETRIEVE` | **每轮实际搬回页数**（封顶） | 512 页 | ✅（唯一杠杆） |
| `--kv-capacity`（池） | 驻留上限与 demote 压力 | 1,728–1,984 页 | ⚠ 只能降上下文，16 GB 装不下 200K |

### 2.5 机制补强：demote 是批量，restore 是逐页

`context.cpp` L1631-1632 原文：

> **The demote side already batches; restore was the remaining serial page path.** Fix: issue every page copy on transfer_streams …

**⇒ 同是约 800 MB：**

```
demote（批量大块连续）      ⇒ publish 0.79 GiB 与 adopt 同秒完成（GB/s 级）
restore（每页一笔 + pageable bounce buffer 逐笔 staging） ⇒ 512 × 20–30 ms ≈ 10–15 s
```

这解释了此前一直没对上的矛盾（§234：快轮 publish 与 adopt 同秒，慢态 restore 却要十几秒）。**C 步「extent 合并」= 把 restore 也 publish 化**，预期回到亚秒级。

### 2.6 content scoring 的历史脉络（recall 门的史前史）

`context.cpp` L1747-1752 注释：content scoring 是 **2026-10-02 本地添加**，动机是词法路径的已测缺陷——

> 「the lexical dependence is the measured defect: a question that is semantically the same but lexically disjoint **lost the mid-prompt needle in 2 of 6 trials**」

**⇒ 三条推论**：

1. `recall@budget` 不是新发明——它的需求在 10-02 就有实测（中段长程内容受词法选择影响；短程强模板如 JSON 不受影响，这就是 §177 三档全同的原因）。
2. `SCORE=0 / 1` 的 2.17× 不是引擎性能差，是**两种选页策略 → 不同上下文可见性 → 模型行为差异**（copy 轮有无），与 §199 修正⑦ 同源。
3. 任何「降覆盖换速度」的实验（含 A3），**必须同时报 recall**，否则无法区分「修好了」与「换了个行为」。

## 三、修正后的判别实验（A0 → A3）

| 步 | 动作 | 成本 | 预注册判据 |
|---|---|---|---|
| **A0** | 读已有日志：`kvmem_score: KEPT`（`skip`/`selected`）、`ring retrieve: preferred= restored=`、`mask hidden:` | **0** | `restored` 是否稳定 ≈ `NINFER_KV_RETRIEVE/64 = 512`；`skip` 只是覆盖差，不是搬页量 |
| **A3** | **`NINFER_KV_RETRIEVE` 32768 → 16384（512→256 页）**，同会话复测小追加 | 10 分钟 | **静默段近似减半（10–15 s → 5–8 s）⇒ 每页固定开销实锤**；不变 ⇒ ② 排除，转 ①/mask。<br>**第二观测（台式机补）**：静默段是否**跨请求累积**——若每轮需求 >256 页，被截掉的页跨轮参与排名/搬运，可能出现「首请求 5–8 s、后续递增」；出现则线性检验按**总搬页量**算，不按单请求 |
| **A4** | 反向：16384 → 32768 复原，确认可逆 | 5 分钟 | 静默段回到 10–15 s ⇒ 线性关系闭合 |
| **B** | `NINFER_DEMOTE_PROFILE=1` + 每页/每段墙钟 | 半天 | 定位到 `restore` 内部（提交 / staging / publish） |
| **C** | 改 `restore_kv_pages_from_host`：按 **host 连续 extent 合并**成一次大拷贝（pinned staging 池），减少提交次数 | 1–2 天 | 同会话 TTFT ≤3 s、逐字门 8/8、池上限不变 |

**为什么 A3 比 A1 强**：A3 直接在**被怀疑的那一维**（页数）上做线性检验，结果只有两种，都能推进；A1 在不被消费的参数上做文章，跑完无论如何都是「无变化」，等于白跑。

## 四、修法：合并 extent，不是加带宽

```
现状（推断）：per-page  cudaMemcpyAsync(pageable)  → 驱动逐笔 staging → 每页 ms 级
修法：按 host arena 的连续 run 合并 —— 一段 N 页 = 一次拷贝
      （HostKVArena 是扁平缓冲，页偏移连续；非连续时退回逐页）
预期：512 次提交 → 数十次；10–15 s → 亚秒级
```

**风险**：`restore` 的取消检查点（`decode_cancelled()`，L1638-1642）是按页粒度的——合并后要保证「取消仍是页边界安全」，否则会把部分页写进半成品状态。现成的安全契约是「未搬回的页不进 mask」，合并后必须保持这条。

## 六、归属与收益评估

### 6.1 三分归属：谁该为这 10–15 s 负责

| 成分 | 归属 | 依据 |
|---|---|---|
| 按页管理 + 按页恢复 | **KVMem 架构固有** | 页是 KVMem 最小管理单位；分层 KV 要「装得下」，必然有「装不下的页搬回来」这一步。上游参考实现同样逐页 |
| **demote 批量了、restore 没批量** | **一半是我们** | `context.cpp` L1628 自述：10-12 的修复只把 restore「挪到 transfer stream」，**没合并提交**；demote 侧早已批量 ⇒ 不对称，非设计必然 |
| **pageable 而非 pinned** | **我们自己选的（被迫）** | `program_impl.cpp` L400-407 / `arena.cu` L636-648：pinned 被 WDDM 按显卡计费，16 GiB 直接吃满 16 GB 卡；代价是 bounce buffer 逐笔暂存 = **Windows 特有税** |
| 池贴顶 + 200K 会话 | **用法把架构推到极限** | 池 1,984 页 vs 200K 会话 3,130 块 ⇒ 每轮恒有上千块在 host；不是 bug，是「16 GB 跑 256K」的必然代价 |
| `SCORE_BUDGET` / 判据 A 的误判 | **流程问题（已修正）** | 把「窗口容量」当「打分量」，差点建议回退 131072（会重演 11-14 丢块缺陷） |

**⇒ 不是 KVMem 天生有缺陷，也不是我们改坏了：一个「按页」的架构，跑在一条「按笔收费」的内存路径上，而恢复侧还停在逐页提交。**

### 6.2 修好之后能实现什么

| 指标 | 现在 | 修好后（预期） |
|---|---|---|
| 小追加 TTFT（265–472 token） | **17.5–24.2 s** | **2–3 s**（800 MB 走 PCIe ≈ 70 ms + 数十次提交） |
| 静默段 | 10–15 s × 2–3 段 | ≈0（不再进 `silent` 判据） |
| 长会话体感 | 每轮「卡一下」 | 与短会话一致 |

**三条连带收益**：

1. **慢态判据变干净**——以后测 OS 逐出/机器态，不再被「每轮十几秒」混淆（§236 已经吃过一次判据污染的亏）。
2. **`KV_RETRIEVE` 可上探 1,024 页**——§233 想要但被时间/显存否掉的方向重新打开，召回质量与吞吐同时松绑。
3. **超池从「应急」变「可用」**——200K 上下文的实际可用性提升一档。

**边界（必须一起写）**：**搬页量本身消不掉**。池装不下的页，每次要算就得搬；C 步消的是「每页固定开销」，不是「页数」。若要连量都消掉，只有降上下文——16 GB 装不下 200K 工作集，这是物理。
