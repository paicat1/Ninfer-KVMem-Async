用已有 11 小时采样（`baselines/valley-20261016/windowwatch_20261016_1237.txt`，642 行）做对齐分析，得到：

| 指标 | 谷档中位（decode<60, n=72） | 健康中位（decode≥100, n=10） |
|---|---|---|
| **GPU 功耗** | **63.6 W** | **214.8 W** |
| GPU util | 100% | 99% |
| GPU 时钟 | 2910 MHz | 2865 MHz |
| 显存占用 | 15,827 MiB | 15,749 MiB |

⇒ **util 与时钟几乎不区分（都在顶格），功耗才是判别量**。候选判据的判别力（以引擎日志 decode 为真值）：

| 候选判据 | 召回 | 精确率 |
|---|---|---|
| **功耗 < 100 W（且引擎在活动：日志有新行）** | **97%（70/72）** | **97%（误报健康 2）** |
| 功耗 < 100 且 util ≥ 90 | 62% | 100% |
| util ≥ 90 | 65% | 85% |

**意义（直击猎人 v2 的高-1 意见）**：
- **检测谷不再需要发探针** ⇒ 观察者的"我方活动"降到接近零 ⇒ **自诱导混淆可被设计性隔离**；

## 3. 实验设计（预登记，判据先写死）

### E1 · 被动长跑基线（**夜班可执行，零扰动**）

- **目的**：① 复核被动指纹在**无探针**条件下的误报率；② 记录自然谷的自然发生率；③ 为 E3 提供"低我方活动"臂。
- **⚠ 原设计错误（2026-10-17 03:1x 修正，用户指出）**：初稿写"不发探针、只采样"——**这是空转**：谷只在**有负载**时显现，不发请求则引擎 idle，**构造上不可能进谷**，该设计零信息。已改为下面的**定频计量驱动**。
- **方法（修正后）**：引擎保持现状（**已在跑**，起服 10-16 20:50）；**定频计量驱动 ＝ `scripts/valley_hunter.ps1`**：**固定 1 发/分钟、参数恒定**（filler 45 KB / max-tokens 200），既当诱饵又当测量；同时 `window_watch.py` 采样（只读）。**不注入压力、不改配置、不重启**。
- **预登记判据**：
  - **谷** = 采样行 `gpu util ≥ 90%` **且** `功耗 < 100 W` **且** 引擎日志在该分钟有新行（证明在处理请求）；
  - **idle** = 日志无新行（既不算谷也不算健康，单独记）；
  - **健康** = util ≥ 90% 且 功耗 ≥ 150 W。
- **时长**：≥ 6 h（覆盖用户睡眠时段）。
- **产出**：误报率、自然谷发生率（若有）、窗内/窗外的系统面对照 —— 全部落 `baselines/`。

### E2 · 时窗开合条件【**需在场**】

- **目的**：判定"窗"是时间、状态还是事件驱动。
- **方法**：密集采样（1/分钟）+ **事件对齐表**（我方事件：起服/重启/PDL 切换/长上下文门测/构建/桌面占用；机器侧事件：功耗基线、时钟、freemem、pagefile、CPU、其他进程显存）+ **窗内/窗外各 ≥3 次同剂量施加**（如 1200 MiB × 240 s）。
  （TELE 首轮意见③：原“各一组”样本不足，已提为 ≥3 次。）
- **预登记判据**：
  - 支持"**窗=状态**"：同剂量在窗内得深档（decode<10）、窗外得谷档（10–60），且可复现 ≥2 次；
  - 支持"**非确定性**"：同剂量深度随机分布，与窗无关；
  - 支持"**事件驱动**"：窗边界与某一类事件对齐（±2 分钟内），且 ≥2 次独立窗均对齐。
- **禁止**：为多抓而加负载；案发期间重启。

### E3 · 自诱导分离 A–B【**需在场**】

- **目的**：把"引擎连续运行时长"与"我方活动密度"两个变量分开（第二号未解）。
- **方法**：**等长交叉对照**，**两臂只差“探针频率”一个变量**（TELE 首轮意见③：其余全部锁死 —— 同样的采样节奏、**期间不做构建/不起压力工具/不改配置**，否则又引入混淆）：A 臂 = 探针 1/分钟；B 臂 = 探针 0（纯被动采样）。**每臂 3 h，顺序 ABAB**。
- **预登记判据**：分别计算谷/深档次数与 ①引擎 uptime ②我方活动事件数 的相关；**只有一臂出现谷 ⇒ 该变量是主因**；两臂都出现 ⇒ 需第三变量。
- **这是唯一能把两条假设分开的设计**（此前 A 组 180 min 零谷对两假说同等兼容，不能选择性引用）。

### E4 · 驱动侧证据采集【**需在场**】

- **目的**：为对外求助/驱动侧定位准备可提交材料（第三号未解）。
- **方法**：谷期 vs 健康期各抓一组：`nvidia-smi -q`（**throttle reasons / 时钟 / PCIe / 功耗上限**）+ Windows 事件（Kernel-PnP / Display / WDDM）+ 引擎四层读数 + reqlog 状态位，**并补 SM 时钟与内存带宽两列**（TELE 首轮意见③：防 throttle 全为 Not Active 时缺直接证据）。
- **判据**：至少找到 **1 项在驱动侧可列的差异**（否则对外求助材料不成立）。

## 4. 执行纪律（照既有铁律）

1. **先冻结、后取证**：命中谷后禁止重启 / 改配置 / 清缓存；
2. **只加"测"、不加"压"**：压力类一律走三级申请（E2 的施加属【需在场】且需用户批准）；
3. **零破坏**：探针 ≤1 发/分钟（E1 为 0 发）；日志帽 500 MB；
4. **不冤枉一次**：判据连续确认制；宁慢十秒；**预登记排除「起步前两探」**——空闲后首发本就慢（实测 #1 decode 23–29、功耗 ~95 W，与谷指纹同形），属冷启动而非谷 ⇒ 不计入 streak；
5. **自活动时间线**：每个案卷都要记"案发时我们自己在干什么"（含采集脚本自身）。
6. **★"我方活动"口径修正（2026-10-17 03:1x）**：**定频驱动是可控基线负载，不算混淆**——它节奏恒定、参数固定、逐发留痕，等价于"给引擎加了一个已知的背景负载"。
   **真正的混淆源是"非定频工具活动"**：构建 / 编译 / 压力工具（vram_hold、memhold）/ 桌面占用变化 / 重启 / PDL 切换。
   ⇒ **分析时以"工具事件"为自变量**，不以"请求数"为自变量；案卷的自活动时间线里，定频驱动单独标记一类，与工具事件分开统计。

## 8. 判据 v2：**相对基线**（2026-10-17 06:2x 预登记，**取代 v1 的绝对 100 W**）——回应 TELE 第四轮

### 8.1 为什么必须改（两条实证）

1. **IDLE BASELINE 跨批次漂移**（TELE 第四轮实测，同一引擎 22808 **未重启**）：
   `060439` 批次 = **660 MHz / 2% / 21.68 W**；`061800` 批次 = **1770 MHz / 30% / 30.94 W**
   ⇒ 时钟 **2.7×**、util **15×**、功耗 **1.4×** —— 不是采样噪声，是**机器态空闲基座自身在漂移**。
2. **probe#7 分歧行**：`decode=39`（谷档量级）但 `power=109.31 W` ⇒ v1 绝对门槛 100 W **漏判**。

⇒ **绝对阈值会被基座漂移带偏**：21.68 W 的基底下算出的绝对阈值，放到 30.94 W 的基底上就会误判。

### 8.2 判据 v2（写死）

- 主判据（不变）：**a2gate 口径的 `decode < 60`**（⚠ 不是引擎 throughput 行的 `decode_win5s`，两者差 ~4 倍）；
- 辅证（**v2 相对基线**）：`util ≥ 90%` 且 **`power < thr_rel`**，其中

  **`thr_rel = idleBase + 0.5 × (healthyRef − idleBase)`**
