## 一、🔴 判据逻辑修正（最重要——单发测试无法分离 H1/H2）

**问题**：测试请求**同时具备** H1 特征（深超池+长输出）与 H2 背景（贴边态保持——引擎未重启、显存贴边依旧）⇒ 原判据"慢⇒支持 H2 / 快⇒证伪 H2"的映射**不成立**（慢时两者共在无法归因；快时连 H1 也没被验证）。

**修正（先写死）**：

| 观测（深请求） | 正确解读 |
|---|---|
| **慢**（decode <30 且 host ≈100%，稳态 ≥5 min） | ⇒ **复现成功**（"贴边态+深超池+长输出"组合充分致慢）——**H1/H2 未分离**（两者共在） |
| **快**（decode ≥150 且 host <40%） | ⇒ **复现失败**（该组合不充分）⇒ 29min 谷存在**第三变量**（请求构造差异/长会话历史/其他）⇒ 下轮查差异 |
| 中间态 | 记录为"部分谷"，不下结论 |

**加"浅请求对照"（低成本分离 H2——当前窗口能做到的最强设计）**：
- 贴边态下先发**浅请求**（浅上下文 + 短输出，~30s 级）：
  - **浅也慢** ⇒ 机器态致慢的**直接证据**（H2 强支持——与请求深浅无关）
  - **浅快** ⇒ 机器态本身不致慢 ⇒ 慢与"深超池"相关（H1 方向）
- **顺序：热身 → 浅对照 → 深主测**（浅的做贴边态基线对照；腾显存去 H2 需重启/关程序，不可得——此为窗口内上限）

## 二、执行要点补强（5 处）

1. **热身请求（防 C12 混淆）**：主测前先发一个几十 token 最小请求——"长时间空闲后首请求"是已知 C12 挂死场景；热身承担该风险（若热身挂死 ⇒ 识别为 **C12 非谷**，停止并报告）；深池请求在"非首请求"状态下发（单变量更干净）。
2. **深超池构造写死**：**单发一次性超长输入**（>131k token，用项目文档固定拼接、可复现），`max_tokens ≥2000`（29min 谷实际输出约 1.7 万——2000 为稳态观测窗，**注明**）；**与谷请求的构造差异记入分析**（谷发生在长会话中段，可能为累积型；单次型 vs 累积型之别）。
3. **分段观测**：**TTFT** · prefill 段（吞吐/host%）· decode 段（decode/host%/power/clk/util/ring retrieve/waiting）· 自由显存——**prefill 与 decode 分开判读**（29min 谷的 host 100% 是 decode 稳态）。
4. **停止/放弃/提前终止**（原预登记缺失）：
   - 总超时 **60 分钟**（prefill 5–25 min + decode 视速）未完成 ⇒ 放弃 + 记录；
   - 慢态稳态已观察 **≥5 分钟** ⇒ 核心数据到手，**可提前终止**（终止动作记入记录）；
   - 疑似挂死（进程在、零输出 ≥5 分钟）⇒ 停止、保护现场、报告用户——**不自动重启**。
5. **加发规则（n=2）**：首发后**无论快慢加发一发**（快⇒复验"复现失败"；慢⇒确认"复现成功"）——n=1 不下定论（项目纪律）；**加发若遇测试中新谷新锁**，按 §三 语义澄清执行（重载请求不属 pressure injection）。
