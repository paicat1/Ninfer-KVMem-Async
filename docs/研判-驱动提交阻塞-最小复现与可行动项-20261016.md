# 研判：死亡谷＝**host 侧提交在驱动里被阻塞**（最小复现 + 可行动项）

- 作者：CodeBuddy（家里线）· 日期：2026-10-16 04:0x · 状态：**待 TELE 审 / 可对外**
- 依据：`夜研-1`/`夜研-2`/`夜报-20261016`（本仓 docs/）+ `.temp\` 全部台账（含轮转件）
- **本件的用途**：把今晚的机制收敛结果整理成**别人能照做的最小复现**与**可行动项**，供上游/驱动侧研判

---

## 一、一句话结论

> 「死亡谷」期间，引擎的**整轮时间全部花在 host 侧的 CUDA 提交调用里**（`submit ≈ wall`、`wait = sync ≈ 0`；自然 3286 条 + 按需 6 条），
> 而**外部进程的 GPU 核 / 宿主页拷贝 / 驱动节流全部正常** ⇒ **卡点在"引擎进程自己的提交路径"**，
> 且该状态**可由外部显存压力按需复现、释放即恢复**。

---

## 二、最小复现（3 步，~2 分钟）

```powershell
# 前提：引擎跑在显存边缘（本机：16,303 MiB 卡，引擎常驻 ~14.3–15.7 GiB）
# ① 健康基线
python scripts\a2gate.py --arm base  --port 8094 --runs 1 --rounds 1 --filler-kb 45 --max-tokens 200   # decode ~160-170
# ② 从另一个进程占住 1200 MiB 显存（持续 40-240 秒）
tools\vram_hold.exe 1200 240
# ③ 施加期内再探
python scripts\a2gate.py --arm press --port 8094 --runs 1 --rounds 1 --filler-kb 45 --max-tokens 200   # decode 3.6–14
# ④ 释放后（进程退出）再探
python scripts\a2gate.py --arm post  --port 8094 --runs 1 --rounds 1 --filler-kb 45 --max-tokens 200   # 立刻回到 160–168
```

**观察要点（判据）**：
| 读数 | 期望 |
|---|---|
| 施加期内 decode | **3.6–14**（健康 160–170） |
| 施加期内 `step profile slow` | **`submit ≈ wall`**、`wait=0`、`sync=0`（本仓日志格式） |
| 施加期内 GPU | `util 99 %` 但**功耗仅 ~109 W**（健康 ~271 W）· 节流位 **Not Active** |
| 释放后 | **立刻**恢复（163–168） |

**饱和与阈值**：外部新增显存需求 **200 MiB ⇒ 0/9 慢**；**400–600 MiB ⇒ 每次恰好 1 个深慢探**；**≥400 MiB 持续 4–5 分钟 ⇒ 全程 100 % 慢（decode 1.5）**。**阈值与引擎当时的空闲显存无关**（905 MiB 余量下 400 MiB 仍触发）。

## 三、证据要点（可回原件核）

| 结论 | 证据 |
|---|---|
| 时间全在 host 提交 | `decode.cpp:172-175` 定义 `submit/wait/post`；3286 条慢轮 `submit≈launch≈wall`、`wait=sync=0`；按需谷 6 条同型（`wall=685.9 submit=685.9`） |

| **非**引擎显存足迹 | 池 65536/49152/32768 交错重测**无一致排序** |

## 四、可行动项（给上游/驱动侧）

1. **定位"提交阻塞"的具体驱动路径**：在 `cudaLaunchKernel`/流提交处阻塞数秒，典型成因是 **WDDM 的显存管理（驱逐/回迁/分页）**——需要驱动侧日志（WDDM 事件、`GPU 引擎`/`本地适配器内存` 计数器）确认；
2. **引擎侧自保**：树里已有 `planning\pressure.cpp`（压力⇒复用宿主页）；实测**第一次压力后引擎常驻缩 ~1.1 GB 并保持** ⇒ 该策略**确实动手了**。可评估：
   - 受压时**主动、可控地**释放/迁移哪些页（而不是让驱动隐式驱逐）；
   - 或在提交前**预热/回迁**关键页，避免"第一次提交撞上分页"；
3. **运行建议（生产）**：**避免与引擎争抢显存**（本轮唯一确证有效的缓解）；引擎侧无有效旋钮（池大小、host 页档位、PDL 均否）；
4. **若要继续深挖**：需要**每进程显存/分页计数**（WDDM 不提供；可用 ETW/GPUView 或驱动侧计数代替）——这是"驱逐"假设未证的原因（本仓 `夜研-2` §15 已如实记录）。

## 五、诚实边界（未证/未解）

- **"驱动驱逐"未证**（第一遍像、第二遍不像；WDDM 无每进程显存）；
- **自然窗口谷的触发源未找到**（1 分钟粒度显存对照为负；需要 1 s 粒度 + 探针，但需用户授权"探针节奏"）；
- **按需谷与自然窗口谷是否同一机制**：强相关未证（按需 decode 6.7–7.9 vs 自然 17–40）；
- **深谷 1.5–2.5 s** 与按需谷的关系：方向一致、幅度差 ~100×，未证；
- **C12（空闲后首请求永久挂死）**：2×2（≤25 min 空闲 × 显存压力）**四格全否**，机制未知。
