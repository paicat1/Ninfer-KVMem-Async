# 网络调研：视觉塔与 MTP 显存动态调换——先例与原理

- 调研日期：2026-10-12（纯网络检索；未动任何工程文件/未执行 git）
- 场景：RTX 5080 16GB · 自编 NInfer 引擎（Bonsai 线 fork，含 Design C）· Qwen3.8-27B 嫁接件（视觉塔 282 MiB；MTP 头 ~239 MB）· KVMem 融合线
- 目标：为"视觉塔 ↔ MTP 头显存时分复用 / 按需加载"做可行性前置调研（先查先例，再决定自研）
- 标注约定：**【官方原文】**=上游/官方 README·docs 原文；**【PR/issue】**=仓库讨论原文；**【实测】**=原文报告的数据；**【调研者推断】**=本文推断；**【未找到】**=检索未获。本地工作区证据单独标注（"本地"）。
- 检索避障备注：vLLM 官方文档站两次 429（改用 GitHub raw 源取得原文）；知乎帖 403（仅存检索摘要）；NInfer issue #73 第 3 次抓取成功。所有数字均转引原文，未复核原始脚本。

## 一句话结论

**你要做的事，NInfer 生态里已经有人完整做过并实测过——名字叫 "on-demand vision residency (overlay)"**：视觉塔常驻锁页主机内存，每张图开启一个有界"窗口"从设备显存借用（优先零拷贝借空闲 KV 页、可与 decode 并行；不够则临时驱逐 MTP head / draft head / embedding / lm_head 等只读文本权重，毫秒级驱逐与恢复、CUDA graph 不失效），窗口结束归还——本质就是"视觉塔与 MTP 头显存时分复用"的工程化实现。该能力经 `ashalliants/ninfer-3090#8` 合入 fork 生态，且（据本地交接文档）已存在于你自编引擎的旗标面（`--vision-residency resident|overlay|cpu`）；但它**未合入 Neroued 上游主线、且仅 Linux/sm_86 实测过、Windows 未测**。→ **第一步应是在本机实测 overlay 旗标，而不是自研**。其余生态（llama.cpp / vLLM / SGLang / TRT-LLM / Ollama / LM Studio）**没有**等价的"组件按需换入换出"；最接近的是静态选卡（`--mmproj-device`）、模型级装卸（sleep / router / keep_alive）、适配器级动态装卸（LoRA API）、架构级编码器分离（EPD）。

## §1 生态内先例（NInfer / llama.cpp / KVMem 系）

### 1.1 NInfer 上游（Neroued/ninfer 始祖）：固定驻留，官方没有运行时切换

- 【官方原文】README（https://github.com/Neroued/ninfer）：**"GPU residency is fixed at process startup.** `--spec` selects speculative decoding residency, and `--vision` independently selects Vision residency."；产品边界明确列出 **"no priority/QoS, weight offload, multi-GPU, or distributed serving"**；"Explicit capacities remain fixed for the process lifetime."
- 【官方原文】`docs/cli.md`（raw master，2026-10-12 抓取）：**没有** `--vision-residency`、`--vision-cpu`、`--vision-max-merged`；有 `--vision`（"enable image/video input and load Vision GPU allocations"）；关键句：**"These choices are not lazy loading: an Engine started without Vision rejects media and cannot enable Vision later."**；"Vision, MTP and DFlash follow the same rule: their weights are required only when that component is enabled at startup."
- 【官方原文】commit `fc5c483` "perf(vision): reclaim transient workspace memory"：把独立的 request-transient arena 并入统一 workspace（item 输出 handoff 由 `[8192,V]` 改为 `[5120,V]`；单 item 上限 16,384 token；聚合 prompt 预算仍 32,768）——**这正是上游判定 overlay"不值得合入"的直接原因**（缩小了 vision 常驻开销）。
- 【调研者推断】上游主线没有、也不打算提供运行时 residency 切换；"fixed at startup" 是官方口径；overlay 属于 fork 特性。

### 1.2 核心先例：on-demand vision residency (overlay) 全链（作者 iamwavecut；四个节点）

**① 设计文档：Neroued/ninfer issue #74**（"Design: on-demand vision residency (overlay) — retrospective for #72"，2026-08-21 创建；08-29 由维护者关闭为 completed。https://github.com/Neroued/ninfer/issues/74）
- 问题原文要点：`--vision` 永久占用常驻 VRAM（视觉塔权重 + vision 份额的 workspace/瞬时预留）；实测在 32 GiB/bf16 KV 配置下 ≈ **36k tokens 上下文容量**的开销。
- 设计五点（原文摘要）：
  1. **驱逐货币 = 只读权重**：`lm_head`、token embedding、**draft/MTP heads** 位于 VMM-backed **16 MiB 粒度 chunk**（稳定虚拟地址 + 固定 host mirror）；窗口期 unmap 最小 chunk 前缀，并把同一批物理 handle 重映射进预保留 staging VA——**事务内零设备端新分配**；恢复 = 幂等 H2D 重上传；**CUDA graph 保持已捕获状态**。选只读权重当"货币"是因为无需 D2H 备份；**KV 从不参与驱逐**。
  2. **分块流式编码**：视觉塔权重经 **~20 MiB ping-pong 缓冲**在 copy stream 上流式搬运、与 block 计算重叠；借用显存 ≈ encode workspace 大小（不是整塔常驻）。
  3. **独占 residency gate**：窗口互斥；并发文本 lane 等待、之后无损恢复。
  4. **fit-and-scale 预算**：`--vision-max-merged N` → 像素上限；超大素材预处理阶段降采样（不拒绝请求）。
  5. 目标范围：27B 系列 + 35B-A3B。
- 【实测】（RTX 5090，驱动 580.65，CUDA 13.1）：bf16 最大上下文 **171,648 → 207,936（+21.1%）**；int8 两侧达原生上限、启动后空闲 **2.45 → 4.80 GiB**；窗口开销 **~400 ms/图**（24 GiB sm_86 fork 测得）对比 ~3.3 s vision TTFT；**两种模式补全逐字节一致**。
- 评论（原文）：`encode_items_overlay` 在**每个窗口、每 item 每请求**用 `cudaHostAlloc` 新分配 **~125 MB** pinned staging（全窗口图）——被建议改为可复用 pinned pool（最终搁置）。
- 关闭理由（维护者 2026-08-27 原文摘要）：commit fc5c483 已缩小 vision workspace，overlay 不再明显挤压 KV 容量，**"当前不值得引入额外复杂度"**。

**② 实现本体：Neroued/ninfer PR #72**（"On-demand vision residency: stream the tower through evicted read-only text weights"；**Closed 未合并**，作者 2026-09-04 主动关闭；https://github.com/Neroued/ninfer/pull/72）
- 机制（与 #74 一致，附源码级名）：`core/evictable_weight_pool.cu`；**驱逐对象 = `lm_head`、token embedding、MTP head、尾部 decoder blocks**；staging 事务零设备分配 → restore 不会失败、CUDA graph 不重捕获；`vision_weight_provider` 块流式（~20 MiB ping-pong）；residency gate 互斥。
- 旗标：**`--vision-residency overlay`**（默认 resident、逐位不变、加法式）+ `--vision-max-merged N`；覆盖两个 in-tree vision 目标（**qwen3.8-27b**、qwen3.6-35b-a3b）；**无 overlay layout 的目标在加载时显式报错拒绝该旗标**。用法示例：`ninfer <artifact> --prompt ... --vision --vision-residency overlay --vision-max-merged 4096 --greedy`。
- 【实测】35B-A3B int8：运行时预留 **1.39 GiB → 474 MiB**（+1.17 GiB 空闲）；overlay 窗口总计 1,912 ms（evict 864 MiB = 1.8 ms；restore = 64.5 ms；stream = 267 MiB）；27B 上 `--vision-max-merged` 12288→11,767 tokens、1024→989 tokens（降采样而非拒绝）。
- 关闭理由（作者摘要）：fc5c483 后常驻 Vision 成本 ~0.65 GiB（= 32 GiB 卡 KV 的 5–7%），int8 已到原生上限——不值得上游引入；工作转移到 sm_86/89 fork（Don-Chad#21），24 GiB 卡可回收 ~13%；第二阶段 = 从空闲 KV 页为窗口出资（可并行）。
- 备注（原文披露）：PR #72 的 AI 披露——实现与验证由 "Claude Fable 5" 产出，提交者操作/审查/验证。

**③ 24 GiB 卡版 + 并行档：Don-Chad/ninfer-3090 PR #21**（"On-demand vision residency (overlay) on the v0.6.2 resource model: no resident vision cost on 24 GiB cards"；**Closed 未合并**，2026-09-08；https://github.com/Don-Chad/ninfer-3090/pull/21）
- **窗口的两档资金来源（本调研最重要的机制细节）**：
  - **空闲 KV 页（并发档）**：当空闲 KV 页足以覆盖窗口时**零拷贝**（不做任何搬运；文本权重保持映射）；编码在专用 `vision_stream` 上执行，**其余 lane 继续 decode**（唯一 prefill 的 lane 让出 prefill 单元至完成事件）。颗粒 = K plane 32 页 + packed V plane 64 页（64 页对齐发放）；scale plane（2 KiB/页）永不外借；归还零拷贝。
  - **可淘汰文本权重尾部（独占档，回退）**：CUDA VMM 权重 arena（16 MiB chunk、地址稳定 → 已捕获 decode graph 仍有效）；**淘汰秩：MTP 400 < draft head 500 < token embedding 600 < lm_head 700**；`Transaction::close()` 重映射回 home、只重传脏区间、不抛异常（恢复失败 → pool 毒化拒后续工作）。
- 其他要点：Vision 权重常驻**锁页主机内存**（`TensorPlacement::HostPinned`，类型层 `HostVisionWeights` 隔离）；一图一窗（`VisionOverlaySession::submit_item`）；**同一图片的后续轮次复用 prefix、不再开窗**；出借页会同步收缩 `usable_pages()/admission_capacity()`（防超额接纳）。
- 【实测】（RTX 3090 24 GiB，qwen3.8-27b groupwise-int，`--spec mtp --draft-tokens 3 --lm-head-draft`，`--vision-max-merged 12288`）：
  - 最大 `--max-context`：int8 无 vision 147,456 / 常驻 122,880 / **overlay 147,456**；rk8v4 196,608/163,840/**196,608**；bf16 73,728/65,536/**73,728** → **overlay 完全恢复"无 vision 容量"**（+20%/+20%/+12.5%）。
  - 65,536 token 时：启动预留 2.66 → 2.23 GiB（−0.43 GiB）；权重后可释放显存 6.35 → 6.61 GiB（+260 MiB，因 282 MiB 塔移到锁页主机内存）。
  - 借出粒度：rk8v4 上 1 个 loan 单位从 100 MiB 页中释放 96 MiB（≈95.1%）；1080p 窗口消耗 2 个单位。
  - **单图成本**：1080p overlay TTFT **3.55 s** vs 常驻 3.47 s（窗口 477 ms；淘汰 192 MiB 用 4 ms / 恢复 11 ms）；4000×3000 图：22.8 s vs 23.0 s（窗口 6.65 s；784 MiB，10 ms/49 ms）。
  - **文本流停顿**：并发窗口 gap p50 40 ms / p99 340 ms / max 413 ms（窗口 408 ms）——**并发档不倒灌**；独占窗口 gap max 670 ms（≈窗口时长全额加到最坏 gap）。无图时文本吞吐两模式无实质差异；补全逐字节一致（`tools/smoke/overlay_ab.py`）。
  - 4090 对照：overlay ≈ 无 vision 容量（差 1 个 2,048-token 步长，源于 per-chunk 暂存张量）。
- **落地流通过程（关键）**：Don-Chad 主线未合并；**`ashalliants/ninfer-3090#8` 已 Merged**（"feat(qwen3.6): on-demand vision residency (overlay) + enable on the C1 launcher"；维护者 2026-09-03 评论 "working like a charm, and with 35ba3b"）；`mgscreativa/ninfer-3090` 2026-09-22 cherry-pick 提交 `5a331eb`（注明 "Cherry-picked from Don-Chad #21"，并适配 rk8v4 `packed_values` 字段差异）。
- 限制（原文列表）：**Windows 未测试**（仅 Linux/sm_86）；35B-A3B 仅代码等价；视频按两帧一组约束；一 prompt 的第二张及以后图片**同步编码**；图像 prompt 自身的 prefill chunk 仍会阻塞 decode（引擎 prefill/decode 交替机制，与窗口无关）。

**④ 旁支与佐证：Neroued/ninfer PR #73**（"Content-addressed host KV cache: prefix restore and trajectory branching"，2026-08-27 closed；https://github.com/Neroued/ninfer/issues/73 ——实为 PR 页面）
- 其分支叠加携带了 overlay 移植 commits（`919124d` overlap 移植到 master、`39f8233` 适配媒体载荷、`e5f051c` fit-and-scale、`fc315d9` 35B overlay、`907f4a4` CLI 旗标）；关联外部 PR "Don-Chad/ninfer-3090#8: Opt-in overlay vision residency: zero resident vision VRAM via evictable text-weight windows"。
- 作者原话：**"cache 本身不依赖 overlay，可与任一 vision residency 模式配合工作"**（有独立 cherry-pick 验证）。
- 相关互斥先例：`--kv-host-cache-mib` 与 `--spec dflash` 在启动时互斥（drafter 上下文，见 #75）——说明 NInfer 生态中 dflash 与宿主侧机制的集成是**逐项**做的。
- 用户佐证（同 PR 评论，gearwave00001）：5090 在 262144 上下文 + `--vision`（resident）时并发受限，需降到 204800 才能并发 >1——**正是容量耦合、也正是 overlay 要解决的问题**。

**关于"运行时切换"与"MTP/DFlash 显存管理"的直接回答**：
- **没有"运行中切模式"的开关**：模式在启动时选定（resident 默认 / overlay opt-in）；overlay 模式下**驻留变化按图自动发生**（每图一个窗口）。【PR/issue 原文 + 调研者推断】
- MTP/DFlash 的上游规则：只在启动启用时加载、单引擎只能选一个投机后端、DFlash 不加速 Vision encode（README/cli.md【官方原文】）；overlay 机制里 **MTP head 与 draft head 恰恰是"可驱逐货币"的第 1、2 顺位**（秩 400/500）——即"多模态时 MTP 临时退场、文本时恢复"的既有实现（#21 的 A/B 配置就是 `--spec mtp --draft-tokens 3 --lm-head-draft` + vision overlay）。

**"overlay 到底借多少设备内存"（回答你的原问）**：
- 借用规模 ≈ encode workspace 大小（"+ ~10 MiB/chunk 暂存张力"级别；塔权重体以 **20 MiB 级 ping-pong** 流过，不整块常驻）；**按图量级示例**：1080p ≈ 192 MiB（2 loan units）、4000×3000 ≈ 784 MiB；35B 塔场景 stream 267 MiB、常驻预留 474 MiB（对照 resident 1.39 GiB）。【PR#21/#72 实测】
- 主机侧另有成本：塔权重常驻锁页内存（282 MiB 级）+ 每窗口 pinned staging ~125 MB（#74 评论，待优化项）。

### 1.4 llama.cpp

- 【官方原文】`docs/multimodal.md`（raw master，2026-10-12 抓取）：**"By default, multimodal projector will be offloaded to GPU. To disable this, add `--no-mmproj-offload`"**；`--no-mmproj` = 完全不加载 mmproj；**全文无任何运行时按需加载/卸载或动态 residency 说明**。
- 【官方原文】`tools/server/README.md`（raw master）：
  - `-mm/--mmproj`、`--mmproj-auto/--no-mmproj`、**`--mmproj-offload/--no-mmproj-offload`（默认 enabled）**、`-mmdev/--mmproj-device`（"device to use for multimodal projector (none = don't offload, default: follows --device)"）——**启动参数静态决定**。
  - **router 模式**："exposes an API for **dynamically loading and unloading models**"（模型级动态装卸；--models-dir/--models-preset/--models-max 默认 4）——粒度=整模型。
  - **LoRA 热换**：`GET /lora-adapters`（列出+scale）、`POST /lora-adapters`（改 scale）；`--lora`、`--lora-scaled`、`--lora-init-without-apply`——**llama.cpp 里唯一"运行时装卸组件"的官方机制（组件=LoRA 适配器）**。
- 社区补丁 **Swap-MoE**（https://github.com/ek15072809/Swap-MoE；llama.cpp patch @f5e85d43a，2026-08-28）：MoE routed experts 权重留 SSD mmap、CPU 计算、**缺页按需载入**；`--expert-keep-recent N`（每层 LRU 显式逐出）、`--expert-cache-size`（MiB 预算）、fixation（钉住 top-k 换 I/O，**伤质量**）、prefetch（上一 pass 预测 + `madvise(WILLNEED)`/`PrefetchVirtualMemory`，**无精度代价**；DeepSeek-V4 实测 0.39→0.55 tok/s）。【实测】Qwen3.5-35B-A3B Q4_K_M：正常加载直接失败 → expert-streaming 7.01 tok/s；纯 CPU 后端、**不支持与 GPU offload 组合**。
- 结论：**llama.cpp 官方没有 vision 组件的按需换入换出**；"运行时搬运"最近的两个先例是：整模型 router、LoRA scale/适配器，以及社区 Swap-MoE（对象=MoE 专家、介质=SSD）。

### 1.5 KVMem 系（kvmem/kvmem-llama.cpp 与相关线）

- 【官方原文/发布说明】**v0.17.0（2026-09-30，源码版）**：⭐**"视觉投影器独立选卡"——`--mmproj-device` 为视觉投影器单独选择 CPU / 指定 GPU（CUDA+Vulkan 构建还可放 Vulkan GPU）**；多会话 KV + NVMe 转存（LRU）；实验双卡；Responses API。（https://github.com/kvmem/kvmem-llama.cpp/releases）
- 【官方原文】**RC3（v0.18.0-ninfer-rc3，2026-10-11）**：RAM/SSD 分层 KV（"完整原生 K/V、量化附属数据及 **MTP KV** 可下沉 SSD；恢复按实际选中内容读取"）；默认配方 = **"CPU 视觉 + 自适应 MTP4 + ngram31"**（`-NoVision` 关）；LRFU/sink/recent；明确"本次没有…自适应预算或配额混合"。
- RC2：多卡时"MTP 位于列表中的第一张卡，视觉默认在 CPU"；Bonsai prism.3：`--no-mmproj-offload` 视觉头放 CPU 省显存（启动静态）。
- tancau/ninfer-kvmem-ring：KV 页搬运线（Phase 2 收官 "decode at wall"；Phase 3 分层 restore 未实现）——**KV 域，不是组件域**（本地快照）。
- 结论：**KVMem 系 = "静态选卡 + KV 分层"**；组件权重层面没有运行时换入换出；其 `--mmproj-device` 是"视觉头换地方"的静态官方化先例。本线的 KVMem 六开关（NINFER_KV_*）同属 KV 域，与"组件 residency"正交。【调研者推断】

## §2 更广生态（vLLM / SGLang / TRT-LLM / Ollama / LM Studio / ExLlama）

### 2.1 vLLM

- **Sleep mode**（【官方原文】`docs/features/sleep_mode.md`，raw main；官方博客 2025-10-26 链接见文档）：
  - **Level 1**：模型权重**备份到 pageable CPU RAM**（唤醒自动恢复）+ KV 丢弃；**Level 2**：权重**直接丢弃**（不备份；唤醒后需 `reload_weights`）+ 模型 buffers 留 CPU（如 rope scaling）；**Level 0 pause**：`llm.sleep(level=0, mode="keep")` + `release_kv_cache_memory()` 只丢 KV。
  - `wake_up(tags=["weights"]/["kv_cache"])` 部分唤醒；只要还有组件未醒 `is_sleeping=true`；HTTP：`/sleep`、`/wake_up?tags=...`、`/is_sleeping`、`/release_kv_cache_memory`；线上需 `VLLM_SERVER_DEV_MODE=1` + `--enable-sleep-mode`（文档警告勿对用户暴露）；可释放 **90%+** 显存；需 cumem 分配器（CPU/unmanaged 分配不支持）。
  - ⭐**`--sleep-preserve-parameter-names`**：Level-2 时把指定参数（glob）备份到 pageable CPU 并原地恢复；两个官方用例：冻结的 Engram 表、**冻结的 draft 权重（`draft.*`）**——**"把草稿/MTP 类组件单独保留与恢复"的官方开关**（RLHF 场景）。
  - `sleep_mode_offload_cudagraph`（默认关）：CUDA graph 内存也备份 pinned host、唤醒原地重放；代价 ~3% decode 延迟（bs=1）。
- **LoRA 动态装卸**（【官方原文】`docs/features/lora.md`）：`POST /v1/load_lora_adapter`（`lora_name`/`lora_path`/`load_inplace`）、`POST /v1/unload_lora_adapter`；**需 `VLLM_ALLOW_RUNTIME_LORA_UPDATING=True`**（安全警告：按调用方路径加载，勿在生产暴露）；`load_inplace` 用于 async RL 原地换权重；LoRAResolver 插件（filesystem/HF）按需加载；`max_loras`/`max_cpu_loras` = GPU 活跃数 / CPU 缓存数（文档未给精确定义）。
- **Disaggregated Encoder / EPD**（【官方原文】`docs.vllm.com.cn/.../features/disagg_encoder/`（2026-05-06 页；同 `docs.vllm.ai`））：Encoder 实例 + PD 实例；拓扑 **E→PD** 与 **E→P→D**；动机=独立细粒度扩缩容、TTFT（纯文本绕过编码器）、跨进程复用（远程共享 EC cache）；`ECConnector`（Scheduler/Worker 角色；代码 `vllm/distributed/ec_transfer`）；dev preview。NVIDIA Dynamo 官方并列支持（见 2.3）。
- 投机解码：draft 模型**静态加载**（官方未见运行时卸载）；社区观察：draft 另占 KV cache + CUDA graph 显存（非官方源，仅作提示）。
- 小结（【调研者推断】）：vLLM 的"组件级"能力分别是 **引擎级 sleep（可含 draft.* 保参）**、**适配器级动态装卸**、**架构级编码器分离**；**没有"同卡内 vision/MTP 互换"**。

### 2.2 SGLang

- 【官方原文】server args（https://docs.sglang.io/advanced_features/server_arguments.html）：
  - **权重 offload 组**：`--cpu-offload-gb`（"How many GBs of RAM to reserve for CPU offloading."，默认 0）；`--offload-group-size`（层分组，默认 -1）；`--offload-num-in-group`（默认 1）；**`--offload-prefetch-step`（"Steps to prefetch in offloading"，默认 1）**；`--offload-mode`（默认 cpu）——"层组流式 + 预取"的参数化实现。
  - **PLE 表组**：`--ple-offload-embedding`（默认对 BF16 Qwen4-Exp 开；gather 内核读 host 指针）；`--ple-offload-backend pinned|file`（file = 稀疏文件 mmap，**内核直接读文件页**）——"组件常驻 host、设备侧直接引用"的先例（对象=嵌入表）。
  - 多模态：`--enable-mm-global-cache`（**Mooncake 全局多模态嵌入缓存（"on encoder servers"）**）、`--mm-enable-dp-encoder`、`--enable-prefix-mm-cache`。
  - 投机：`--speculative-algorithm EAGLE|EAGLE3|NEXTN|STANDALONE|NGRAM`、`--speculative-draft-model-path` 等——同样**静态加载**（未见运行时卸载参数）。
- 【调研者推断】SGLang 有 offload/预取/缓存面，**无"vision/MTP 组件互换"面**。

### 2.3 TensorRT-LLM / NVIDIA Dynamo

- 【官方原文】TRT-LLM "Multimodal Support"（2026-09-26 更新，commit c76f4a8）：仅概述（输入预处理 / 编码器 / 与 LLM 集成）；优化 = In-Flight Batching（"**within the GPU executor**"）、CPU/GPU 并发（预处理与编码异步重叠）、raw data hashing 提 KV 复用；**组件级显存管理细节在检索范围内【未找到】**（API 侧有 `MultimodalEncoder` 类、`EncodeCudaGraphConfig`）。
- 【官方原文】Dynamo "Encoder Disaggregation"（docs.nvidia.com/dynamo，v1.2.0）：视觉编码器拆成**独立 worker 进程**，embeddings 经 **NIXL（RDMA）** 传给下游；两种部署形态 **E/PD** 与 **E/P/D**；适用="编码是瓶颈/需要独立伸缩/想让编码跑在不同（如更小的）硬件上"；后端支持矩阵：vLLM、SGLang 支持两种，**TRT-LLM 仅 E/P/D**。→ 行业级答案 = **分离部署**，而非卡内互换。

### 2.4 Ollama / LM Studio / ExLlama

- **Ollama**（【官方原文】https://docs.ollama.com/faq）：模型级 keep_alive——默认**驻留 5 分钟后卸载**；`keep_alive: 0` = 生成完立即卸载；负数 = 常驻；`ollama stop`；`OLLAMA_KEEP_ALIVE`（全局）；内存不足 → 新请求排队、空闲旧模型被卸载腾空间；GPU 并发加载要求模型**完整装进 VRAM**；`ollama ps` 观察。**无组件级机制**。
- **LM Studio**（【官方原文】lmstudio.ai/docs/app/advanced/speculative-decoding）：草稿模型在主模型加载后于侧栏选择；草稿体积上限建议（主 3-7B→草稿 1B；14B→3B；32B→7B）；"同时运行草稿模型会消耗更多算力与资源"；**未说明装载/卸载耦合与独立 offload**；bug tracker #458（2025-02）怀疑其未用 `-ngld` 优先卸载草稿层。
- **ExLlama(V2)**：本轮检索**未找到**组件/子模型级动态换入换出机制（以模型级加载 + KV/缓存管理为主）。【未找到】

## §3 学术与通用技术

- **MoE 专家 offloading 系**（"大组件按需换入换出"最成熟的研究域）：
  - Eliseev & Mazur 2023（arXiv:2312.17238）：参数 offload + 利用 MoE 固有属性加速；Mixtral-8x7B 跑上桌面/免费 Colab（细节数字在正文）。
  - SwapMoE（arXiv:2308.15030，ACL 2024）：Virtual Experts + 可调内存预算；【实测】Switch Transformer 摘要任务 **14.2 → 4.7 GiB、延迟 −50%、Rouge-2 −0.041**。
  - MoE-Infinity（arXiv:2401.14361）：稀疏感知专家缓存 + trace 驱动替换/预取；每 token 延迟 **3.1–16.7×** 改善（vs vLLM/Ollama/DeepSpeed/BrainStorm）。
  - KTransformers（SOSP 2025，清华 MadSys PDF）：CPU/GPU 异构（热专家 GPU / 冷专家 CPU）+ 异步调度并入单 CUDA graph；宣传口径"24GB 单卡千亿参数级"。
  - Swap-MoE（llama.cpp patch，见 §1.4）：SSD 按需缺页 + LRU + prefetch。
- **适配器（LoRA）动态装卸系**（"运行时装/卸 MB 级组件"最成熟的服务域）：
  - vLLM LoRA API（§2.1）；**S-LoRA**（arXiv:2311.03285）：Unified Paging（适配器权重与 KV 统一分页内存池）、单卡数千适配器、吞吐最多 4×；**Punica**（arXiv:2310.18547，MLSys'24）：SGMV、固定集群吞吐 12×；**dLoRA**（OSDI'24，usenix PDF）：credit-based batching 决定 merge/unmerge + 请求-适配器 co-migration。
- **权重流式/offload 推理系**：
  - **FlexGen**（arXiv:2303.06865，ICML'23）：GPU/CPU/disk 聚合 + LP 求解放置与调度 + 4bit 压缩；【实测】OPT-175B 单 16GB GPU **1 tok/s**（有效 batch 144）。
  - **PowerInfer**（arXiv:2312.12456，SOSP'24）：热/冷神经元（功率律局部性）；【实测】单 4090 vs llama.cpp 最高 **11.69×**；OPT-30B 达 A100 生成率 82%。
- **投机/草稿组件系**：
  - **SpecOffload**（arXiv:2505.10259）：把投机解码嵌入 offloading 流水线、target/draft 交错执行、draft 放"潜藏 GPU 资源"；【实测】GPU 利用率 4.49×、吞吐 **2.54×**（vs "best baseline"，未具名）。——**"草稿/投机组件与 offload 共存"的直接先例**（方向与你的相反：基座 offload、draft 留卡上）。
  - vLLM sleep 的 `draft.*` 保参（§2.1）——"draft 权重单独保留/恢复"的官方开关。
- **模型级加载/切换系**：Ollama keep_alive（§2.4）、llama.cpp router（§1.4）、vLLM sleep（§2.1）、Aegaeon（SOSP'25，多模型服务 token 级扩缩容；报道称 GPU 用量 −82%，未核全文：ACM DOI 10.1145/3731569.3764815）。
- **编码器分离系**：vLLM Disaggregated Encoder、Dynamo E/PD 与 E/P/D（§2.1/2.3）。

## §5 对本场景的结论与建议

### 5.1 (a) 有没有现成机制可直接用？

**有——但要先在本机验证。** `--vision --vision-residency overlay` 就是你设想的"视觉塔与 MTP 头时分复用显存"的现成机制：设计（#74）、实现（#72）、24 GiB 卡并行版（#21）、合流（ashalliants#8 已合并）、周边佐证（#73 用户实测、知乎 5070Ti 帖）全齐；本地交接文档亦记录你的引擎源码面里有 `--vision-residency resident|overlay|cpu`。
- 它是"**按图窗口**"而非"模式切换"：文本时段 MTP 常驻不受影响；图片到来时窗口开启——**优先借空闲 KV 页（零拷贝、可与 decode 并行）**；不足时**按秩驱逐 MTP head/draft head/embedding/lm_head 尾部**（毫秒级驱逐、随后恢复）。你设想的"多模态时 MTP 卸、vision 上；文本时反向"= 该机制**独占档（回退档）**的精确描述。
- 主要不确定性与条件：① 构建含 overlay 且该 artifact 有 layout（不满足则"加载时显式报错拒绝"）；② Windows/sm_120 无验证数据；③ dflash2 组合未验证（MTP 组合已验证）；④ "借 KV 页（并发）档"需要空闲 KV 页——你小池+高占用时大概率走独占档（每图阻塞其他 lane ~0.4-0.7 s 量级，视觉请求已是你当前 15-20 s 级延迟的瓶颈，可接受）。

### 5.2 (b) 如果不可用：最接近的先例与自研路径/风险

- **最接近的先例（按移植贴近度排序）**：Don-Chad#21（T2 最完整，含并行档）→ ashalliants#8（已合流版，qwen3.6 标题）→ mgscreativa `5a331eb`（rk8v4 适配 cherry-pick）→ 上游 #72（覆盖 **qwen3.8-27b** 最直接）。你的引擎血统已经吃掉其中一段（ashalliants#8），先确认到底缺哪块。
- **不自研的替代**：静态换位实验——(i) GPU 常驻 vision + 缩池（对照 fc5c483 后 ~0.65 GiB 口径与你的 282 MiB 塔 + workspace 实测账）；(ii) 维持 `--vision-cpu`（现状），把 CPU 编码作为固定成本。两者零代码，先算清"省下的显存能否换来池/并发提升"。
- **自研路径（若坚持）**：按 #72/#21 蓝图——VMM 16 MiB chunk 池 + 稳定 VA + pinned host mirror + 预保留 staging VA + 零分配事务 + 20 MiB ping-pong + residency gate + fit-and-scale 预算 + KV 页出借核算（`usable_pages/admission_capacity` 收缩）。建议分期：先"单组件窗口借用"，再"双组件互换"。
- **风险**：上游两度判"不值得"不等于机制错，而是 ① 实现复杂度高（VMM/staging/图保持/"恢复不失败"语义）② 32 GiB 卡上收益变小。**在 16GB 卡上收益可能更大**（塔 282 MiB + MTP 239 MB + vision workspace 的占比远高于 32 GiB 卡）——但先测现成开关，别重写已存在的东西；真要写，优先从 fork 移植而不是从零复刻。

### 5.3 (c) 点名：“谁做过 vision encoder 按需上 GPU / draft/MTP 头运行时卸载”

- **vision 按需上 GPU（同进程窗口式）**：**NInfer overlay 全链**（iamwavecut：#74 设计 / #72 实现 / Don-Chad#21 24GiB 版 / ashalliants#8 合流 / mgscreativa cherry-pick）——目前**唯一**做到"按请求把 vision tower 在 host↔GPU 间搬进搬出"的成体系实现。静态版先例：llama.cpp & kvmem `--mmproj-device`。
- **draft/MTP 运行时卸载**：**NInfer overlay**（MTP head/draft head 作为"可驱逐货币"被窗口临时驱逐再恢复——即你要的"运行时卸载"的既有实现）；vLLM sleep `draft.*` 保参（引擎级、面向 RL）；SpecOffload（反方向：基座 offload、draft 常驻潜藏显存）。其余（llama.cpp/vLLM/SGLang draft、LM Studio）均静态。
- 未找到：其他引擎的"vision 按需上 GPU"同款机制（vLLM/SGLang/TRT-LLM 走的是分离部署或静态放置）。【未找到】

### 5.4 需要回家实测验证的点（首要任务清单）

1. **旗标可用性（最高优先）**：用现役自编引擎 + iq4nlvis 嫁接件，以 `--vision --vision-residency overlay` 起服。观察：a) 是否被拒（"无 overlay layout 的目标显式报错"）；b) 启动日志的 residency/overlay 行；c) `/v1/models` 的 modalities.vision=true。若被拒 → 定位是否缺 overlay commit（对照 ashalliants#8 / mgscreativa 5a331eb）。
2. **窗口行为与借用账**：发一张图，记录 TTFT（对照 `--vision-cpu` 的 15-20 s / DSH 26.9 s 基线——目标是把识图压到秒级）；记录图期间显存变化与"文本 lane gap"（并发档预期百 ms 级；独占档 ≈ 窗口时长）。
3. **组合兼容**：overlay × MTP(k4/d12) × ngram × KVMem 六开关 × hemostat；**特别试 dflash2**（未验证项；若现互斥类报错，先用 MTP 档定位——dflash 与宿主机制的互斥在 #73/#75 有先例）。
4. **容量收益结算**：overlay 后把池逐步顶到 55296/更高，找 16GB 卡新平衡（参照：3090 上 overlay 恢复"无 vision"容量、free +260 MiB；5090 上 +2.35 GiB 余量）；同时监控 host 端（塔驻留 + 每窗口 ~125 MB staging + 12 GiB Host KV payload 预算，RAM 要算总账）。
5. **Windows 稳定性**：连续多图/长会话；关注 pinned 内存增长、每窗口 `cudaHostAlloc`、崩溃或 capture 失效迹象；遵守"起服前关 GPU 占用程序"纪律。
