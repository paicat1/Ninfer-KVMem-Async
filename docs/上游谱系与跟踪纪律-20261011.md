## 四、跟踪纪律（立此存照）

1. **每次大问题排查前**：先 `git fetch` Bonsai 线 + 翻 `docs/06-Bug手册.md` 新条目——**先看上游有没有解法，再闷头自己撞墙**；
2. **定期（每周）**：`HEAD..origin/main` 计数 + Bug 手册 diff 摘要；
3. **指代纪律**：禁用"官方"统称；说"Bonsai 线"、"兄弟件 RC2"、"NInfer 原始仓"、"tancau 环线"、"qw3 策略层"；
4. **上游解法入库路径**：Bonsai 线分析 → **与前作 P 系列对照去重合并**（同一修法两条线的各自落地）→ 对照本线实测 → 评估移植（env 级 > patch 级 > merge 级，按风险递增）→ 实测验证 → 构建史记档；
5. **本档维护**：谱系变化（新仓/新分支/新下游）时更新本文件 + 修订记录。

## 五、FORK 跟踪与安全拉取策略（我们是 Bonsai 线的实质 fork）

**现状**：s6-20261008 定稿基线（self-built-20261008 由此编出）+ 自有层（launcher/文档/探针/构建修正 `5b07bc1`/`a25012b`/`3b9dc83`）。

| 动作 | 策略 | 风险控制 |
|---|---|---|
| **跟踪** | `git fetch` 只读；盯 origin/main 的 docs/06-Bug手册 + docs/13/14 增量（低频：每周或每次大问题） | 不动工作区 |
| **拉取** | **永不盲目 merge**（merge 会动 s6 定稿源码树，self-built 引擎失去可复现性）；采用 **cherry-pick 评审制**：单提交 → `git apply --check` → diff 评审 → 本线实测 → 落档 | 每次吸收独立 commit，可 revert |
| **吸收** | env 级（零源码，如 sink）> patch 级（cherry-pick 单修）> merge 级（整体同步，仅在 Bonsai 出下一个定稿 tag 时评估） | 定稿基线只进不退；吸收后必须重跑探针（test_ab_arm1/multiturn/stream_stall） |
| **去重/合并** | 吸收前对照我方已有提交（`5b07bc1` MSVC / `a25012b` Design C / `3b9dc83` STANDALONE）+ 我方 env（KV_ENV 六开关已含 sink/retrieve/window）+ 前作 P 系列——**同一修法多线落地时合并收敛，互为验证** | | 防"考古自己"（P-01 教训） |

**当前欠账**：落后 23 提交未逐条评审（B33-B39 病历 + docs/13/14）——评审产物记入构建史；有引擎行为级变更才考虑 cherry-pick，纯文档类已通过 fetch 阅读（无需落树）。
