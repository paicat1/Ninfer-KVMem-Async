### 1.4 方法论遗产

- **一链三层**取代"三轴并列"：输入唯一性只否定臂内对照，**ABBA 臂间对照有效性无损**（无损门与收益测量的基础）；
- "同输入"与"cache 失效"不可兼得的 paradox——**residency 轴不可构造是能力缺口，不是观测缺位**；
- 任务设计即判据边界："解释模式 + 自检清单"的强结构化输出请求 ⇒ 任何 n-gram 判据在此任务上先天地不可靠——**尺子要先于刻度**。

## 三、无损门分档（发布面口径）

| 开关类 | 跨臂同 sha 承诺 | 适用态 | 依据 |
|---|---|---|---|
| 纯开关类（ngram、mtp-attention-window） | 应承诺 | **仅 fresh 态** | 10-14 首触实证；同进程复发 run-to-run 不同为 10-13 同臂实锤，fresh 承诺不可外推 |
| 调度类（async demote、graph） | 不承诺 | 任意态 | 按定义改变执行路径；跨臂差异单独立"路径敏感性"账 |

**"无损门失败"表述废止**——判据用错对象，不是 bug。

**发布面四条口径**：①收益 = +19%（弃"2 倍"）；②不引 dup8（max8 亦待定义落实）；③护栏句：超池+贪婪+长输出开 repetition penalty；**慢态勿关异步**（同步回退路径正是复读路径，"risk backstop"实锤为坏保险丝）；④无损门按上表分档表述，避免"异步防复读"类因果误写（residency 轴下任何臂都可能态依赖分叉）；
⑤**README 既有主张需加限定**：现文"池内 vs 超池输出逐字无损"必须改写为"**同臂、fresh 态、池内 vs 超池首触**逐字无损"（10-13 实证：45K 池内跨臂一致、90K 超池首触跨臂一致；**复发轮不承诺**）——否则与上表自相矛盾，且被 10-13 复发反例直接打脸。这是本轮唯一波及公开材料的实质风险项。

## 四、实验设计终版（Y1'' / Y2 / 路线图）

### 4.1 实机夜前置（7 件检查 + 1 件代码，不完成不排期）

**代码 1 件**：C0 a2gate.py L88 文件名加 `_run%d`（将来 runs>1 的材料保护）。

**检查 7 件**（零机时/秒级，全主机）：P-a max_shared_prefixes 语义 grep · P-b max8/dup8 实现 grep · P-c logprobs curl 实测 · P-d cached_tokens 读数（gate_*.json + reqlog_abab_*.jsonl，r1=0/r2>0 即坐实缓存命中）· P-e logstat 按 round 分段可行性确认 · **P-f** demote profile 行是否带 step 号 · **P-g** restore 侧是否已有耗时字段。

**P-f 的分叉价值**（第一个"结果越好、路线图越提前"的前置）：行内**有 step 号** ⇒ 请求内页操作率可算 ⇒ 深度自适应 v0 提前（受日志管道时延约束：读日志只能近实时，引擎内计数器才到批级）→ 不必等新打点、不必等 residency 接口；**无 step 号** ⇒ 引擎加一行计数。**P-g**：已有耗时字段 ⇒ restore_profile 是"补字段"；无 ⇒ "建打点"（成本差一个量级）。

可复制命令：

```bash
# P-a / P-b（在家 J:\ninfer-kvmem）
grep -rn "max_shared_prefixes" engine-src/ | head -30
grep -rn "max8\|dup8\|repeat_8gram\|n8_max" engine-src/ .temp/ | head -30

# P-c（引擎起服后；不支持会返回 400 或忽略字段）
curl -s -X POST http://127.0.0.1:8094/v1/chat/completions -H "Content-Type: application/json" \
  -d '{"model":"qwen3.8-27b-coder390","messages":[{"role":"user","content":"hi"}],"max_tokens":5,"logprobs":true,"top_logprobs":3}'

# P-d（四臂 × 3 round 的 cached_tokens）— 单行写法，避免 PowerShell 多行缩进坑
python -c "import json,glob; [print(f, [(r['round'], (r.get('usage') or {}).get('prompt_tokens_details', {}).get('cached_tokens')) for r in json.load(open(f, encoding='utf-8'))['runs']]) for f in sorted(glob.glob('.temp/gate_abab_*.json'))]"
```

### 4.1b classify_repeat 判定算法（四分类操作定义，主机可立即执行）

对每份全文的每个循环段（由 max8 重复 8-gram 的起点起、连续至断点）：

| 类 | 判定 |
|---|---|
| `quote_src` | 该段是 filler（NATO 26 词序列）的子串 |
| `quote_prev` | 该段是**本会话前轮 assistant 输出**的子串（r2/r3 才可能有；r1 恒为 0——因此 r1 的循环段是唯一"无传染"观测） |
| `self` | 两者皆非——模型自造重复 |
| `结构` | 编号/句式模板重复（如"N. 检查 X 是否 Y"连续 ≥3 次）但逐字内容不同 |

输出：各类字符数占比 + 最长 `self` 段长度 + `quote_prev` 是否出现在 r2/r3（传染链证据）。
文件定位：主机 `.temp/abab_text_abab_{off,on}_c{1,2}_r{1,2,3}.txt`（arm 名带 `abab_` 前缀，共 12 份，runs=1 无覆盖）。

### 4.2 Y1''（一次实验夜三件事）

1. **P6' 池内对照**：verbatim_gate 8 提示 × 两臂——池内短 prompt 无页管理 ⇒ 预言 sha 全同（分叉必由页管理路径驱动的检验）；
2. **析因（去重后实为 3 格）**：池内短（与 P6' 同格）/ 池内长 / 超池长，各 × ON/OFF = 6 臂——"超池短"天然不存在（短 prompt 不超池）；核心格必须跨重启跑（每格 fresh 进程），否则进程内页池态递进会成为混杂因子；
3. **runs=2 改名"cache 路径敏感性对照"**（原 residency 提议的残骸，独立有价值）：run1 r1（fresh prefill）vs run2 r1（cache 命中）sha/diff ⇒ 直接回答"#53 分叉是否依赖 prefill 路径"——路径敏感获证则 FP/调度家族落锤，不敏感则 G2 读码扩围；
4. 附加：**nonce 态轴扫描**（OFF 臂 3-5 nonce，复读对 cache 态的敏感性）、P1 gap 实测（若 P-c 通过）。

## 八、未竟：异步页流水的下一步（2026-10-26 三方讨论纪要）

> 参与：用户（工程直觉）、CB（边界论证）、lummy（路线补充）。本节为讨论沉淀，**未做实机验证**，不改变 §一 的归因结论。

### 8.1 三方共识

1. **加速有上限且可写**：decode ≈ `max(计算时间, 搬运时间) + 管理开销 + 暴露残差`；异步的目标是让它收敛到**计算时间**（下界）。浅载已到顶（D2 187.1 vs D0 183.6，+1.9%），空间在**深载**（慢峰单批 11.5-33.7 ms 已接近步窗 27-32 ms）。
2. **收益是搬运量的函数**：`前端把搬运量压小，后端绝对收益下降，但比例恒 ≥1`；最好的后端技术最终"同化"为不需要被谈论的默认行为。前端优化不会"推翻"异步，只会让它的价值趋零——问题被消掉，而不是技术失效。
3. **#33 与 depth 不是替代关系**：#33 管"每批多便宜"（页管理事件数/快照开销），depth 管"爆发怎么摊平"（传输延迟）；两者正交但存在交互项（见 8.2）。

### 8.2 待验证的分歧与边界（CB 对 lummy 五点的修正）

| 议题 | lummy 观点 | CB 修正 |
|---|---|---|
| 移动语义下的中间态 | "双副本过渡期消失或大幅简化 ⇒ depth 甜蜜点右移" | **简化而非消失**：传输中页仍需 owner 标记 + fence（否则 host 得半截数据）；省的是 epoch 双副本一致性检查，fence 不可省。甜蜜点右移成立，但上限仍由"爆发深度 ÷ 8"决定 |
| 管理开销量级 | "O(页数) 硬底，深载可能已与 DMA 同级" | **与现有 profile 不符**：demote profile 实测 `copy=2.68 publish=0.00 tail=0.00`——开销几乎全在 DMA copy，不在账本。真开销是搬运本身，#33 不省搬运字节。**留余地**：restore/裁决侧未测 |
| 攻关顺序 | 点一"先 #33 再分档" vs 点五"①分档→③#33" | **自相矛盾**。折中：先跑分档**最小版**（depth 1 vs 2）验证慢态判据与方法，完整 1/2/3/4 待 #33 后重测 |
| 终点=控制回路 | "义务率估计 → depth/批大小/预取 → 执行 → profile 反馈" | **缺三个前提**：①**目标函数未定**（tok/s / TTFT / 尾延迟，三者对 depth 要求不同）②**稳定性**（估计滞后导致 depth 振荡，需滞回/阻尼）③**估计器上限**由注意力局部性决定（长尾访问下预取收益有限） |
| 三抓手合并立项 | 预取/深度自适应/页选择共享"页需求估计器" | **同意，但要渐进**：先做最小估计器只服务深度自适应（最容易），验证后再接预取（中）、页选择（难，本质是置换算法） |

### 8.3 攻关顺序（修正版，按成本/收益排序）

1. **深载 depth 分档最小版（1 vs 2）+ 慢态判据**——便宜，先验证方法与判据；数据会受 #33 影响，但流程可复用。慢态判据：**功耗 65-110W / submit≈wall / decode<60**，命中即作废重跑（§164 教训；预算按 2-3 晚等正常态窗口，不要按"一晚"排）。
2. **搬运双侧归因**（demote + restore）——原表述只测 demote 侧。**深度修正**：深载 3.5× 超池下 demote 与 restore 都在高频（§164 ON 臂 demote **994 点火**，不是"只有召回"），但 restore 侧只有环内打点（S6 覆盖 demote/ring/restore **环内五段**：亚毫秒、STALL=0）+ `ring retrieve: restored=N` 计数，**缺 H2D 传输 + 发布的 ms 级分解**。前置新仪器：restore 侧补 `restore_profile: copy=X publish=Y tail=Z`（**字段名直接镜像 demote profile，不发明新名**，两侧并表归因）。**已有基础（成本比"建打点"低一档）**：`NINFER_MAT_DEBUG=1` 源码存在于 `runtime/engine/context_cache/materialization_planner.h:154`，打印 **admission/materialization gate**（准入/物化门）——正是 restore/召回实现模块；`valley_s13`/`valley_incidence`/`pdl_aba`/`night_ab`/`mitig_interleave` 等多条脚本已在用；且有判读先例（谷攻关报告"下次起服把 MAT_DEBUG 一并打开，谷窗直接看准入/物化门"）。故 restore 打点 = **在 MAT_DEBUG 现有行上补耗时字段**，不是新建仪器。
3. **#33 POC（移动语义，只动 sync 路径）**——量三件事：OFF 臂 decode 提升、restore 延迟、逐字门是否仍过；再决定是否动 async 状态机。
4. **页需求估计器 v0**（只服务深度自适应）——**时间分解免费**（StepProfile：步级 wall 四分解 submit/wait/post/rest + 提交段五分 rows/pre/launch/sync/harvest）；**页操作计数待 P-f**。两条硬约束：①**请求级 ≠ 请求内**——`reqlog.host_work.units` 请求结束才写，跨请求估计抓不到"轮首爆发"（单请求内现象）；②**日志管道时延**——靠读日志做"实时"只能到近实时（秒级），真正的批级自适应需引擎内计数器。验证后再接预取/页选择；运行时观测依赖 residency 接口立项（一个接口三吃）。
5. **完整 depth 分档（1/2/3/4）+ 估计器版**——在 #33 落地后的新开销曲线上重测，才是"甜蜜点右移"的实证。
6. **终点：控制回路**——义务率估计 → depth/批大小/预取 → 执行 → profile 反馈；前提是先定目标函数 + 加滞回，否则回路会振荡。

**⚠ #56 范围标注（本轮连带修正）**：#56 的"不装节奏器（上限 2.49% < 5%）"用 ledger44 的 **demote 侧**慢峰（3.4-7.8 ms/批）算出——**restore 传输侧的优化空间从未评估**。故该结论只对 demote 侧成立，**不得外推**。这是八轮里第一个"结论因范围标注而降格"的既有挂账，记账方式应成为模板：**任何用单侧成本做的"不装/不修"结论，都必须标注覆盖范围**。

### 8.5b 外部路线评估：Strata（KV 分层、布局解耦、顺序访问）

> 来源：OSDI '26 论文摘要页（USENIX 官方）+ 二手精读（swiftscholar，AI 生成，可能有转述失真）+ Niko1221/Strata 的 `docs/DETAILS.md`（工程引擎，非同一项目）。**未取得论文全文，机制细节标注为"二手"**。

**① 两个 Strata 必须分清**

| | OSDI '26 Strata（学术） | Niko1221/Strata（工程引擎） |
|---|---|---|
| 身份 | Stanford+NVIDIA（Zhiqiang Xie 等），集成 **SGLang**，已生产部署 | MIT，C++，125B MoE 跑 12GB，Windows |
| 机制 | HBM/DRAM/SSD 三级 + **GPU-assisted I/O + 布局解耦 + cache-aware 调度** | `--kv-streaming`：KV 常驻 pinned RAM（13.7 KB/token），VRAM 只留 attention 当前读的部分 |
| 收益口径 | vs vLLM-LMCache 最高 **5×**、vs TRT-LLM 3.75× | Q2_0 262K：50.9 → 62.6 tok/s（省显存多放专家） |

**② "无损"的真相——两家都不承诺输出逐字一致**

- OSDI 摘要**无 "lossless" 一词**，只有 "without hurting short-context performance"（**性能**无损，非输出一致）；二手精读确认全文无端到端输出等价性实验。
- Niko1221 文档明写：**"Exact token replay across restarts is not guaranteed"**、**"a switch that changes rounding can change a greedy answer at a near tie"**。其"无损"仅指 **"attention reads exactly the same values (only where the KV lives changes)"**。
- ⇒ **与 #53 结论同构：值无损 ≠ 轨迹无损。** 网友说的"无损"是值层面，不是"跨路径逐字一致"——这一点可以正面回应。

**③ 不可整体学：顺序访问是负载假设的产物**

| | Strata 假设 | 我们的现实 |
|---|---|---|
| 缓存对象 | 整段 context 前缀（多请求复用） | 229K 上下文 / 65K 池——**只能装一部分** |
| 加载时机 | **prefill 前**整段拉入（layer-by-layer） | **decode 每步**按需召回（打分 SELECT） |
| 访问集合 | 连续区间 | 稀疏、动态、非连续 |

**顺序加载 = 要求池装下全部 KV = 放弃超池**。换访问模式必须先换负载假设，不是反过来。

**④ 真实访问分布是"头 sink + 尾密集 + 中段稀疏"** ⇒ 分区策略而非二选一：头部常驻（不搬）、尾部顺序追加（本来就是顺序）、中段随机召回（打分）。现在的 KVMem 环已是此形状，缺的是把"头常驻/尾顺序"显式成独立通道。

**⑤ 三处可学（都不改超池语义）**

1. **布局解耦（治 #53 根因）**：GPU 侧固定 **layer-first**（所有 token 第 0 层连续，attention kernel 友好）、host/SSD 侧 **page-first**（大块连续，吃满 PCIe），转换在 I/O kernel 内用**算术偏移**完成（二手：几乎零开销）。**让计算侧布局稳定、存储侧自由**——这正是"布局历史 → 归约序 → 分叉"的正解方向。
2. **批量召回按逻辑序排序后再提交**：现在召回 N 页是打分集合，物理地址散乱；按 token 位置排序后提交 DMA，提高合并率，**语义不变、零风险**。
3. **层流水（layer-by-layer）**：多页召回按层分阶段搬 + CUDA event 保证"层就绪才计算"，减少"整页搬完才可用"的暴露窗口。

**⑥ 不可学**：整段顺序加载（放弃超池）；batch 编排/bubble filling（`max-concurrency 1`，无第二请求可插——但其 **loading-bound 判据**（加载 token/新输入 token 超阈值即 loading-bound，默认 100）可搬到 depth 自适应作触发条件）。

**⑦ 一个零成本测量（决定后续优化排序）**：统计 **头/尾/中段的页命中比例**（attention 权重分布）。中段只占 5-10% ⇒ 随机召回总开销小，优化应投头尾（常驻 + 层流水）；中段占 30%+ ⇒ 才值得投入"召回顺序化/预取"。

**⑧ 对外口径一句**：Strata 的"无损"是"KV 不做有损压缩、搬运不改值"，不是"输出逐字一致"；它是**层序流水**（顺序固定所以简单），我们是**随机页级召回**（所以要页状态机与记账）——不是同一问题的不同解法，是两个问题。可学的是布局解耦与 I/O 方式，不是访问顺序。

### 8.6 推送流程纪律（2026-10-26 事故后固化）

**事故链**：API 直推 → `git fetch` 失败（`Empty reply from server`）→ `git reset --hard origin/main` 落到**旧引用** → 工作区文件被删（已从 API 恢复，内容无损）。

| 场景 | 动作 |
|---|---|
| `git fetch` 成功 | 改文件 → `git add/commit` → `git push`（历史连续，**首选**） |
| `git fetch` 失败 | 改文件 → **不在本地 commit**（避免孤儿）→ API 直推（parent = 远端 HEAD）→ 保留工作区改动，等 fetch 成功后 reset |
| `reset --hard` 前置 | **必须确认** `origin/main == 远端最新 sha`，否则不 reset（旧引用会回退工作区） |

**本地丢弃提交登记**（内容已由远端承载，reflog 保护期内可查，跨 clone 不保留 ⇒ 台账备查）：

| 本地 commit | 内容 | 远端承载 |
|---|---|---|
| `62d0913` | 合并版首推 | `35958bb` |
| `c2e818e` | 撤回史归错方修正 | `f1e4c2c` |
| `cbb282a` | §八 首版 | `3cd748e` |

> sha 以 `git log -1 --format='%H %P'` 完整输出为准（本轮曾就 `20d9c2e`/`20d0913` 产生转述分歧，短 sha 口头引用易错，一律写全）。

**结构说明**：本地侧不是链式历史，是**三个兄弟提交**——三者 parent 全部是 `20d9c2e`（每次 API 直推后本地重写、再 commit，产生一个新兄弟）：

```
20d9c2e（RC1 命名，已推送的父）
  ├─ 62d0913（合并版）      → 远端 35958bb
  ├─ c2e818e（撤回史修正）  → 远端 f1e4c2c
  └─ cbb282a（§八 版，HEAD）→ 远端 3cd748e
```

**场景 2 的安全前提**：fetch 失败时"改文件 → 不 commit → API 推 → 等 fetch 后 reset"这套流程，**前提是 API 推的内容与工作区完全一致**；否则 reset --hard 会把未推送的工作区改动一起刷掉。**部分推送时（只推部分文件）禁止走此流程**，必须先 fetch 成功再动 reset。
