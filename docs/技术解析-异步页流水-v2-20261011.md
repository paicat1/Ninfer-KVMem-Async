# 技术解析：异步页流水（Async Page Pipeline / v2）

> 2026-10-11 · CodeBuddy 整理 · 对象 = 挂账 42 全链 + 挂账 44 + 挂账 46
> 读者：未来维护者 / 上游对照 / 技术复用

## 0. 一句话

> **KVMem 解决了"KV 放得下"；v2 解决了"KV 搬得起"——搬的时候不卡 decode。**

v2 前：单轮内速度可用、**多轮必死**（第二轮即掉个位数）。
v2 后：**多轮可用**（5-6 轮正常推进），深谷可**自愈爬出**。

---

## 1. 问题背景：页漂移与"多轮必死"

### 1.1 KVMem 机制回顾（数据层，继承仓二）

| 层 | 容量 | 放什么 |
|---|---|---|
| 显存池（`--kv-capacity`） | 64K token ≈ 1.7 GB（rk2v4-e8，0.83 MB/页，1 页 ≈ 32 token） | **活跃工作集**（GPU 直接读，全速） |
| 主机内存（`--host-kv-mib`） | 16 GB ≈ 600K token | 溢出页/冷页（需要时召回） |
| 逻辑上下文（`--max-context`） | 256K token | 虚拟账本 |

decode 每步只读**活跃工作集**：sink 5120（开头常驻）+ window 32768（最近窗口）+ 检索召回（实测 128 页 ≈ 4K token）≈ 42K token —— **< 64K 池**，这就是"64K 显存撑 256K 上下文"的数学。

### 1.2 页漂移（挂账 42 本体）

多轮 cache replay 逐轮把最早页挤出设备池（34 轮 → ~330 页滞留 host）→ **召回/驱逐需求随轮数暴增**。

### 1.3 v2 前的病态（定量证据）

| 时段 | 引擎 | 中位数 decode | p25 | 峰值 |
|---|---|---|---|---|
| 14:5x（挂账 42 前） | 凌晨版 | **5.6** | **1.2** | 343.7 |
| 20:4x-20:5x | **v2** | **100.5** | 79.5 | **333** |

凌晨版形态 = **深谷（大部分时间个位数）+ 偶发冲刺**；多轮场景下"第二轮即死"——**服务不可用级别**。

---

## 2. 机理：搬运为什么卡 decode

### 2.1 挂账 44 profile 定案（真凶锁定）

demote 路径 profile 采样（`NINFER_DEMOTE_PROFILE=1`）证实：
- **真凶 = compute stream 上的同步 D2H 拷贝**——慢峰 3.4-7.8 ms/批（快慢双峰分布，差距 10-20 倍）；
- **页账本 / arena 分配 / 发布路径全部无罪**（profile 逐段排除）。

### 2.2 调用链（为什么"步间检查点"够不着）

```
decode.cpp 每步 → ensure_sequence_kv_mapped → ensure_ring_room
                    → demote_other_addresses_to_host + demote_kv_pages_to_host（批量）
                    → restore_kv_pages_from_host
```
页操作在**单个 decode 步内部**执行——官方取消检查点在**步间**（`openai_chat_http.cpp:200`）——页漂移极端态下步内长时间卡同步，**检查点无法到达**（挂账 41 并入 42 的根因）。

## 3. v2 机制：异步页流水

### 3.1 核心思想

**拷贝提交后立即返回**（不等待）；拷贝在 **transfer stream** 上飞行；**下一步的 demote 调用收割**（此时的等待已被上一步 kernel 时间覆盖 ≈ 0ms）。

### 3.2 实现（`PendingDemote`，每 KV store 一槽）

```cpp
struct PendingDemote {
    std::optional<HostKVExtentReservation> reservation;  // extent pin（RAII）
    std::vector<LogicalKVPageHandle> handles;            // 已 prepare 的页
    LogicalKVPageStore* store = nullptr;                 // 来源 store
    bool submitted = false;                              // copy 已提交 transfer_streams
};
std::optional<PendingDemote> pending_demote_text_;
std::optional<PendingDemote> pending_demote_backend_;
```

**提交路径**（`demote_kv_pages_to_host`）：首个满批（K=8 页）异步提交——
① 先排序在所有已入队 compute 写之后（capture.cpp 先例）；② D2H 拷到 **transfer_streams**；③ extent 交给槽，**函数立即返回**。

**收割路径**（`retire_pending_demote`，在下次 `ensure_ring_room` 最前）：
wait copy event（实测 **max 0.22 ms**）→ **publish**（extent 账本）→ 逐页 **release + drop**（device replica）。

**RAII 析构**：槽逆序析构——extent pin 释放前 transfer 必须 land（否则会写进已回收的 arena 内存）。

**开关**：`NINFER_ASYNC_DEMOTE`（默认 1=ON；0=同步批量回退 = A/B 对照臂）。

### 3.3 为什么这样是安全的（正确性契约）

| 契约 | 保持方式 |
|---|---|
| 页只在 publish 后 drop device replica | 收割顺序固定（wait → publish → release/drop） |
| 部分 demote = 合法中间态 | 已 demote 页是完整发布（copy+publish+drop 全done）——重试安全 |
| 取消安全 | 页边界取消检查点（`decode_cancelled()` break——挂账 42/41 第一步） |
| 取消场景兜底 | `ensure_ring_room` 现有 early-verdict（free 不足 → 请求失败释放槽位） |

## 4. 与 KVMem 的关系（技术解说）

### 4.1 两层架构——不是两个机制，是一个机制的两层

```
数据层（KVMem，仓二继承）：KV 页放哪（显存池/主机内存）、何时召回（打分 SELECT）
搬运层（v2，本仓新）：      页怎么搬——"搬得不卡 decode"（异步流水）
```

### 4.2 逐项对照

| | KVMem（仓二） | v2（本仓） |
|---|---|---|
| 管什么 | KV 页的**存储位置**与召回决策 | 页搬运的**时序**（与 decode 解耦） |
| 层面 | 数据（存储层次扩展） | 时序（流水线化） |
| OS 类比 | **虚拟内存 + 按需调页** | **异步 I/O**（脏页后台回写 / 预读） |
| 解决 | "小显存跑大上下文"（放得下） | "搬运不打断解码"（搬得起） |
| 关系 | v2 是 KVMem 的**完成态**——数据层 + 时序层合起来才是完整能力 |

### 4.3 为什么 v2 是"KVMem 的完成态"

KVMem 的设计初衷 = 小显存跑大上下文——**但同步搬运让"多轮长会话"场景失效**（页风暴时 decode 等死）。v2 补齐时序层后，KVMem 的全部价值才真正释放：**多轮可用 + 深谷自愈**。

### 4.4 常见误解澄清

| 误解 | 事实 |
|---|---|
| "把 decode 下放到内存然后召回" | ❌ decode 计算**从未离开 GPU**（现在也全在 GPU）——变的是"页等待"从关键路径消失 |
| "把上下文放在内存里" | 部分对——放的是 **KV cache**（注意力键值中间状态），不是上下文文本本身 |
| "DECODEMEM"（用户命名） | 精神对（页自由流动、解码永不等页）；精确名 = **异步页流水（Async Page Pipeline）** |
| "检索命中会受 KV 量化影响" | ❌ 检索打分**不读 KV 页内容**（查预计算分数表，`context.cpp:1734`）——召回决策与 KV 精度无关 |

## 6. 死亡谷（Death Valley）分析与下一步

### 6.1 现象与解剖（req#61 三段式）

| 阶段 | 时长 | decode | host |
|---|---|---|---|
| 谷 | 100s | 1.0-6.2 | 84-126% |
| 峰（自愈爬出） | 60s | 72-228 | 98-101% |
| 深谷 | 155s | 3.2-27.2 | **峰值 318.5%** |
| 峰收尾 | 15s | 175-219 | ~98% |

（prompt 55,364 | output 16,108 | total 6m0.3s | 16K 输出**全部完成**）

### 6.2 数据结论

- **主因 = demote copy 慢**：16 样本 avg **11.5** / max **33.68 ms**（8 页/批，正常应 1-3ms）——PCIe 竞争/排队；
- **非主因 = retrieve**（仅 3 次/6 分钟）；
- **机制本身健康**：retire wait max 0.22ms（异步收割零等待）。

### 6.3 下一步（v2.1，设计稿已入库）

**多批 in-flight**（`PendingDemote` 单槽 → N 槽环形队列 + `cudaEventQuery` 非阻塞收割）——
填满 PCIe 流水，直接削谷。设计稿：`docs/设计-挂账46-v2.1多批in-flight-20261011.md`。
后续：早期页 pin（减少搬运需求，根本解）→ 步级预算（摊平变浅）。
