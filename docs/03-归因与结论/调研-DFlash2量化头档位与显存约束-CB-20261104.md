# 调研：DFlash2 量化头档位与 16 GB 显存约束

- 日期：2026-11-04
- 对象：`Qwen3.8-27B-DFlash2` 各量化档（dense 27B 专用，非 MoE）
- 方式：HF-Mirror API 全档枚举 + 上游 `kvmem` 文档的实测记录（`refs/kvmem-kvmem-main/docs/dflash2-quantized-heads.md`）
- 证据等级：**实测数字**（RTX 5060 Ti，2026-10-26 Task 1）+ **文件级 SHA-256**

---

## 〇 一句话

**dense 27B 的 DFlash2 头有 7 个量化档（最小 Q2_K 0.657 GB），但实测 Q3_K_M 只比 Q4_K_M 省 174 MiB 显存——而 Coder390 需要省 706 MiB，差 4 倍。⇒ 换档救不了 Coder390。**

## 二 NInfer 的支持范围

`dflash2-quantized-heads.md:3-5` 原文：

> The NInfer backend can import the Qwen3.8-27B DFlash2 **Q3_K_M/Q4_K_M** companions **without converting**
> their attention output and MLP down projections to Q8.

| 档 | NInfer 支持 |
|---|---|
| Q3_K_M | ✅ 文档明写 |
| Q4_K_M | ✅ 文档明写 + 本仓已实证（§203） |
| NVFP4 | ✅ 文档明写（ModelOpt 源适配器） |
| **Q2_K** | ⚠ **文档未提**，是否支持未知 |

**转换命令（现成，`--components text,mtp,dflash2`）**：

```powershell
python -m tools.convert --model <target-metadata> \
  --recipe qwen3_5_dense_gguf --source gguf=<target.gguf> \
  --source dflash2=<Qwen3.8-27B-DFlash2-Q3_K_M.gguf> \
  --override tools/convert/recipes/dflash2_gguf_blocks.py \
  --components text,mtp,dflash2 --device cpu --out target-dflash2-q3.ninfer
```

**关键**：文档 L78 原文 —— **"The original MTP component can coexist in the same artifact and remains selectable with `--spec mtp`"**
⇒ **一个件内可同时装 MTP + DFlash2，按 `--spec` 切换。**

## 四 为什么 Q3_K_M 救不了 Coder390

### 4.1 显存只差 174 MiB，不是 210 MB

```
Q4_K_M 峰值  14,600 MiB
Q3_K_M 峰值  14,426 MiB
──────────────────────
差            174 MiB
```

**GGUF 文件差 0.21 GB，但容器内只差 174 MiB** —— 因为容器里还有**不随 K 档变化的部分**：
Q6_K 张量、BF16 conv 投影、Q8 QKV、norms。

### 4.2 而缺口是 706 MiB

由用户实测事实反推（`MTP 完全卸载 + 0 池都不够`）：

```
SWIFT   : 13.29 GiB（含 DFlash2 头）+ 32K 池 0.80 GiB = 14.09 GiB  ⇒ 能起
Coder390: 13.40 GiB + 头 X + 0 池                                 ⇒ 起不来
⇒ X > 0.69 GiB（≈706 MiB）
```

```
需要省        706 MiB
Q3_K_M 能省   174 MiB
──────────────────────
缺口          532 MiB
```

**⇒ 差 4 倍，换档不可行。**

### 4.3 而且代价也不划算

```
接受率      Q3 74.7%  <  Q4 76.5%
代码吞吐    Q3 86.54  <  Q4 88.26   （低 2%）
```

**⇒ Q3_K_M 省的显存不够，收益还更低。**

### 4.4 NVFP4 更差

```
峰值显存  14,556 MiB（比 Q3 多 130 MiB）
代码吞吐  76.70（比 Q4 低 13%）
```

**⇒ 权重 NVFP4 在这条线上不如 GGUF companion。**

## 五 结论

| 档 | 峰值显存 | 相对 Q4 省 | Coder390 可用 |
|---|---:|---:|---|
| Q4_K_M | 14,600 MiB | — | ❌ 缺 706 MiB |
| Q3_K_M | 14,426 MiB | 174 MiB | ❌ 仍缺 532 MiB |
| NVFP4 | 14,556 MiB | 44 MiB | ❌ 且更慢 |
| Q2_K（0.657 GB） | 未知（NInfer 未提） | 估 300 MiB 量级 | ⚠ 即使支持仍不够 |

**⇒ 16 GB 卡上 Coder390 + DFlash2 这条路，换档救不了。**

**根因不在头，在 Coder390 本体**：

```
Coder390 权重 13.40 GiB  vs  SWIFT 13.29 GiB   ⇒ 差 0.11 GiB
池需求                   54K→32K = 22K 页       ⇒ 差 0.57 GiB
──────────────────────────────────────────────────────────
合计                                            ≈ 0.68 GiB
```

**⇒ 除非换更小的 Coder390 权重档（如 IQ3_XXS），否则此路不通。**

## 六 附带发现：CUDA Graph 预留差 40 倍

| 来源 | Graph 预留 |
|---|---|
| 上游 `dflash2-quantized-heads.md` | **128 MiB** planning allowance |
| 本仓 `--adaptive-mtp`（§205） | **5.06–5.29 GiB** |

**⇒ 上游只用 128 MiB，我们预留 5 GiB，差 40 倍。**

如果 Coder390 的 706 MiB 缺口里有一部分来自 Graph/workspace 预留，**那才是真正能省的地方**（不是头）。

**待查**：`--adaptive-mtp` 的 5 GiB 预留来自什么（是 Graph 还是别的）。
