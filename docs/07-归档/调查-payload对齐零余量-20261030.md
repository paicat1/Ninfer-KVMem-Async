# 调查：payload 对齐零余量（2026-10-30）

> **来源**：`_research/codebuddy-mtp-roadB-数据侧重打包.md` §5.2 指出的风险 —— 描述准确，但**落地时怎么处理的没有记录**。
> **性质**：**未完成调查**。本页记录"已知什么 / 不知道什么 / 怎么查"，不编结论。

## 一、已知（来自 10-09 调研，原文有据）

```
原始件 json_bytes = 249,824
32 + 249,824 = 249,856 = 61 × 4096     ← 正好卡在 4096 对齐边界，零余量
```

| 改法 | JSON 变化 | payload 起点 | 后果 |
|---|---|---|---|
| `gguf_q4_0`(9 字符) → **`gguf_iq4_nl`**(10 字符) | **+5 字节**（×5 个张量） | **+4,096** | 全部对象 `offset` 平移 ⇒ **整包 13.27 GB 必须重写** |
| `gguf_q4_0` → `gguf_q4_k`（同为 9 字符） | **0 字节** | 不变 | 可原地覆写 5 段 |
| 用 iq4_nl 但从 `provenance` 裁掉 ≥5 字节 | ≤0 | 不变 | 可原地 |

## 二、不知道（本页的核心）

**P1b 实际产物（`.mtp-iq4nl*.ninfer`）走的是哪条路？**

- 是整包重写（payload 起点 +4096）？
- 还是裁了 JSON（起点不变）？
- 还是……？

**没有任何记录。** 10-09 审核件只写了"5 个张量 238,878,720 B、Δ0"，**没说文件总大小、没说 payload 起点**。

## 三、怎么查（零机时，一条命令）

对产物读前 32 字节取 `json_bytes`，算 `align_up(32 + json_bytes, 4096)`：

```python
import io, struct
p = r'<P1b 产物路径>'
h = io.open(p, 'rb').read(32)
json_bytes = struct.unpack('<Q', h[8:16])[0]
start = ((32 + json_bytes + 4095) // 4096) * 4096
print('json_bytes=%d  payload_start=%d  (原始件 249824/249856)' % (json_bytes, start))
```

| 结果 | 含义 |
|---|---|
| `json_bytes == 249,829` 且 `start == 253,952` | **整包重写**（+4096 位移），对象 offset 全变 |
| `json_bytes <= 249,824` 且 `start == 249,856` | **裁过 JSON**，可原地 |
| 其它 | 需进一步看目录 JSON 的 `provenance` 差异 |

## 四、为什么值得留这一页

**"零余量"是个只在特定边界出现的陷阱**：`json_bytes` 恰好让 `32+json_bytes` 落在 4096 整数倍上，任何格式名变长 1 个字符都会触发整包重排。

**下次换格式（例如再想改 dtype）会再撞一次。** 不写下来，就要重新推一遍。
