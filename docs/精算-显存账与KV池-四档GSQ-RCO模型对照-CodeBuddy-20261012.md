## 0. 口径与三个硬锚（一切计算的基石）

**锚 1 · 页账（最精确）**：`1 页 = 64 token`；`rk2v4-e8 下 1 页 ≈ 0.83 MiB`
- 构建史四组页数-容量对全部 = 64 tok/页：8,192/128 页、20,480/320 页、32,768/512 页、40,960/640 页、55,296/864 页、65,536/1024 页
- ⇒ 现池预算 = **864 页 ≈ 717 MiB**（rk2v4-e8）；每 token ≈ 13.3 KiB（理论构型 13.0 KiB，取实测 0.83 MiB/页 口径）

**锚 2 · 标定差**：55,296 → 65,536（+160 页）恰需 +128 MiB（`--cuda-graph-allowance-mib 128` 补缺起服）
- 160 页 × 0.83 MiB = 132.8 MiB ≈ 128 MiB ✓（±3%）

**锚 3 · 理论构型**：16 全注意力层（64 层 4:1 混合）× 8 KV heads × 128 head_dim
- rk2v4-e8 = K 2bit(256B) + V 4bit(512B) + scales/e8(64B) = 832 B/层 → ×16 = **13.0 KiB/token** ✓
- k8v4 同法 = 1600 B/层 = 25.0 KiB/token —— 与教程"每 token ≈ 25 KiB（k8v4）"逐字吻合 ✓

**锚 4 · 权重实测**：当前上卡权重 = **12.30 GiB**
- README 显存账："权重 12.3 GiB + 高速池/工作区 1.9 GiB + 视觉，free 490 MiB"
- 构建史实测：Q8MTP 版 `loading weights | 12.5 GiB`（10-10 00:32）− iq4_nl 头省 212 MB ≈ 12.29 GiB ✓ 双源吻合

**当前池标定（本库实测）**：40,960 稳定 → **51,200 稳定** → **55,296 贴边**（缺 17-50 MiB 随桌面波动）→ **65,536 实测成功**（需 graph128 + 净桌面 ≤~1.0 GiB）→ **81,920 实测成功（2026-10-13；98,304 被拒 -134 MiB）**
- 用户"卡在 55K 左右" = 55,296 贴边口径 ✓

## 3. 能力对照（换过去能力怎么变）

**3.1 底座差异（最大变量）**：Swift-1.5 = Qwen3.8-27B 的"推理高效型"微调（UkisAI）——**与现役 Coder390-EfficientThink 同向，但微调方不同**。
- 官方 BF16 基准（ukisai.com）：比 Qwen3.8-27B 少 **58.5%** 思考 token（中位），8 项基准 6 项不降反升：
  - **LiveCodeBench v6 76.76 → 81.71（+4.95）** · **Terminal-Bench 2.1 69.21 → 72.13（+2.92）** ← 编码/agentic 向增强（正是本线用途区）
  - GPQA +0.31 · C-Eval +0.92；略降：ERQA −2.05 · AIME −2.67 · HMMT −2.00 · IFBench −1.46
- 训练路径：RL + 同策略蒸馏，聚焦**长时程 agent 与编码任务**（与 DSH agentic 用途吻合）。
- ⇒ **换底座 ≠ 降级**，是"换任务画像"：编码向大概率持平/更强，纯推理向略弱（参考量级：1-3 分）。

**3.2 量化损失（GSQ-RCO 方法 + 官方 KLD 表，v2 更新）**：
- GSQ（Gumbel-Softmax 学习网格+scale）+ RCO（黎曼约束逐张量比特分配），2026 新方法；实现路径：复用 ISTA-DASLab 的逐张量分配 + Swift V1MIX importance matrix 精炼。
- **ukisai 源 GGUF 仓的官方 KLD 表**（相对 Swift-1.5 BF16，512-token 口径；code 域 = CodeParrot，散文 = C4）：

| 档 | 开发集 KLD | code 域 KLD | C4 KLD | 中文 KLD |
|---|---:|---:|---:|---:|
| IQ2_XS | 0.189979 | 0.120884 | 0.161594 | 0.207063 |
| IQ2_S | 0.134751 | 0.084739 | 0.107438 | 0.129485 |
| IQ3_XXS | 0.097774 | 0.062546 | 0.080238 | 0.103141 |
| **IQ3_S** | **0.051265** | **0.035447** | 0.041748 | 0.052241 |

- 参照系：KLD <0.05 ≈ 接近无损；IQ3_S（code 0.035）量化损伤确实小；IQ2_XS（0.121）已偏大。
- ⚠️ 官方自注：512-token 测试**不能说明长上下文质量**；且 ukisai 精炼版与 ISTA 对照并非全面更优（数学文本 KLD 高 4.9-7.7%、IQ3_S 在 7 域中 5 个高于 ISTA 对照）；这是分布指标**非任务分**。
- 与 ISTA 官方数字（经引述）：2.75bpw 档零样本综合均分 **75.70 vs BF16 74.34**；同体积对 Unsloth UD-IQ2_S：**AIME25 +10.0 / GPQA +8.6 / LCB +4.6**。

**3.3 与当前 Q2LynnStyle 的关系（v2 修正）**：
- **Q2LynnStyle 真实构成（Merkyor 官方）**：BPW = **3.89**（"LynnStyle" = 混合精度风格、最低下探到 Q2，**非全模型 2bit**）。LynnStyle 全谱：Q2 3.89 / Q3 5.07 / Q4 5.75 / Q6_K 6.79 / Q8_0 8.51。
- 本库鉴定（804 对象）：真 Q2 级张量仅 **23 个**；主体为 iq3_s(144) + iq4_xs(76) + q4_k(67) + iq3_xxs(26) + iq2_s(21) 混合；bf16/fp32 高精度小张量 456 个；MTP 头 5×q4_0。
- **IQ 四档换算 BPW（÷27.32B 参数）**：IQ2_XS **2.62** / IQ2_S **2.71** / IQ3_XXS **3.12** / IQ3_S **3.62** —— **四档全部低于 Q2Lynn 的 3.89**。

- **结论修正**：IQ3_S 量化损伤小（code KLD 0.035）为真，但**"质量更优"不成立**——其 bpw 低于现役 Q2Lynn；两边量化损失都不大，差异主因在**底座微调**（Swift-1.5 vs Coder390）+ 方法（GSQ-RCO vs imatrix+Lynn 配方）——须本机 A/B。

## 7. 池目标函数的修正：异步页流水之后，32-64K 即正解（v2 新增）

**背景**：v2 异步页流水（`patches/ledger42_v2_async_demote.patch`）使 demote/restore 与 decode 流水并行——**物理池从"容量门槛"降级为"搬运频率旋钮"**。本库实测：74.4K 深超池（host 99%）decode 仍 **114.4 tok/s**；深谷可自愈爬出；多轮对话可用（v2 前多轮必死）。⇒ **不必追 262K 全驻留**。

**新目标**：池 **32K（能跑）~ 64K（充裕）**；剩余显存全部转投"权重档 vs KV 档"。

### 7.3 结论

- **不换模型的同预算升级三选一**：`55.3K + rk2v4-e8`（现状，最快）/ `32K + rk4v4-e8`（KV +1 档，池减半）/ `28.8K + k8v4`（KV 到官方默认档）。
- ⚠️ **谷视角修正（v2.1）→ 放行 + 两条硬约束（v2.2 更新）**：后两档的隐性谷代价为现状的 8-13 倍（demote 量 ∝ (上下文−池) × 每token字节），但 **v2.1 默认 depth=1 已移除灾难性放大项（R2 §三）⇒ 不再"暂缓"**。新增两条实机实证的硬约束：
  - **① 预算线约束**：缩池换精度必须留在"该精度的预算线"内——`k8v4` 只能 ≤ **28,800 贴边 / 26,624 稳定**，**不是 32K**（32,768@rk8v4 实机越线 ≈97 MiB → 页账故障 + HTTP 500，构建史 §三·二十二）；
  - **② prompt 约束**：池 ≥ 预期最大 prompt（DSH agentic 会话 45-73K）。
  两条约束的算术（构建史 §三·二十三 §2）：现模型上"49.6K prompt + k8v4"物理不可行（需 1,231 MiB > 预算；rk2v4 只需 642 MiB）⇒ **要兼得只能换更小的模型档**（§7 换模型路线）。
- **换模型最优组合（64K 池固定）**：**IQ3_S + 61.6K@k8v4**（全面小升，最保守）；**IQ3_XXS + 64K + int8**（池翻倍 + KV 升 2.54×）；**IQ2_S + 64K + bf16**（KV 天花板，权重降至 2.71bpw）。⚠️ 同样受 §7.4 谷负担公式约束（大池是它们的成立前提）。
- **待测汇率**：权重 bpw vs KV 档，谁更伤代码质量——先做 KV A/B，再定换模型方向。

### 7.4 池的第三重身份：死亡谷的缓解旋钮（v2.1 追加）

> 缘起：用户提出"池大是否也能配合异步机制，缓解死亡谷的深度/概率/延续时间"——机制分析成立，且反向修正了 §7.3 的推荐。

**谷的机理链（req#61 解剖，构建史 §三·十九）**：
多轮堆积 → 页漂移深 → demote 需求暴增 + copy 慢（avg 11.5 / max 33.68 ms/批，PCIe 竞争）
→ 页操作总耗时超步窗口（host 200-318%）→ decode 步几乎全在等页 → demote 消化完后自愈。

**⚠️ 机理更新（v2.2 · 2026-10-13，I1/I2 深挖）**：
- **demote / ring / restore 三路已排除**：环内五段亚毫秒级、STALL=0、回收零等待；深谷时 `mask=0 / SELECT=32 / retrieve=25`（近乎静默）而 host 94-148%、GPU 99%、**每 token ≈3 s host 工作** ⇒ 本谷是"**静默自旋**"，**瓶颈在环外未计量路径**（推翻"谷=demote 风暴"的旧表述）；
- **触发与 host 页库规模相关**：谷起点紧随页库 1.42→1.49 GB 跳变（重填新增页）——"页库规模相关成本"嫌疑（下一刀：I3b 步级仪表）；
- ⇒ §7.4 核心公式**方向不变**（池大 → 超池量小 → 页库/搬运成本低），但"谷负担"的构成扩展为"页库规模相关成本"。

**⚠️ 机理更新二（v2.3 · 2026-10-14，夜间自动迭代）**：
- **GPU 侧自旋指纹**：谷期 util 99.8-100% + SM 满频 2,910 MHz + pmon 锁定 ninfer-serve（87-99%），但**显存控制器仅 2.6-9%**、功耗 63-98 W（健康 129-217 W/64%）；单轮墙钟 400-1,019 ms = **1107 节点 × ~24 µs/节点**（健康 27-32 ms）⇒ 自旋在**图内节点间隙**；已排除提交/驱动、降频、外部进程、带宽拉爆；
- **谷 = 时间现象，非 token 现象（A2 lossless gate 通过）**：同 prompt 池内与首次超池的输出 **sha 逐字相同**——超池本身不改变输出，谷是**时段性**降速；
- **机器级粘性**：谷跨引擎重启存活 ≥4.5 小时（非进程状态）；三次自愈（23:45 / 01:06 / ~05:40）+ 两次来袭，触发源未明（守望者已上线抓它）。

**池的作用（四个环节全单调缓解）**：

| 环节 | 池大的效果 |
|---|---|
| ① 漂移起点 | `depth = pool − working_set`（tancau 作者级公式）→ 触发更晚（实测：64K 比 51K 多撑 ~8 轮） |
| ② 需求速率 | demote 量 = 上下文 − 池 → 池大 → 需求速率低 → **谷概率↓** |
| ③ 拖死程度 | 积压量 ∝ 单次需求批次 → 池大 → 积压小 → **谷深度↓** |
| ④ 自愈时间 | 谷时长 ≈ 积压 ÷ 消化速率 → **延续时间↓** |

**核心公式**：`谷负担 ∝ (上下文 − 池tokens) × 每token字节`（池与 KV 精度在此式中是乘法关系）。

**隐性谷代价（以 60K 上下文为场景）**：

| 组合 | demote 量 | 谷负担 | 相对现状 |
|---|---:|---:|---:|
| **现状：55.3K + rk2v4-e8** | 4.7K tok × 13 KiB | **61 MiB** | 1.0× |
| 41.3K + rk4v4-e8（同预算） | 18.7K × 17.4 | 325 MiB | 5.3× |
| 32K + rk4v4-e8 | 28K × 17.4 | 487 MiB | 8.0× |
| 28.8K + k8v4 | 31.2K × 25 | 780 MiB | 12.8× |

⇒ **"池小 + KV 高"是死亡谷最差组合**；低 KV 精度反有"页小搬运快"的谷内优势（同批 8 页，rk2v4 的字节量是 k8v4 的 52%）。

**两种工作集（池作用分两段）**：
- 单轮活跃集（窗口 32,768 + sink 5,120 ≈ 38K）——池 ≥ ~40K 后单轮型谷饱和；
- 多轮累积集（页漂移，可涨到 100K+）——池只能"挪悬崖"（tancau 原话），每轮抬升需求速率。

**池的边际价值曲线**：40K 以下陡（削谷显著）→ 40-64K 平缓（只对多轮型）→ 64K 以上贴边风险（启动不稳/分配失败路径；55,296 不可复现 vs 51,200 稳定；挂账 47 教训）。

**三条路（顺序建议）**：

| 路 | 动作 | 预期 | 代价 |
|---|---|---|---|
| A. 池 | 维持大池（55.3K） | 谷最稳 | 挤占 KV/权重预算 |
| **B. 引擎** ⭐（部分落地） | ① depth=1 默认（移除灾难放大项）✅；② "在飞页计入空闲裁决"已施工（`ledger46_v2.1_inflight_demand_fix.patch`）但 depth≥2 端到端更差（未启用）；③ **谷未根治**——新靶心 = 静默自旋（环外路径），I3b 步级仪表为下一刀；④ 顺带修复：超池页账 500（writer-blocked reconcile v2，A/B 2/2→0/0）✅ | 谷内 decode 恢复目标不变 | 引擎施工（滚动进行中） |
| C. KV | 升精度 | 质量↑ | 谷负担 ×5-8（同预算池必缩） |
